## 验证断言回查任务

{{REGRESSION_DATA}}

## 背景

daily-review 的 issue 产出规范要求每个 issue 携带「验证断言」段（断言/检查方式/到期日期）。断言到期（创建后 30 天）时需要回查：修复到底是否兑现——**「修复」是可证伪的假设，不是一次性动作**（R20260916rsis 缺口 2）。

**断言 = issue 作者写死的「问题还在判据」**：什么条件满足 = 问题仍未解决 / 修复未兑现。判定方向在提 issue 时写死，回查只判「判据是否成立」，不反向解读。

## 执行步骤

对上述每个到期断言，逐条执行：

1. **读 issue**：`gh issue view <N> --json body,state,title`，定位「验证断言」段（## 验证断言 下的断言/检查方式/到期三行）。issue 里没有验证断言段 → 在评论中提醒补写（这是规范漏洞，不是跳过），然后标记本条「无断言」
2. **执行检查方式**：按断言写的检查方式实际执行（sqlite 查询先按 daily-health-check 前置纪律确认 dbPath / gh 命令 / 读文件核对）。不凭印象判断，必须真的跑
3. **判定**：断言 = 「问题还在判据」，只判「判据是否成立」——
   - **判据满足**（问题还在 / 修复未兑现）→ ❌ 未通过
   - **判据不满足**（问题已消失 / 修复已兑现）→ ✅ 通过
   - 证据不足/数据源缺失 → ⚠️ 无法判定（说明缺什么）
   不反向解读：判据写成「X 仍不存在」「率仍 <30%」这类「问题还在」表述时，判据不满足 = 问题已消失 = ✅ 通过，绝不判 ❌
   断言若写成「好结果」方向（如「修复后 X 不再发生」「覆盖率 ≥80%」）而非「问题还在」方向 → 不猜方向，本轮标 ⚠️ 无法判定，评论提醒作者按「问题还在判据」改写后下次再回查
4. **回写评论**：在 issue 留评论，格式：

```
🔁 验证断言回查（到期 <到期日期>）
- 断言：<原文>
- 检查方式：<实际执行的命令/查询>
- 证据：<关键输出摘要>
- 判定：✅ 通过 / ❌ 未通过 / ⚠️ 无法判定
<!-- regression-verify: issue=<N>; verdict=pass|fail|unknown; at=<ISO时间> -->
```

5. **未通过处置（仅「判据满足 = 问题还在」适用）**：❌ 的 issue 若已 closed → 重开并升一级优先级（P2→P1），评论说明「问题仍在/修复未兑现」；若仍 open → 评论提醒，不重复升级。**判据不满足一律 ✅ 销案**：issue 若 open 按「问题已解决」关闭（评论写明判据不满足的证据）；若已 closed 保持不动，绝不重开。⚠️ 的保持 open 状态不动，等下一次回查窗口

## 纪律

- 每个断言必须有真实执行的证据，禁止「凭逻辑推断已通过」
- **重开/升级的唯一判据 =「问题还在判据」成立**（问题仍在 / 修复未兑现）；判据不满足（问题已消失）绝不重开——「预言坏状态」类断言，判据不满足 = 问题消失 = 销案（先例：评测机制去留已拍板后仍被反复重开）
- 一天最多回查 10 条（防爆量；超过时按到期日从早到晚取前 10，剩余的明天继续）
- 全部处理完后输出一行汇总：回查 N 条 → ✅ a / ❌ b / ⚠️ c / 无断言 d
