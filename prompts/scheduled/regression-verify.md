## 验证断言回查任务

{{REGRESSION_DATA}}

## 背景

daily-review 的 issue 产出规范要求每个 issue 携带「验证断言」段（断言/检查方式/到期日期）。断言到期（创建后 30 天）时需要回查：修复到底是否兑现——**「修复」是可证伪的假设，不是一次性动作**（R20260916rsis 缺口 2）。

## 执行步骤

对上述每个到期断言，逐条执行：

1. **读 issue**：`gh issue view <N> --json body,state,title`，定位「验证断言」段（## 验证断言 下的断言/检查方式/到期三行）。issue 里没有验证断言段 → 在评论中提醒补写（这是规范漏洞，不是跳过），然后标记本条「无断言」
2. **执行检查方式**：按断言写的检查方式实际执行（sqlite 查询先按 daily-health-check 前置纪律确认 dbPath / gh 命令 / 读文件核对）。不凭印象判断，必须真的跑
3. **判定**：证据满足断言 → ✅ 通过；不满足 → ❌ 未通过；证据不足/数据源缺失 → ⚠️ 无法判定（说明缺什么）
4. **回写评论**：在 issue 留评论，格式：

```
🔁 验证断言回查（到期 <到期日期>）
- 断言：<原文>
- 检查方式：<实际执行的命令/查询>
- 证据：<关键输出摘要>
- 判定：✅ 通过 / ❌ 未通过 / ⚠️ 无法判定
<!-- regression-verify: issue=<N>; verdict=pass|fail|unknown; at=<ISO时间> -->
```

5. **未通过处置**：❌ 的 issue 若已 closed → 重开并升一级优先级（P2→P1），评论说明「修复未兑现」；若仍 open → 评论提醒，不重复升级。⚠️ 的保持 open 状态不动，等下一次回查窗口

## 纪律

- 每个断言必须有真实执行的证据，禁止「凭逻辑推断已通过」
- 一天最多回查 10 条（防爆量；超过时按到期日从早到晚取前 10，剩余的明天继续）
- 全部处理完后输出一行汇总：回查 N 条 → ✅ a / ❌ b / ⚠️ c / 无断言 d
