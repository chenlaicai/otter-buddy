## 验证断言回查任务

{{REGRESSION_DATA}}

## 背景

daily-review 的 issue 产出规范要求每个 issue 携带「验证断言」段（断言/检查方式/到期日期）。断言到期（创建后 30 天）时需要回查：修复到底是否兑现——**「修复」是可证伪的假设，不是一次性动作**（R20260916rsis 缺口 2）。

## 执行步骤

对上述每个到期断言，逐条执行：

1. **读 issue**：`gh issue view <N> --json body,state,title`，定位「验证断言」段（## 验证断言 下的断言/检查方式/到期三行）。issue 里没有验证断言段 → 在评论中提醒补写（这是规范漏洞，不是跳过），然后标记本条「无断言」
2. **执行检查方式**：按断言写的检查方式实际执行（sqlite 查询先按 daily-health-check 前置纪律确认 dbPath / gh 命令 / 读文件核对）。不凭印象判断，必须真的跑
3. **判定**：先分辨断言类型，再判定——
   - **修复型断言**（断言「修复已生效」，预期好结果出现，如「修复后 X 不再发生」「覆盖率 ≥80%」）：证据满足 → ✅ 通过；不满足 → ❌ 未通过；证据不足 → ⚠️ 无法判定（说明缺什么）
   - **预测型断言**（断言「坏状态持续/机制死亡」，预期坏结果，如「仍不存在」「仍 <30%」「机制确认死亡/空心」）：
     - **证伪**（坏结果未发生、机制存活、问题未恶化）→ 正向结果，判定写 **✅ 通过（预测证伪=机制存活）**，不按「未通过」处置
     - **成真**（坏结果确实持续）→ ❌ 未通过，按问题持续处理
4. **回写评论**：在 issue 留评论，格式：

```
🔁 验证断言回查（到期 <到期日期>）
- 断言：<原文>
- 检查方式：<实际执行的命令/查询>
- 证据：<关键输出摘要>
- 判定：✅ 通过 / ❌ 未通过 / ⚠️ 无法判定
<!-- regression-verify: issue=<N>; verdict=pass|fail|unknown; at=<ISO时间> -->
```

5. **未通过处置（仅修复型断言适用）**：❌ 的 issue 若已 closed → 重开并升一级优先级（P2→P1），评论说明「修复未兑现」；若仍 open → 评论提醒，不重复升级。**预测型断言证伪不在此列**——证伪=机制存活，issue 若 open 按正向销案关闭（评论写明「预测证伪=机制存活，无需修复，销案」）；若已 closed 保持不动，绝不重开。⚠️ 的保持 open 状态不动，等下一次回查窗口

## 纪律

- 每个断言必须有真实执行的证据，禁止「凭逻辑推断已通过」
- **预测型断言证伪 ≠ 修复未兑现**：重开/升级只针对「修了没修好」，不针对「预言的坏结果没发生」（先例：评测机制去留已拍板后仍被反复重开）
- 一天最多回查 10 条（防爆量；超过时按到期日从早到晚取前 10，剩余的明天继续）
- 全部处理完后输出一行汇总：回查 N 条 → ✅ a / ❌ b / ⚠️ c / 无断言 d
