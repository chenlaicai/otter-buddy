# 作者处置协议（对检视发现的回应）

检视发现不等于命令。作者对每条发现必须批判性评估后逐条处置——但反驳必须带证据，空驳回等同未处置。本协议同时约束两端：作者按四分类回应，检视者按证据评估反驳。

## 四分类处置

每条检视发现必须回应为以下之一：

1. **接受并修复** — 说明修复方式
2. **反驳** — 必须附证据：`file:line`、测试运行结果、方案/设计文档原文。"我觉得没问题"、"过度设计"、"影响不大"这类无证据驳回是无效处置，等同未处置
3. **部分接受** — 划清边界：接受哪部分、反驳哪部分（反驳部分同样要证据）
4. **呈搭档裁决** — 涉及产品方向、资源投入、对外承诺；或作者与检视者一轮证据交换后仍对立

## 为什么不允许盲目遵从

检视者有 fresh eyes 但上下文浅，作者上下文全但有立场——对峙结构的价值在碰撞中产生。照单全收等于把检视者的误读原样引入，对抗审视就退化成了单人审阅。批判性接纳不是态度问题，是这个结构的必要组成。

## 证据交换规则

- 反驳在对话内直接发给原检视獭（它仍在场），不需要为它重建或重附材料
- **证据交换不消耗审视轮次**——轮次按全量/delta 审视计数（轮次记账与收敛判据见 review-loop.md）。一轮交换仍对立 → 呈搭档裁决，不许多轮拉扯
- 检视者评估反驳只看证据，不靠权威压人
- 裁决结果（谁拍的板、理由）必须留痕：PR 描述或方案文档决策史

## 与"发现问题立即修复"规则的关系

code-implementation 的"立即修复、不许问要不要修"管的是**作者自己发现的问题**（防拖延）。检视发现走本协议——反驳是合法处置，不算拖延；但没有证据的反驳不算处置。

## 非阻断发现的处置

非阻断发现不阻断本 PR 合入，但它仍是真实问题——必须有可验证的处置：

- **本 PR 修复**（diff 可见）
- **建 issue**（执行 `gh issue create`，在回应中贴 issue 链接，并写入 PR 描述 Discovered Issues 节）

口头"已记录"不构成处置。没有 issue 链接的"记录"等于静默丢失——这是 Let It Slide 反模式的变体（详见 `anti-patterns.md`）。回应允许极简（一行），但必须包含 issue 链接或修复说明。

**建 issue 的执行主体是作者**：检视者是只读角色，建不了 issue、改不了 PR 描述。凡处置为"建 issue"的非阻断发现，作者负责执行 `gh issue create` 并将链接写入 PR 描述——检视者在 delta 审视时核对落实情况（见 `review-loop.md`）。

## 方案审视路径的处置适配

上述处置选项面向代码 PR 审视。方案文档审视路径（见 `_shared/review-protocol.md` 方案审视协议）的适配：

- **阻断性发现**：本次修订（diff 可见）或呈搭档裁决
- **非阻断发现**：本次修订，或写入方案文档待办清单（标注具体段落定位，如章节号或标题）

方案文档没有 PR 描述 Discovered Issues 节——用文档内的"待办"或"决策史"节代替，必须可定位（段落编号或标题），不可口头"已记录"。delta 审视核对方式相应不同：代码 PR 路径核对 PR 描述 Discovered Issues 节；方案文档路径核对方案文档的待办/决策史节。
