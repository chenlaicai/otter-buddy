# 作者处置协议（对检视发现的回应）

检视发现不等于命令。作者对每条发现必须批判性评估后逐条处置——但**不作为不允许**：每条发现都必须经过决策树判断，要么改、要么用"改了反而变更差"的论证反驳回去，没有第三条路。本协议同时约束两端：作者按决策树 + 四分类回应，检视者按证据评估反驳。

## 核心问题：改了让系统变好、还是变更差？

每条发现，作者必须回答这一个核心问题。回答驱动处置：

```
改了让系统变好 → 必须改（两条子路径）
├─ 本 PR 修复（diff 可见）
└─ 本 PR 无法承载 → 建 issue（先过「建 issue 前置闸」判定关联度；强关联发现默认当场修，建 issue 须论证为什么**不能**现在修，理由命中合法清单 + 链接可见 + 登记 Discovered Issues 节——见下方「建 issue 前置闸」）

改了让系统变更差 → 反驳（必须附证据）
├─ 反驳成立（含事实错误/看错/误解）→ 双方达成一致，问题关闭
├─ 反驳不成立 → 仍是"更好"，必须改
└─ 一轮证据交换仍对立 → 呈搭档裁决

部分成立（同一条发现部分更好、部分更差）→ 走「部分接受」：
├─ 接受的更好部分 → 按上述"更好"分支处置（本 PR 修复 / 建 issue）
└─ 反驳的更差部分 → 按上述"更差"分支附证据反驳
```

## 分级与反驳门槛

检视者给发现分级为「严重」或「建议」。分级不改变处置决策树——两条路径都走决策树——但**反驳门槛不同**：

| 级别 | 默认处置 | 允许的反驳类型 |
|------|---------|---------------|
| **严重**（Critical） | 必须整改 | 仅"事实错误/看错/误解"类反驳；**不允许"改了变更差"反驳** |
| **建议**（Suggestion） | 必须走决策树 | 反驳和修复都是合法出口；"改了变更差"反驳需附证据 |

「严重」意味着检视者已判断"改了让系统变好"——作者若想反驳，必须证明检视者看错了（事实层面），不能在价值层面反对。

「建议」意味着检视者把"更好/更差"判断交给作者——作者必须显式给出判断并附理由。

## 四分类响应（决策树产物）

每条发现的回应写成以下之一——但**任何响应都必须先经过决策树判断**：

1. **接受并修复** — 判断为"更好"，说明修复方式（本 PR 修复 / 建 issue）
2. **反驳** — 判断为"更差"，必须附证据：`file:line`、测试运行结果、方案/设计文档原文。"我觉得没问题"、"过度设计"、"影响不大"、"建议不重要"这类无证据驳回是无效处置，等同未处置
3. **部分接受** — 划清边界：接受哪部分（更好→改）、反驳哪部分（更差→附证据）
4. **呈搭档裁决** — 涉及产品方向、资源投入、对外承诺；或作者与检视者一轮证据交换后仍对立

**未走决策树 = 未处置**。仅写"已修复"或"已记录"而不给出"更好/更差"判断，是 Inaction 反模式（详见 `anti-patterns.md`）。

## 不允许的处置（铁律）

- **静默忽略**（发现无任何处置）
- **口头"已记录"**（无 issue 链接、无 diff、无论证）
- **无理由不改**（"建议不重要"、"Low risk"、"Can optimize later"、"非阻断"作为可忽略暗示）
- **"建议"作为降级标签**（建议发现是必须走决策树的真实问题，不是可忽略项）

口头"已记录"不构成处置——这是 Let It Slide 反模式的变体（详见 `anti-patterns.md`）。

## 为什么不允许盲目遵从

检视者有 fresh eyes 但上下文浅，作者上下文全但有立场——对峙结构的价值在碰撞中产生。照单全收等于把检视者的误读原样引入，对抗审视就退化成了单人审阅。批判性接纳不是态度问题，是这个结构的必要组成。

## 证据交换规则

- 反驳在对话内直接发给原检视獭（它仍在场），不需要为它重建或重附材料
- **证据交换不消耗审视轮次**——轮次按全量/delta 审视计数（轮次记账与收敛判据见 review-loop.md）。一轮交换仍对立 → 呈搭档裁决，不许多轮拉扯
- 检视者评估反驳只看证据，不靠权威压人
- 裁决结果（谁拍的板、理由）必须留痕：PR 描述或方案文档决策史

## 与"发现问题立即修复"规则的关系

code-implementation 的"立即修复、不许问要不要修"管的是**作者自己发现的问题**（防拖延）。检视发现走本协议——反驳是合法处置，不算拖延；但没有证据、未走决策树的反驳不算处置。

## 建 issue 前置闸：强关联发现默认当场修（F20260909ugd8）

走「更好→本 PR 无法承载→建 issue」子路径前，必须先过关联度判定——**「建 issue」不是默认出口，是被举证责任锁住的例外**：

**第一步：判定关联度。** 发现属于以下情形之一即「与本 PR 语义强关联」：

- 守护本 PR 刚修复/刚引入的行为不回退（如本 PR 修复某语义，发现是「补一个防该语义回退的回归测试」）
- 澄清本 PR 刚改动的代码/口径（如「刚改的聚合逻辑缺注释，易被误读」）
- 修复本 PR 变更直接引入或暴露的问题

**第二步：按关联度分流。**

- **强关联** → 默认**当场修**（原 PR 未合入则修在原 PR，已合入则立即开补充 PR）。想走「建 issue」，举证责任在作者：必须论证为什么**不能**现在修，且理由只能来自下方的合法清单
- **弱关联**（与本 PR 语义无关，顺手发现）→ 「建 issue」是合法出口，按打标规范执行

**「本 PR 无法承载」的合法理由清单（穷尽）：**

1. **依赖未就绪**：修复依赖的外部条件（上游接口、数据、服务）尚不存在
2. **需要产品/方向决策**：修复方向涉及产品取舍，超出作者技术决策权（此时应走「呈搭档裁决」，issue 用于记录裁决结果）
3. **工作量确超阈值**：预估增量改动 >300 行 **或** 涉及 >3 个本 PR 未触碰的模块（达到此量级更可能是独立特性，应建 issue 走完整开发流程）

**不构成「无法承载」的伪理由（反面清单，源自 #860 教训）：**「需要搭测试 fixture」「涉及本 PR 未变更的文件」「建议级不阻断」——这些只描述工作量或位置，不证明承载不能。fixture 当天可搭，补充 PR 可触新文件，建议级仍是必须处置的真实问题。

**举证留痕**：选择建 issue 时，回应中必须显式写出关联度判断（强/弱 + 依据）与「无法承载」论证（命中合法清单哪一条），否则处置不成立。

## 建 issue 的执行主体

「更好→本 PR 无法承载」子路径（已过上方前置闸）需要建 issue。**执行主体是作者**：检视者是只读角色，建不了 issue、改不了 PR 描述。作者负责：

1. 按前置闸完成关联度判定 + 「无法承载」论证（命中合法清单条目）
2. 论证不成立 → 必须当场修复（原 PR 或补充 PR），不可走 issue 子路径
3. 论证成立 → 执行 `gh issue create`（按 SYSTEM.md R2 Issue 规范打标：type + priority，标题 `[模块] 摘要`），在回应中贴 issue 链接
4. 将 issue 写入 PR 描述 Discovered Issues 节

检视者在 delta 审视时核对：关联度判断是否给出 + 论证是否命中合法清单 + issue 链接是否存在 + Discovered Issues 是否登记（见 `review-loop.md`）。任一项缺失 = 处置未完成。

## 方案审视路径的处置适配

上述决策树与四分类同时面向代码 PR 审视和方案文档审视。方案文档路径（见 review-protocol skill 的方案审视协议）的载体差异：

| 处置 | 代码 PR 路径 | 方案文档路径 |
|------|------------|-------------|
| 更好→本 PR 修复 | PR diff | 本次修订 diff |
| 更好→本 PR 无法承载 | 建 issue，登记 PR 描述 Discovered Issues 节 | 写入方案文档待办清单（标注段落定位：章节号或标题） |
| 更差→反驳 | 对话内反驳 + 证据 | 对话内反驳 + 证据 |
| 呈搭档裁决 | PR 描述决策史留痕 | 方案文档决策史留痕 |

方案文档没有 PR 描述 Discovered Issues 节——用文档内的"待办"或"决策史"节代替，必须可定位（段落编号或标题），不可口头"已记录"。delta 审视核对方式相应不同：代码 PR 路径核对 PR 描述 Discovered Issues 节；方案文档路径核对方案文档的待办/决策史节。
