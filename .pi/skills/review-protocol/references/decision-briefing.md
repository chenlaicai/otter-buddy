# 决策简报

凡 yield to user 请求拍板时，发言必须附本简报——解决「搭档看到待决策清单、但不知道讨论了什么、方案全貌是什么」的信息不对等（盲签问题）。

## 简报骨架（六要素）

1. **一句话结论**：「我建议 X」——放最前，搭档赶时间只看这句也够
2. **背景 ≤3 行**：为什么走到这一步，触发点是什么
3. **选项对比**：候选 A/B/C 各一句话 + 关键取舍，**含被否掉的方案和否决理由**——搭档最容易盲区的正是"还有哪些路没走"
4. **獭间分歧如实呈现**：讨论中若有异议，双方观点都摆出来，不藏——大獭收敛结论不代表分歧消失
5. **推荐 + 理由 + 置信度 + 最大风险**
6. **锚点**：特性文档 ID / 讨论位置——想深挖顺藤摸，不想深挖信简报

## 默认通过模式（L2 中低风险项）

「我推荐 X，理由如下，**今天内无异议就开工**」——把「必须即时响应」改成「异步默许」，搭档忙时不用专门回，有异议随时喊停。

**适用判据**（三条须同时满足，拿不准就往高风险归——宁问不默）：

- 无不可逆后果（或逆回成本低）——❌ 反例：删除 memory 表某字段、force-push 受保护分支
- 不涉及对外承诺——❌ 反例：承诺搭档/外部在 X 时间前交付 Y
- 搭档否决成本低于约 1 天工时——✅ 正例：引入新依赖库 X；✅ 正例：采用方案 B 而非 A（两者均已验证可行）

高风险 / 不可逆项**不适用**默认通过——必须等明确拍板。

## 示例

反例（裸奔拍板，禁止）：

> 方案讨论完了，有 3 个问题需要你拍板：1… 2… 3…

正例：

> 建议用方案 B（理由：…）。讨论中 mimo 担心 X，我认为可控因为 Y。被否的 A 差在 Z。细节在 F20260909xxxx。无异议今天开工。

## 适用范围

- 代码 PR 终审（review-protocol A 步骤 5）
- 方案终审（review-protocol B / requirement-analysis 产出）
- 小改动 PR 终审（worktree-isolation 产出表）
- 任何其他 yield to user 请求决策的时刻（含审视僵局呈裁决）

## 分级边界

什么该问搭档、什么獭自己定，分级定义在 SYSTEM.md「决策分级」节。简报是 L2 层的强制输出物；L0/L1 层不出简报（L1 只留痕，可事后否决）。
