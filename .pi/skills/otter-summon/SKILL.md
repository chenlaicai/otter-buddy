# Otter Summon Protocol

大獭召唤小獭的决策框架和协作编排。

## 触发

**触发条件**：需要独立审视（异体执行）、≥2 个同 skill 任务并行、模拟多角色讨论、或单任务涉及多阶段产出（设计+实现+测试）时。

**排除**：搭档在讨论/闲聊/发散 → `companion`。单步可答或一次 read + speak + yield 能闭环 → 大獭直接做。搭档说"你来就行" → 尊重。

**硬规则**：搭档明确提到多个任务/多个 PR/并行处理时，必须召唤，不得自行判断为单步可答。搭档说「你来处理这几个 PR」= 隐含并行 + 审视意图，不是「只做 rebase」。

**输入**：
| 输入 | 必选 | 缺失时 |
|------|------|--------|
| 任务描述 | 是 | 停下来明确任务 |
| 任务类型 | 否 | 从描述推断，不确定则问搭档 |
| 背景信息 | 否 | 尽量收集，不阻塞 |

## 工作流

1. **判断是否召唤**：能自己做的自己做，真正需要帮手时才召唤。核心判断表：

   | 场景 | 动作 |
   |------|------|
   | 需要独立审视 | 召唤检视獭 |
   | ≥2 个同 skill 任务并行 | 召唤多只小獭 |
   | 需要角色讨论 | 召唤按立场命名的小獭 |
   | 单任务涉及多阶段产出（设计+实现+测试） | 召唤开发獭 |

   **判断示例**：

   | 场景 | 判断 |
   |------|------|
   | 4 个 daily-review issue 待处理，每个都要分析→设计→实现→提PR | 召唤 4 只开发獭并行，各处理 1 个 |
   | 3 个 PR 待审视 | 召唤 3 只检视獭并行，各审视 1 个 |
   | 1 个 bug fix（改 1-2 个文件） | 自己干，但完成后必须安排异体检视（见 code-implementation 步骤 10） |
   | 搭档问"这个函数在哪调用" | 自己干，不召唤 |
   | 设计一个新功能并实现（涉及 5+ 文件、多阶段产出） | 召唤 1 只开发獭独立闭环 |
   | 收到 N 个任务清单（N ≥ 2，每个都走相同 skill 流程） | 召唤 N 只小獭并行 |
   | 搭档说「处理 N 个 PR」 | 必须召唤 N 只小獭并行（含审视） |

   核心原则：**任务体越大、越并行，越该召唤**；单步可答的事自己做。

2. **写 systemPrompt**：身份信息不需要写（SMALL_OTTER.md 已覆盖），只写任务相关内容：

   ```
   你的任务：[一句话]
   背景信息：[相关上下文、已有结论、约束条件]
   特性文档：[路径，如存在]
   预期产出：[格式]
   完成标准：[什么算做完]
   ```

   **任务简报模板**（冲突预防 + 信任校准）：

   ```
   ## 任务简报

   ### 目标声明（冲突预防）
   - 做：<具体任务>
   - 不做：<明确排除的范围>
   - 边界：<与其他獭可能重叠的区域，以及谁拥有优先级>
   - 共享资源：<本任务可能修改的共享资源列表>

   ### 信任上下文（信任校准）
   - 信息来源：<本任务依赖的关键信息及其来源>
   - 可信度标注：<哪些信息需要核实，哪些可以直接使用>
   - 上游依赖：<哪些结论来自其他獭，需要如何验证>
   ```

   **硬规则（#307）**：如果任务涉及代码修改，systemPrompt 必须包含 R1 红线提醒：「小獭在 worktree 内工作，禁止修改主目录文件。需要提交代码时，先由大獭创建 worktree，你在 worktree 内工作。」

   如果存在特性文档（通过 `list_artifacts` 查找），在 systemPrompt 中附上路径。

3. **接住产出**：审视小獭产出质量 → 整合有价值的产出 → 发现遗漏决定自己补或再召唤 → 向搭档汇报。

> 约束：召唤要有明确任务，不要让小獭从零开始。小獭的产出是你的输入，不是最终交付物。

## 模型分配规则

对抗性角色召唤时 MUST 异模型（训练路径不同 → 盲区不同，这正是对抗价值的来源）：

| 角色对 | 规则 | 理由 |
|--------|------|------|
| 实现者 / 对抗审视者 | MUST 异模型 | 同模型审不出同模型的盲区 |
| 方案编写者 / 方案审视者 | MUST 异模型 | 同上 |
| 并行同 skill 獭 | SHOULD 模型混布 | 不必两两不同，但避免全部同模型 |
| 召唤者 / 被召唤者（一般任务） | 无约束 | 按任务特征选模型即可 |

**分配流程**：
1. 查对方模型（`get_active_participants` 返回的 modelAlias，或任务上下文）
2. `create_otter` 传不同的 `modelAlias`（按 strengths 匹配任务特征：代码/逻辑 → mimo，全局一致性 → kimi，中文语义 → glm）
3. 任务简报「信任上下文」段写明双方模型，提示审视者从优势维度切入

**降级**：单模型池 → 同模型 + B1-B4 checklist 补偿 + **审视报告标注「同模型审查，盲区风险未消除」**。降级绝不静默。

## 产出

本 skill 是编排层，后续动作由被召唤的小獭的 skill 决定。
