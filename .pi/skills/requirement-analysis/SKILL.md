# Requirement Analysis

把搭档的模糊意图变成清晰、可执行的技术方案。

## 触发

**触发条件**：搭档要求分析需求、设计方案、做技术方案时。

**排除**：已有方案要求写代码 → `code-implementation`。闲聊讨论 → `companion`。

**输入**：
| 输入 | 必选 | 缺失时 |
|------|------|--------|
| 需求描述 | 是 | 停下来问搭档 |
| 业务上下文 | 否 | 用 search_memory 补充 |
| 技术约束 | 否 | 从代码库推断，标注为假设 |

## 工作流

1. **解析需求**：将搭档的需求分为三类——明确（可执行）、模糊（必须问）、隐含（主动提出）。引用搭档原话作为意图锚，不意译。
2. **检索上下文**：`search_memory` 找历史决策，`search_terminology` 确认术语对齐，识别已有约束。
3. **分析现状**：读相关代码和文档，了解当前系统如何处理、涉及哪些模块、有哪些已知限制。
4. **评估风险**：影响哪些已有功能？是否有破坏性变更？哪些边界场景可能被忽略？
5. **产出方案**：按下方模板输出结构化技术方案。
6. **对抗审视**：
   - 召唤检视獭（`otter-summon`），systemPrompt 中附上方案全文或 worktree 内绝对路径。要求其先 read `adversarial-review` skill
   - 收到报告后校验合规性（含“本轮焦点”声明、发现分级、file:line 引用）——不合规打回重做
   - **对抗审视原则**：检视发现不等于命令。对每条发现必须批判性评估：检视者有 fresh eyes 但上下文浅，作者上下文全但有立场——碰撞才有价值；照单全收等于把检视者的误读原样引入，对抗审视退化为单人审阅；四类处置：接受并修订 / 反驳（必须附证据）/ 部分接受 / 呈搭档裁决；无证据的反驳（“我觉得没问题”、“过度设计”）等同未处置
   - 按 `adversarial-review/references/author-response-protocol.md` 逐条处置：接受并修订 / 反驳（必须附证据）/ 部分接受 / 呈搭档裁决
   - 按结论修订方案并复审。第 2 轮起是 delta 审视（附上轮发现清单 + 处置 + 修订 diff）
   - 收敛判据同代码审视。决策史回写文档——每道题的结论和理由留痕
   - 审视通过 → 方案定稿，可进入实现阶段

> **约束**：多种可行方案 → 列出权衡，推荐一种。搭档说"就这样" → 执行决策，不争论。每个设计选择记录正反两方面论据，不只记结论。背景必须引用搭档原话（意图锚），目标用编号（T1, T2, ...），非目标必须显式声明。

## 产出模板

```markdown
## 背景
引用搭档原话（意图锚）。

## 目标
T1: ...
T2: ...

## 非目标
明确排除的内容。

## 方案设计
涉及模块/文件、核心逻辑、数据模型变更、关键接口。

## 影响范围
影响哪些已有功能。

## 风险与约束

## 不兼容更新
[Incompatible] 标注破坏性变更。

## 设计取舍
| 取舍 | 决策 | 替代方案 | 理由 |

## 验证
验收标准和测试设计。

## 改动范围
| 文件 | 操作 | 说明 |
```

## 产出

| 产出 | 下一步 | 执行者 |
|------|--------|--------|
| 技术方案 | 对抗审视 | 检视獭 |
| 需求澄清问题 | 等待搭档回答 | 搭档 |
