# 参与者管理（Participant Management）

管理对话中的参与者生命周期。

## 核心原则

**先看人，再说话。** 开始处理任务前，先确认当前对话中有哪些参与者，避免重复工作或遗漏协作者。

## 查询参与者

使用 `get_active_participants` 获取当前对话中的所有活跃参与者。

### 必须查询的场景

1. **任务分配前**：需要确认有哪些 Otter 在场，决定是否需要邀请新成员
2. **发言石路由前**：决定 talkingStonePassedTo 时，先确认谁是活跃参与者
3. **协作判断时**：不确定当前对话的参与者构成时

## 邀请新成员

使用 `pass_talking_stone` 邀请指定 Otter 加入对话。

### 邀请规则

- 只邀请能为目标任务贡献价值的 Otter
- 邀请前先确认目标 Otter 尚未在场（用 `get_active_participants` 检查）
- 邀请后，在 `speak` 的 `talkingStonePassedTo` 中指定被邀请者的 ID

## 退场时机

当你的任务已完成且不需要继续参与时，应主动结束发言并将发言权交给需要继续工作的参与者。

### 不应退场的场景

- 你被明确要求等待后续指示
- 你的任务还未完成
- 你是对话中唯一的参与者且用户可能还有后续问题

## 发言石路由

发言石（talkingStonePassedTo）决定谁下一个发言。

### 路由原则

- **回答用户问题**：传用户 ID
- **需要其他 Otter 接手**：传目标 Otter ID
- **任务完成，等待用户**：传用户 ID
- **可以多个**：数组支持多个 ID，表示多个参与者都可以发言

## 上下文管理

使用 `get_context`、`set_context` 和 `delete_context` 管理你的工作状态（如当前阶段、进度标记）。

- **set_context**：记录你的工作进展，如 `"phase": "analysis"`, `"feature_id": "F20260720xxxx"`
- **get_context**：恢复之前的工作状态
- **delete_context**：清理不再需要的临时状态

上下文是**会话级临时状态**，不同于记忆系统（跨会话持久化）。会话结束后上下文会丢失。

## 禁止行为

- 不要在不清楚参与者构成的情况下盲目传递发言石
- 不要邀请与当前任务无关的 Otter
- 不要反复查询参与者（结果在会话内不会频繁变化）
