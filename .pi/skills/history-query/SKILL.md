# 对话历史查询

你拥有 4 个消息查询工具，用于回溯当前对话中已发生的发言。本规范定义何时以及如何使用这些工具。

## 核心原则

**精确回溯，不凭记忆猜测。** 当你需要引用或核实当前对话中说过的话，用工具查询原文，不要依赖自己的上下文窗口记忆。

## 与记忆召回的区别

| 维度 | 对话历史查询（本规范） | 记忆召回（memory-recall） |
|------|----------------------|--------------------------|
| 范围 | 当前对话的消息 | 跨会话的持久化记忆 |
| 数据源 | messages 表（原始消息） | memory_entries 表（索引/摘要） |
| 时效 | 实时，包含本轮对话 | 延迟，依赖索引周期 |
| 粒度 | 完整原文 | 渐进式披露（summary → full） |

**选择依据**：如果信息可能存在于当前对话中 → 先查历史；如果信息一定来自更早的会话 → 查记忆。两者可以串联使用。

## 必须查询的场景（硬规则）

遇到以下情况时，**必须先查询消息历史再回答**：

1. **引用回溯**：用户说"你刚才说的"、"刚才提到的"、"第几条消息"等指向当前对话中特定发言的表述
2. **决策核实**：用户问"我们刚才是不是决定了 X"，需要确认具体措辞和上下文
3. **列表/步骤回溯**：用户要求"把之前列的清单再发一遍"、"回到第 3 步"
4. **上下文断裂**：你发现自己不记得当前对话中某个具体细节（长对话中常见）
5. **分歧裁决**：用户和你对"之前说过什么"有争议，需要查原文

## 建议查询的场景（软规则）

以下场景建议查询，但不强制：

1. **连续讨论收尾**：长讨论结束时，查询关键节点消息以确保总结准确
2. **多轮修改追踪**：方案经过多轮修改后，查询原始版本以理解演变
3. **跨 Turn 续接**：新 Turn 开始时，如果 handoff summary 信息不足，查询上一个 Turn 的关键消息

## 查询协议

### 工具选择

根据场景选择合适的工具：

| 场景 | 工具 | 说明 |
|------|------|------|
| 找特定关键词的消息 | `search_messages` | FTS5 全文搜索，最常用 |
| 浏览最近的消息 | `list_messages` | 分页获取，默认按时间倒序 |
| 查看某条消息的完整内容 | `get_message` | 按 ID 精确获取 |
| 了解对话结构 | `get_turn_history` | 查看 Turn 链和参与者变化 |

### 渐进式查询

不要一次拉取大量消息。按需逐级深入：

1. **第一步**：`search_messages` 或 `list_messages(limit: 10)` — 快速定位
2. **第二步**：对目标消息调用 `get_message` 获取完整内容 — 仅在需要详情时
3. **结构查询**：`get_turn_history` — 仅在需要理解对话流程时

### 结果处理

- 查询无结果时，如实告知用户"在当前对话中未找到相关内容"，并建议查记忆系统
- 查询有结果时，引用原文关键部分，不要逐条罗列所有消息
- 消息中的工具调用和中间过程不需要向用户复述，提炼结论即可

## 禁止行为

- 不要对不涉及当前对话历史的问题调用消息查询（浪费 token）
- 不要每次回复前都查询历史（只在有明确信号时查询）
- 不要将 `list_messages` 的原始 JSON 结果直接展示给用户
- 不要用消息查询替代记忆召回——跨会话信息请用 `search_memory`
- 不要查询超过需要的消息数量（默认 limit 10 足够定位）
