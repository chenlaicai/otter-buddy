# 对话历史查询

你拥有 4 个消息查询工具，用于回溯当前对话中已发生的发言。本规范定义何时以及如何使用这些工具。

## 核心原则

**需要引用或核实时，精确回溯。** 当你需要确认当前对话中某句话的具体措辞、某个决定的上下文、或某个列表的完整内容时，用工具查询原文。对于你上下文窗口中已有且不需要精确引用的信息，直接回答即可。

## 与记忆召回的区别

| 维度 | 对话历史查询（本规范） | 记忆召回（memory-recall） |
|------|----------------------|--------------------------|
| 范围 | 当前对话的消息 | 跨会话的持久化记忆 |
| 数据源 | messages 表（原始消息） | memory_entries 表（索引/摘要） |
| 时效 | 实时，包含本轮对话 | 延迟，依赖索引周期 |
| 粒度 | 完整原文 | 渐进式披露（summary → full） |

**选择依据**：

- 用户说"**刚才**"、"**这轮**"、"**你刚才说的**" → 明确指向当前对话 → 用 history-query
- 用户说"**上次**"、"**记得当时**" → 明确指向更早会话 → 用 memory-recall
- 用户说"**之前**"、"**之前说的**" → 有歧义 → **先 history-query，返回 0 结果再 memory-recall**

两者可以串联使用：history-query 兜底 memory-recall，反之亦然。

## 必须查询的场景（硬规则）

遇到以下情况时，**必须先查询消息历史再回答**：

1. **引用回溯**：用户说"你刚才说的"、"刚才提到的"、"第几条消息"等指向当前对话中特定发言的表述
2. **决策核实**：用户问"我们刚才是不是决定了 X"，需要确认具体措辞和上下文
3. **列表/步骤回溯**：用户要求"把之前列的清单再发一遍"、"回到第 3 步"
4. **上下文断裂**：用户的提问涉及某个具体细节，你在上下文窗口中搜索后仍然找不到相关信息（常见于长对话、多轮讨论后）
5. **分歧裁决**：用户和你对"之前说过什么"有争议，需要查原文
6. **工具调用回溯**：用户问"你刚才调用了什么工具"、"刚才那个工具调用为什么失败了"
7. **元信息查询**：用户问"我们聊了多久"、"这条对话有多少消息"

## 建议查询的场景（软规则）

以下场景建议查询，但不强制：

1. **连续讨论收尾**：长讨论结束时，查询关键节点消息以确保总结准确
2. **多轮修改追踪**：方案经过多轮修改后，查询原始版本以理解演变
3. **Turn 切换续接**：新 Turn 开始时，如果 session summary 信息不足以理解上下文，查询上一个 Turn 的关键消息

## 查询协议

### 工具选择

根据场景选择合适的工具：

| 场景 | 工具 | 说明 |
|------|------|------|
| 找特定关键词的消息 | `search_messages` | FTS5 全文搜索，最常用 |
| 浏览最近的消息 | `list_messages` | 分页获取，默认按时间倒序 |
| 查看某条消息的完整内容 | `get_message` | 按 ID 精确获取 |
| 了解对话结构 | `get_turn_history` | 查看 Turn 链和参与者变化 |

**决策流程**：不确定用哪个工具时，按此顺序尝试：

```
有明确关键词？ ──是──→ search_messages(query, limit: 10)
  │ 否
需要浏览最近消息？ ──是──→ list_messages(limit: 10)
  │ 否
知道消息 ID？ ──是──→ get_message(messageId)
  │ 否
需要了解对话结构？ ──是──→ get_turn_history
```

### 参数指南

- `list_messages(limit, before)`：`before` 是游标分页参数，传入上一页最后一条消息的 ID 获取更早的消息。工具默认 limit 为 50，但本规范建议使用 10 以避免过度拉取。典型用法：先 `list_messages(limit: 10)` 获取第一页，再 `list_messages(limit: 10, before: <最后一条ID>)` 获取第二页
- `get_turn_history(includeMessages)`：默认 `false` 仅返回 Turn 元信息；传 `true` 会包含每个 Turn 下的消息列表，适用于需要理解 Turn 内部对话流时
- `search_messages(query, limit)`：`query` 支持中文关键词，底层使用 FTS5 trigram 分词。搜索无结果时可尝试拆分关键词重试
- `get_message(messageId)`：按 ID 精确获取单条消息的完整内容

### 渐进式查询

不要一次拉取大量消息。按需逐级深入：

1. **第一步**：`search_messages` 或 `list_messages(limit: 10)` — 快速定位
2. **第二步**：对目标消息调用 `get_message` 获取完整内容 — 仅在需要详情时
3. **结构查询**：`get_turn_history` — 用户问"刚才讨论了几个话题"、"对话流程是什么"、"参与者变化"，或需要定位 Turn 边界再用 `list_messages(before: ...)` 获取目标 Turn 消息时

### 结果处理

- 查询无结果时，正常回答用户。如果用户的问题明显指向更早会话，可建议"这可能在之前的会话中，需要我查一下记忆吗？"；否则不要主动提记忆系统
- 查询有结果时，引用原文关键句（用引号标注），附上简要解读。不要逐条罗列所有消息，也不要把原始 JSON 扔给用户
- 消息中的工具调用和中间过程不需要向用户复述，提炼结论即可
- 如果消息很长（超过 3 行），截取与用户问题相关的段落，用省略号标注省略部分

### 错误处理

- `search_messages` 返回 0 结果但用户确信说过 → 建议用户换关键词或提供更具体的上下文
- `get_message` 返回 "not found" → 如实告知用户该消息可能已被删除
- 工具调用超时或异常 → 告知用户查询失败，建议稍后重试，不要静默忽略

## 禁止行为

- **不要对已有答案的问题查询**：上下文窗口中已有相关信息且不需要精确引用时，直接回答。只有硬规则/软规则的明确信号出现时才查询
- **不要展示原始 JSON**：将查询结果转为自然语言引用（如"> 用户原话" + 1-2 句解读），不要把 `list_messages` 或 `search_messages` 的 JSON 原样输出
- **不要跨会话查询**：跨会话信息用 `search_memory`，消息查询工具只管当前对话
- **不要一次拉 100 条**：先 `limit: 10` 定位，需要更多时用 `before` 参数分页获取
