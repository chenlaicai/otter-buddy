## 背景

搭档原话（意图锚）：

> "我设计otter之初，就是让海獭成为伙伴，而不是严格的流程机器。"
> "研发流程只是海獭的一个研发场景的skill链路，并不代表海獭只做这件事。"
> "除了大獭是固定的，小獭都是视具体业务场景要求随时进场和退场参与对话。"

当前问题：海獭系统的 6 个 skill 全部是研发流程环节（需求分析、代码实现、审视、仓库安全），没有"伙伴"能力的 skill。SYSTEM.md 的"流程纪律"在实际效果上变成了"所有任务都必须走研发流程"，大獭的隐含定位变成了"调度者"而非"主要伙伴"。

本方案的目标是：**在不削弱现有流程纪律的前提下，补充"伙伴"那一面，让海獭回到"一起干活的搭档"这个原点。**

## 目标

- T1：SYSTEM.md 核心原则补充"搭档优先"，明确流程是手段不是目的
- T2：新增 `companion` skill，覆盖非结构化协作场景
- T3：调整 `otter-summon` skill，明确"大獭是主要伙伴，小獭是请来的帮手"
- T4：现有 skill 的"完成标准"增加弹性层，区分"流程完成"和"搭档满意"
- T5：`core-workflow` 扩展为伙伴也能用的基础能力，不只是"查询和记录"

## 非目标

- 不改变现有研发流程的严谨性（审视、异体执行、收敛判据保持不变）
- 不改变小獭的 dissolve 机制（任务制小獭用完即走是合理的）
- 不引入新的底层架构变更（本方案只改 .pi/ 下的 skill 和 system 文件）
- 不做"Agent 持久化记忆"的底层改造（那是另一个方案的范畴）

## 方案设计

### 一、SYSTEM.md 核心原则修订

在现有三条原则之后，新增第四条：

```
**搭档优先**：海獭是搭档的伙伴。搭档需要严谨时走流程，搭档需要灵活时放下流程。
流程是服务搭档的手段，不是反过来。判断"该不该走流程"本身也是伙伴能力的一部分。

具体表现：
- 搭档的输入不匹配任何场景 skill 时，直接响应，不追问"你要走哪个流程"
- 搭档在进行非结构化讨论时，不主动拉入流程
- 搭档说"行了"就是完成，不需要走完所有步骤
- 但在搭档做出需要严谨处理的结论时（"那就这么定了"、"提交吧"），
  主动问：要不要记录下来 / 出个方案 / 走一遍审视？
```

同时修订"流程纪律"的表述，从：

> "凡有既定 skill 覆盖的工作类型，先 read 对应 skill 再动手"

改为：

> "凡有既定 skill 覆盖的工作类型，先 read 对应 skill 再动手。但不是所有任务都有对应的 skill——不匹配任何 skill 的任务，按'搭档优先'原则直接响应。"

### 二、新增 companion skill（伙伴模式）

新增 `.pi/skills/companion/SKILL.md`，定位为**非结构化协作的默认模式**。

核心设计：

- **触发条件**：搭档的输入不匹配任何其他 skill 的触发短语
- **行为**：直接响应，不走流程，基于上下文判断搭档需要什么
- **完成标准**：搭档觉得搞定了（"行了"、"我知道了"、"就这样"）
- **边界感知**：讨论中出现需要严谨处理的结论时，主动提醒搭档

这个 skill 的特殊之处：它不需要搭档显式触发，它是**默认行为**——当没有其他 skill 匹配时，海獭就是伙伴模式。

### 三、调整 otter-summon skill

当前 otter-summon 的隐含语境是"大獭调度小獭"。需要调整为"大獭是主要伙伴，需要帮手时召唤小獭"。

具体修改：

- 在"何时召唤"之前增加"何时不召唤"的判断：
  - 搭档在讨论、理思路、发散 → 不召唤，大獭直接做
  - 搭档的需求明确但简单 → 不召唤，大獭直接做
  - 只有真正需要独立视角/并行工作/异体审视时才召唤
- 调整"召唤原则"的第一条：从"召唤要有明确任务"改为"先判断是否需要召唤"

### 四、现有 skill 完成标准弹性化

在每个现有 skill 的"后续动作声明"中，增加一条通用规则：

```
弹性完成规则：当搭档明确表示满意（"行了"、"够了"、"就这样"）时，
即使流程步骤未走完，也可以终止。但必须在终止前确认搭档是否了解
未走完的步骤可能带来的风险（如：方案未经审视、PR 未经检视）。
搭档知情后仍选择跳过 → 记录决策后放行。
```

这不是新规则——SYSTEM.md 已经有"搭档明确说'跳过'时，记录决策后放行"。这次是把它从 SYSTEM.md 的通用原则，落到每个 skill 的行为层面。

### 五、core-workflow 扩展

当前 core-workflow 的定位是"查询和记录"。扩展为伙伴也能用的基础能力：

- 增加"联想"能力：搭档提到某个话题时，主动关联之前的讨论、相关决策、已知约束
- 增加"建议"能力：发现搭档可能遗漏的风险点时，主动提出（不是等搭档问）
- 这些能力不需要新的 skill，只需要在 core-workflow 的描述中明确"这些是大獭的默认行为，不只是查询工具"

## 影响范围

| 受影响的文件 | 影响类型 |
|-------------|---------|
| `.pi/SYSTEM.md` | 核心原则修订 |
| `.pi/skills/companion/SKILL.md` | 新增 |
| `.pi/skills/otter-summon/SKILL.md` | 调整"何时召唤"判断 |
| `.pi/skills/core-workflow/SKILL.md` | 扩展伙伴能力描述 |
| `.pi/skills/requirement-analysis/SKILL.md` | 增加弹性完成规则 |
| `.pi/skills/code-implementation/SKILL.md` | 增加弹性完成规则 |
| `.pi/skills/adversarial-review/SKILL.md` | 增加弹性完成规则（仅限方案审视，代码审视不弹性） |
| `.pi/skills/repo-safety/SKILL.md` | 增加弹性完成规则（仅限小改动） |

## 风险与约束

| 风险 | 缓解措施 |
|------|---------|
| "弹性完成"被滥用，该走流程的不走了 | 弹性只适用于搭档明确表态的场景；涉及代码变更、生产发布的流程红线不弹性 |
| companion skill 太模糊，海獭不知道怎么做 | companion 的核心是"直接响应"，不是"做某件特定的事"——它就是正常对话 |
| 大獭不召唤小獭，自己硬做 | otter-summon 的"何时不召唤"有明确判断标准，不是"永远不召唤" |
| 流程纪律被削弱 | 方案明确"不改变现有研发流程的严谨性"，弹性只在搭档主动要求时生效 |

## 不兼容更新

行为语义调整（非破坏性）：
- **流程纪律修订**：原为“流程未走完，任务不算完成”（无条件），现新增例外“不匹配任何 skill 的任务，按搭档优先原则直接响应”。不影响已有 skill 的执行行为，只影响无 skill 覆盖的场景
- **新增 companion 模式**：无 skill 匹配时默认进入伙伴模式。这是新增行为，不改变已有行为

## 设计取舍

| 取舍 | 决策 | 替代方案 | 理由 |
|------|------|---------|------|
| companion 是独立 skill 还是 SYSTEM.md 的一部分 | 独立 skill | 写在 SYSTEM.md 里 | skill 有触发短语、输入契约、后续动作声明的标准格式，便于维护和引用 |
| 弹性完成是全局规则还是 per-skill 规则 | per-skill 落地 | 只在 SYSTEM.md 写一次 | 不同 skill 的弹性边界不同（代码审视不能弹性，方案审视可以） |
| 大獭的角色定位调整 | 在 otter-summon 中调整 | 在 SYSTEM.md 中写 | otter-summon 是"何时召唤"的决策点，在这里调整最自然 |
| 是否需要新的"伙伴能力"skill | 不需要，companion 覆盖 | 拆成多个小 skill | 伙伴能力是弥散的，不适合拆成独立流程 |

## 验证

### 验收标准

- V1：SYSTEM.md 包含"搭档优先"原则，且"流程纪律"表述已修订
- V2：companion skill 文件存在，且描述清晰（触发条件、行为、完成标准、边界感知）
- V3：otter-summon 包含"何时不召唤"的判断逻辑
- V4：现有研发 skill 包含弹性完成规则
- V5：core-workflow 包含伙伴能力描述
- V6：所有修改不改变现有研发流程的红线和严谨性

### 验证方式

- 人工审读每个修改后的文件，确认语义一致
- 用典型场景测试：
  - "帮我看看这个需求" → 应该走 requirement-analysis（不变）
  - "你觉得这个想法怎么样" → 应该走 companion（新增）
  - "帮我理一下思路" → 应该走 companion（新增）
  - "行了我知道了" → 应该终止当前流程（新增弹性）
