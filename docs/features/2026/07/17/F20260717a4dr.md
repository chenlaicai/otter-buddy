## 概述

搭建一个系统提示词模块，支持两层继承架构：
1. **平台级 System Prompt**：所有 AI 必须遵从的原则/铁律（all-Otter 配置）
2. **Otter 级 System Prompt**：per-Otter 可选覆盖，与平台 prompt 叠加
3. **System Reminder**：运行时注入的系统提醒
4. **User Prompt**：用户消息

## 设计方案

### 核心概念

#### 1. 平台级 System Prompt（原则/铁律）

所有 AI 必须遵从的系统提示词。特点：
- all-Otter 配置，对所有 Otter 实例生效
- 存储在数据库表中（独立于 Otter 配置）
- 注入到 Pi Agent 的 system message 最前面
- 不可违背，Otter 级 prompt 只能补充不能覆盖

#### 2. Otter 级 System Prompt（可选覆盖）

Per-Otter 的自定义提示词。特点：
- 用户在创建/编辑 Otter 时可选设置
- 存储在 PiHarnessFactory 内存 Map 中
- 与平台 prompt 叠加（concatenation），不是覆盖
- 可为空（此时只使用平台 prompt）

#### 3. System Reminder（系统提醒）

运行时注入的系统提醒，类似 Claude Code 的 `<system-reminder>`。特点：
- 在对话过程中动态注入
- 用于提醒 agent 特定上下文
- 存储在 Otter 配置中（per-Otter）

#### 4. User Prompt（用户提示）

用户发送的消息。特点：
- 用户直接输入
- 是对话的主要内容
- 与 system prompt 和 system reminder 分开

#### 构建流程（两层继承）

```typescript
// system-prompt-builder.ts（修改）

export function buildSystemPrompt(
  platformPrompt: string,
  otterConfig: OtterPromptConfig,
  dynamicContext?: DynamicContext,
): (ctx: HarnessContext) => string {
  return (_ctx: HarnessContext) => {
    const parts: string[] = [];

    // 1. 平台级 prompt（原则/铁律，不可违背）
    if (platformPrompt) {
      parts.push(platformPrompt);
    }

    // 2. Otter 级 prompt（可选叠加）
    if (otterConfig.systemPrompt) {
      parts.push(otterConfig.systemPrompt);
    }

    // 3. System reminders
    if (otterConfig.reminders && otterConfig.reminders.length > 0) {
      const sortedReminders = [...otterConfig.reminders]
        .sort((a, b) => getPriorityWeight(a.priority) - getPriorityWeight(b.priority));

      for (const reminder of sortedReminders) {
        parts.push(`<system-reminder>\n${reminder.content}\n</system-reminder>`);
      }
    }

    // 4. 动态上下文（会话摘要 + 记忆检索）
    if (dynamicContext?.sessionSummary) {
      parts.push(`## 会话摘要\n${dynamicContext.sessionSummary}`);
    }

    if (dynamicContext?.memoryRetrieval) {
      parts.push(`## 记忆检索结果\n${dynamicContext.memoryRetrieval}`);
    }

    return parts.join("\n\n");
  };
}

/** 优先级权重 */
function getPriorityWeight(priority?: 'low' | 'medium' | 'high'): number {
  switch (priority) {
    case 'high': return 0;
    case 'medium': return 1;
    case 'low': return 2;
    default: return 1;
  }
}
```

### 集成点

#### 1. 系统启动流程

```
系统启动
  -> PiHarnessFactory 初始化
  -> loadPlatformPrompt() 从数据库加载平台 prompt
  -> 所有后续 Otter invoke 都会包含平台 prompt
```

#### 2. 平台 Prompt 更新流程

```
管理员更新平台 prompt
  -> PUT /api/platform-prompt
  -> PlatformPromptController.update()
  -> PiHarnessFactory.updatePlatformPrompt()
  -> 更新数据库 + 内存缓存
  -> 所有后续 Otter invoke 使用新 prompt
```

#### 3. Otter 创建流程

```
用户/LLM 传入 systemPrompt（可选）
  -> OtterController.create()
  -> CreateOtter.execute()
  -> AgentGateway.create(otterId, { systemPrompt })
  -> PiHarnessFactory.create()
  -> 存储 OtterPromptConfig
```

#### 4. 对话流程

```
用户发消息
  -> AgentInvoker 构建 DynamicContext
  -> PiHarnessFactory.invoke(otterId, message, { dynamicContext })
  -> buildSystemPrompt(platformPrompt, otterConfig, dynamicContext) 生成函数
  -> new AgentHarness({ systemPrompt: 函数 })
  -> 函数在每轮 LLM 调用前执行
  -> 最终 prompt = 平台 prompt + Otter prompt + reminders + 动态上下文
```

## 设计决策

### 决策 1：两层继承架构（平台 + Otter）

**决策**：采用平台级 all-Otter prompt + per-Otter 可选叠加的两层架构。

**正面论点**：
- 符合用户确认的"all-otter 配置"和"原则/铁律"需求
- 平台 prompt 对所有 Otter 生效，统一行为准则
- Otter prompt 提供灵活性，允许 per-Otter 定制

**反面论点**：
- 增加了架构复杂度（两层存储、两层构建）
- 需要额外的平台 prompt 管理 API
- 两层 prompt 叠加可能导致 prompt 过长

**理由**：用户明确要求"all-otter 配置"和"原则/铁律"，这是核心需求，必须支持。

### 决策 2：叠加语义（非覆盖）

**决策**：Otter prompt 与平台 prompt 叠加（concatenation），不是覆盖（override）。

**正面论点**：
- 平台 prompt（原则/铁律）始终存在，不可违背
- Otter prompt 是补充，不是替换
- 语义清晰：最终 prompt = 平台 + Otter

**反面论点**：
- 如果 Otter 需要完全不同的 prompt，叠加可能不合适
- prompt 总长度可能超过限制

**理由**：用户说"原则/铁律"，暗示平台 prompt 应始终生效。如果需要覆盖语义，可以在 Otter prompt 中明确说明"忽略平台 prompt 的 X 部分"。

### 决策 3：平台 Prompt 存储在数据库

**决策**：平台 prompt 存储在数据库表中，而非配置文件。

**正面论点**：
- 便于版本管理（审计追踪）
- 支持多实例部署（配置文件不共享）
- 与现有 Otter 存储一致

**反面论点**：
- 增加数据库依赖
- 需要额外的数据库表

**理由**：系统已有数据库基础设施，使用数据库存储更一致且支持多实例部署。

### 决策 4：移除变量替换和条件过滤

**决策**：移除 `variables` 和 `condition` 字段。

**正面论点**：
- 用户未要求变量替换（无 UA 来源）
- `condition` 函数类型不可序列化，与 API/数据流不兼容
- 简化设计，减少复杂度

**反面论点**：
- 变量替换可能在未来有用
- 条件过滤提供了灵活性

**理由**：遵循"未来扩展不是过度设计的借口"原则。变量替换无用户需求，condition 不可序列化。如未来需要，可作为独立 feature 添加。
