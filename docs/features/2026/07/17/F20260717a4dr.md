## 设计方案

### 核心概念

**平台 System Prompt**：全局配置的一段文本，注入到所有 Pi Agent 的 system message 最前面。特点：
- all-Otter 配置，对所有 Otter 实例生效
- 存储在现有 `settings` 键值表中（key: `platform_system_prompt`）
- 启动时加载到 `PiHarnessFactory` 内存
- invoke 时 prepend 到 system prompt 前面
- 与 per-Otter 的 `systemPrompt`（角色定义等）叠加，不冲突

### 架构变更

#### 1. 存储层：复用 settings 表

不需要新建表。复用现有 `settings` 键值对表，key = `platform_system_prompt`。

#### 2. PiHarnessFactory：持有平台 prompt + invoke 时 prepend

```
构造函数新增参数：
  settingsRepo: SettingsRepository  — 用于从 DB 加载平台 prompt

新增字段：
  private platformPrompt: string = ''

新增方法：
  loadPlatformPrompt(): Promise<void>  — 从 settingsRepo.get("platform_system_prompt") 加载
    key 不存在时（首次启动）视为空字符串，不报错
  setPlatformPrompt(prompt: string): void  — 更新时同步内存缓存

修改 invoke():
  传入 buildSystemPrompt(platformPrompt, otterPrompt, dynamicContext)
```

#### 3. buildSystemPrompt：签名变更

```
原签名：buildSystemPrompt(staticPrompt, dynamicContext)
新签名：buildSystemPrompt(platformPrompt, staticPrompt, dynamicContext)

构建顺序：
  1. platformPrompt（在最前面，全局原则/铁律）
  2. staticPrompt（per-Otter 角色定义等）
  3. 动态上下文（会话摘要、记忆检索）
```

#### 4. API 层：新增平台 prompt 专用端点

```
GET  /api/platform-prompt  — 获取平台 prompt
PUT  /api/platform-prompt  — 更新平台 prompt（body: { systemPrompt: string }）
```

边界条件：
- PUT body.systemPrompt 为空字符串 → 合法操作，清空平台 prompt
- PUT body.systemPrompt 长度超过 100KB → 400 拒绝
- GET 首次启动（key 不存在）→ 返回空字符串

新增 `PlatformPromptController`，依赖 `SettingsRepository` + `PiHarnessFactory`。

#### 5. 启动流程集成

```
main.ts:
  agentGateway = initAgentCore({ ..., settingsRepo: repos.settings })  ← 构造函数注入 settingsRepo
  agentGateway.loadPlatformPrompt()  ← 启动时加载平台 prompt
  ...后续流程不变
```

#### 6. API 路由注册

```
router.ts:
  新增 registerPlatformPromptRoutes(app, ctrl)
```

### 设计决策

#### 决策 1：复用 settings 表 vs 新建表

**决策**：复用 settings 表。

**理由**：平台 prompt 是一个全局单值配置，与 provider/model 等 settings 性质相同。新建表增加不必要的复杂度。

#### 决策 2：专用 API 端点 vs 复用 /api/settings

**决策**：新增专用 `/api/platform-prompt` 端点。

**理由**：平台 prompt 是独立的配置域，语义清晰。复用 /api/settings 会导致 settings API 职责膨胀，且 prompt 内容可能较长，混在 settings 响应中不合适。

#### 决策 3：PiHarnessFactory 持有 vs AgentInvoker 层注入

**决策**：在 PiHarnessFactory 中 prepend。

**理由**：PiHarnessFactory 是构建 system prompt 的唯一出口，在此处 prepend 最自然。如果放在 AgentInvoker 层，需要修改 invoke 接口签名或 dynamicContext 结构，改动更大。
