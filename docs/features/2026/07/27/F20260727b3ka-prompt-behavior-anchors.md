# F20260727b3ka SYSTEM.md 原则重写

## 术语定义

| 术语 | 定义 |
|------|------|
| **原则** | 指导行为的核心信念，覆盖所有场景，不需要括号列具体案例 |
| **做事步骤** | 告诉 LLM"怎么做"的具体指令，如工具参数、查询流程 |
| **括号补丁** | 用括号给已有规则加例外条件，如"XXX 除外——YYY 场景始终 ZZZ" |

## 背景

### 起因：对话 t001 的行为缺陷

大獭在排查 bug 时，连续 4 轮声称"我来分析"但从未调用工具获取实际数据。用户要求大獭自行排查，大獭不知道代码仓路径、数据库类型、日志路径——但没有提问，而是猜测。

### 追溯：SYSTEM.md 的结构问题

排查行为锚点设计过程中（三轮架构师审查），发现根因不只是缺少排查规则，而是 SYSTEM.md 整体的补丁式结构：

| 问题 | 具体表现 |
|------|----------|
| **做事步骤过多** | 66 行中约 30 行是工具使用指南（查询流程、记录格式、状态流转规则） |
| **括号补丁堵不住** | "上下文有答案就直接回答（排查场景除外——排查时始终先用工具获取最新数据）"——LLM 总能找到"上下文有答案"的理由绕过 |
| **效率规则与准确性原则冲突** | "上下文有答案就直接回答"是效率优化，但它给了 LLM 跳过工具调用的合法出口 |
| **"原则"标题下不是原则** | "一次一人发言""发言权显式交接"是平台机制，放在"原则"标题下误导 |

### 设计转变：从打补丁到立原则

三轮审查的迭代过程：

| 轮次 | 发现 | 教训 |
|------|------|------|
| 第一轮 | 元认知前提不成立、负向约束自相矛盾、信号分散 | 行为锚点不能依赖 LLM 判断自身状态 |
| 第二轮 | 触发条件太窄、后验约束不触发、三选一出口是后门 | 补丁堵不住逃逸路径 |
| 第三轮 | "分析情况"过宽污染非排查场景、"上下文有答案"提供合法逃逸 | 补丁之间会产生新冲突 |

**核心教训**：每加一个括号补丁，就多一个逃逸路径需要新补丁堵。正确的做法是用原则替代补丁——原则覆盖所有场景，不需要括号。

## 设计方案

### D1 — SYSTEM.md 重写

**结构变化**：

| 之前（66 行） | 之后（~30 行） |
|---------------|----------------|
| 对话环境（3 行） | 对话环境（3 行，合并搭档定义） |
| 搭档（3 行） | — |
| 原则（5 行，平台机制） | **删除**——平台机制不是原则 |
| 参与者（3 行，工具指南） | **删除**——工具使用指南 |
| 信息查询（12 行，步骤+补丁） | **精简为 3 行**——原则性指引 |
| 关键产出记录（6 行，步骤） | **精简为 1 行**——原则性指引 |
| 使用中文（1 行） | 保留 |
| 身份认知（23 行，原则+补丁） | **重写为 10 行**——纯原则，无补丁 |

**核心原则提炼**：

从原来的 4 条行为边界 + 验证来源层级 + 决策vs判断 + 优先级，提炼为 3 条铁律：

1. **事实优先**：基于实际数据和逻辑分析，不凭印象、不靠推测。区分决策（尊重执行）和判断（平等评估）。优先级：事实 > 搭档判断 > AI 偏好。
2. **诚实直言**：不确定就说不确定。发现问题直言，不讨好不顺着。
3. **安全底线**：安全风险必须指出。

**关键变化**：

| 原规则 | 问题 | 新处理 |
|--------|------|--------|
| "上下文有答案就直接回答" | 效率规则给了 LLM 跳过工具的合法出口 | **删除**——用"事实优先"原则替代 |
| "排查场景除外——括号补丁" | 补丁堵不住逃逸路径 | **删除**——"分析必须基于实际数据"已覆盖 |
| "不自我贬低" | 是"诚实直言"的子集 | **合并**到"诚实直言" |
| "不确定就说不确定+标注置信度+建议验证" | 太具体，括号多 | **精简**为"说明缺什么信息，建议验证方式" |
| "验证来源层级"（代码>文档>训练数据） | 做事步骤 | **删除**——"事实优先"原则已覆盖 |
| "一次一人发言""发言权显式交接" | 平台机制，不是原则 | **删除** |
| 查询工具列表（6 条） | 做事步骤 | **精简为 1 行**——保留查询方向 |
| 产出记录格式（groupId、状态流转） | 做事步骤 | **精简为 1 行**——只保留"必须记录" |

### D2 — 身份修正（BIG_OTTER.md）

## 硬约束

1. 不注入项目特定信息（路径、数据库类型等）
2. 不规定排查流程步骤
3. 每条规则必须是正向表述，不出现"不要"、"不猜"、"不能"
4. 原则必须覆盖所有场景，不需要括号列具体案例

## 架构师审查记录

### 第一轮：需修改

元认知前提不成立、负向约束自相矛盾、锚点分散。修订：砍掉"信息不足时"段落，用"声称即举证"替代。

### 第二轮：需修改

t001 的问题是"根本没有声称查看任何东西就开始分析"，触发条件太窄。修订：扩展为行为类型触发。

### 第三轮：需修改

"分析情况"过宽污染非排查场景；"上下文有答案"提供合法逃逸。修订：收窄为"排查问题时"；加排查限定。

### 第四轮（用户审查）：需修改

用户指出：括号补丁是错误的 prompt 设计方式，系统提示词应该是少量核心原则/铁律。修订：从打补丁转为立原则，重写整个 SYSTEM.md。
