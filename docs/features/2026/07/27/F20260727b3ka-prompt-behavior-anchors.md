# F20260727b3ka Prompt 行为锚点优化

## 术语定义

| 术语 | 定义 |
|------|------|
| **行为锚点** | prompt 中的一个具体行为模式，让 LLM 在特定情境下匹配到一个正向行动 |
| **语言惯性** | LLM 一旦开始生成某个方向的文本，倾向于把话说完而不是中途转向工具调用 |
| **元认知** | LLM 识别自身认知状态的能力（如"我知道自己不知道什么"）——这是 LLM 最弱的能力 |
| **概率偏移** | prompt 规则的实际效果——提高某个行为的概率，而非保证该行为一定发生 |

## 背景

### 问题现象

对话 t001 的 bug 排查阶段（Turn 22-33）暴露了大獭的严重行为缺陷：

1. **猜测而非提问**：大獭不知道代码仓路径、数据库类型、日志路径，但没有向搭档提问，而是自己猜测
2. **表演排查**：连续 4 轮声称"我来分析"、"我找到了线索"，但从未调用 `read`/`bash` 工具获取实际数据
3. **身份误读**："不推不拖"被解读为"不问就干"，与"不确定就说不确定"产生矛盾

### 根因分析（LLM 本质视角）

LLM 的核心行为是 token 预测。这意味着：

- **文字是舒适区**：生成"我来分析一下"之后，LLM 会继续生成分析文本，而不是中断去调用工具。工具调用需要额外的"跳转"，比继续生成文本的阻力更大。
- **负向约束失效**："不要猜测"要求 LLM 先识别"什么是猜测"再避免，这比直接匹配一个正向行为难得多。
- **元认知不可靠**：LLM 无法可靠地识别"我信息不足"或"我在推测"这类状态。t001 中大獭**以为自己在做合理分析**，不是"知道自己在推测但选择继续"。

### 不做什么

- **不绑定特定项目**：不注入代码仓路径、数据库路径等项目特定信息（Otter 应适配任意项目）
- **不规定排查流程**：不写"先查日志→再查数据库→再分析"的固定步骤（不同问题需要不同路径，硬流程会用步骤代替判断力）
- **不依赖元认知**：不用"信息不足时"、"推测"、"拿不准时"等需要 LLM 判断自身状态的触发条件
- **不用负向约束**：不出现"不要"、"不猜"、"不能"等需要 LLM 理解再避免的指令

## 目标

### T1 — 排查行为锚点

在 SYSTEM.md 的信息查询段落开头植入排查行为锚点，让大獭在排查问题时必须先通过工具获取数据。同时限定已有"上下文有答案直接回答"规则在排查场景不适用。

### T2 — 身份修正

修改 BIG_OTTER.md 中"不推不拖"的表述，区分"不推卸任务"和"不确认就行动"。

## 设计方案

### D1 — 排查行为锚点（SYSTEM.md）

**改动 1**：在 `## 信息查询` 段落开头（第 21 行之前）插入：

```markdown
排查问题时：先用工具读取相关文件/数据，再基于读取内容分析。
```

**改动 2**：修改第 28 行，从：

```markdown
- 上下文中已有答案且不需精确引用时，直接回答，不要重复查询
```

改为：

```markdown
- 上下文中已有答案且不需精确引用时，直接回答，不要重复查询（排查场景除外——排查时始终先用工具获取最新数据）
```

**设计原理**：

**为什么只保留"排查问题时"，去掉"分析情况"？**

第三轮审查指出"分析情况"是一个极度宽泛的触发条件。"你觉得方案 A 和 B 哪个好"、"帮我总结对话"、"这个正则什么意思"都包含"分析"，但这些场景不需要强制读取工具。"排查问题"则隐含了"需要获取新信息"的限定——排查意味着已有信息不足以定位问题。

**为什么去掉示例？**

第三轮审查指出示例"排查卡顿 → read 日志文件 → 基于日志内容定位原因"会把排查和读日志绑定。LLM 会把示例中的具体行为当作默认路径，导致在所有排查场景都去读日志，即使问题可能在代码、配置或其他地方。

**为什么要在已有规则后加排查限定？**

SYSTEM.md 第 28 行的"上下文中已有答案且不需精确引用时，直接回答"是一条效率规则——避免重复查询。但在排查场景中，这条规则会成为逃逸路径：LLM 可以认为对话历史中的信息就是"上下文中已有的答案"，然后直接生成分析文本，绕过排查锚点。

t001 Turn 24 正是这个模式：大獭认为 turn history 中的错误信息就是"答案"，直接生成了推测性分析。

加限定"排查场景除外——排查时始终先用工具获取最新数据"后，排查场景中"直接回答"的逃逸路径被关闭。

**关于负向约束**：

限定语"排查场景除外"在形式上是一个例外条件，不是负向约束。它不禁止某个行为，而是明确一个场景的优先级。"始终先用工具获取最新数据"是正向行为指令。

**方案局限性**：

prompt 规则的效果是概率偏移，不是行为保证。LLM 在以下情况下仍可能跳过工具调用：
- "我来分析一下"的语言惯性极强时（连续多轮分析会累积惯性）
- system prompt 距离当前 token 位置较远，attention 衰减导致信号被淹没
- 用户消息中的措辞更匹配"理解/分析"而非"工具调用"

这些是 LLM 架构的本质限制，prompt 只能提高概率，不能消除。实际效果需要在对话中验证，根据覆盖率迭代。

### D2 — 身份修正（BIG_OTTER.md）

**位置**：`## 你是谁` 段落中

**当前文本**：

> 简单的事你直接上手做，不推不拖

**修改为**：

> 简单的事你直接上手做；拿不准的事先跟搭档确认，确认了就执行

**为什么这样改**：

- 用分号拆成两个独立行为模式，消除"不推不拖"的捆绑歧义
- "拿不准的事先跟搭档确认"——正向指令，建立"不确定 → 确认"的模式
- 去掉"不拖"——这个词在原句中强化了"赶紧行动"的暗示，与"先确认"矛盾
- 整句形成决策树：简单 → 直接做；拿不准 → 确认 → 执行

**关于与 SYSTEM.md "不确定就说不确定"的关系**：

SYSTEM.md 的"不确定就说不确定"是**认知层面**的——承认自己不确定。D2 的"拿不准的事先跟搭档确认"是**行为层面**的——不确定时采取什么行动。两者是递进关系：先承认不确定（SYSTEM.md），再主动确认（BIG_OTTER.md）。

## 硬约束

1. 不注入项目特定信息（路径、数据库类型等）
2. 不规定排查流程步骤
3. 每条改动必须是正向行为锚点，不出现"不要"、"不猜"、"不能"
4. 改动总量控制在 5 行以内——prompt 越短，信号越强
5. 不依赖元认知——锚点触发条件必须是 LLM 可直接匹配的行为模式，不是状态判断

## 架构师审查记录

### 第一轮审查：需修改

**三个致命问题**：
1. 元认知前提不成立——原 D1（"信息不足时"段落）假设 LLM 能识别"信息不足"状态
2. 自己违反正向锚点原则——"不猜"是负向约束，"要标注"也是负向约束变体
3. 锚点重叠冲突 + 信号分散——三个锚点分散在两个文件中

**修订**：砍掉原 D1，用"声称即举证"替代；核心锚点集中到 SYSTEM.md 一处；全部正向表述。

### 第二轮审查：需修改

**核心发现**：t001 的问题不是"虚假声称查看了文件"，而是"根本没有声称查看任何东西就开始分析"。

**具体问题**：
1. 三选一出口 3（标注推测）是元认知后门
2. 触发条件太窄（"声称查看了"覆盖不了"我来分析一下"）
3. 规则是后验约束不是前验触发

**修订**：砍掉出口 3；触发条件扩展为"排查问题、分析情况时"；改为行为序列；加示例。

### 第三轮审查：需修改

**两个阻塞问题**：
1. "分析情况"触发条件过宽——会污染非排查场景（方案评估、总结对话、代码解释等）
2. "上下文引用"逃逸路径——已有规则"上下文有答案就直接回答"与排查锚点冲突，LLM 可合法绕过

**非阻塞问题**：
3. 示例过度引导——排查=读日志的绑定
4. 与已有规则"先查原文"语义重叠

**修订**：触发条件收窄为"排查问题时"；去掉示例；在已有规则后加排查限定。

### 遗留风险

- prompt 方案只能提高行为概率（概率偏移），不能保证 100% 触发
- 语言惯性在多轮对话中会累积，单次 prompt 信号可能被淹没
- 需要在实际对话中验证覆盖率，根据效果迭代
