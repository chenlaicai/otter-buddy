### Pi Agent 事件模型（来自 F20260715r3s2 研究文档 + 代码验证）

Pi AgentHarness 的 `invoke()` 通过 `harness.subscribe()` 回调推送事件。Pi 事件 -> SSE 事件 -> MessageEvent（持久化）的三路映射：

| Pi 事件（onEvent 回调） | SSE 事件（推送给前端） | MessageEvent（持久化到 DB） | 说明 |
|------------------------|----------------------|---------------------------|------|
| `message_update` (delta) | `message.delta` | `text_delta` | 增量文本 |
| `message_end` (assistant) | `message.complete` | --（由 `SendMessage.complete()` 处理） | Agent 消息完成 |
| `tool_execution_start` | `tool.start` | `tool_call` | 工具开始执行 |
| `tool_execution_end` | `tool.result` | `tool_result` | 工具执行完成 |
| `turn_end` | `turn.complete` | --（不持久化） | 轮次结束 |
| `agent_end` | `agent.idle` | --（不持久化） | Agent 空闲 |
| 其他错误 | `error` | `error` | 错误事件 |

> 注：`message.start` SSE 事件不是 Pi 事件，由 AgentInvoker 在调用 `SendMessage.start()` 创建 streaming 消息后手动发出。

**实体层 MessageEventType**（`entities/conversation/message.ts:10`）：
```typescript
type MessageEventType = "text_delta" | "tool_call" | "tool_result" | "error";
```

AgentInvoker 负责将 Pi 事件映射为：(1) SSE 事件格式（给前端）和 (2) MessageEventInput（持久化到 DB，使用实体的 MessageEventType）。

### AgentInvokePort 接口设计

**设计原则**：AgentInvokePort 是 interface-adapters 层定义的接口，签名与 `PiHarnessFactory.invoke()` 结构匹配。TypeScript 结构类型系统允许 `PiHarnessFactory` 直接作为 `AgentInvokePort` 的实现传入，无需显式 `implements` 声明。main.ts 将 `PiHarnessFactory` 实例注入为 `AgentInvokePort`，AgentInvoker 依赖此接口而非 frameworks 层具体类。

```typescript
// interface-adapters/agent-runtime/agent-invoke-port.ts

/** Agent 流式事件（与 Pi 的 AgentEvent 结构匹配） */
export interface AgentStreamEvent {
  type: string;       // Pi 事件类型：message_update, message_end, tool_execution_start, ...
  delta?: string;     // text_delta 内容
  [key: string]: unknown;
}

/** Agent 执行结果（与 Pi 的 AgentRunResult 结构匹配） */
export interface AgentRunResult {
  text: string;       // Agent 生成的完整文本，供 SendMessage.complete() 使用
  tokenUsage?: { input: number; output: number };
}

/** 动态上下文（与 Pi 的 DynamicContext 结构匹配） */
export interface DynamicContext {
  memoryRetrieval?: string;
  sessionSummary?: string;
}

/** invoke() 选项 */
export interface InvokeOptions {
  dynamicContext?: DynamicContext;
  onEvent?: (event: AgentStreamEvent) => void;
}

/**
 * Agent 调用端口：描述"驱动 Agent 生成"的能力。
 * PiHarnessFactory (frameworks 层) 的 invoke() 方法结构匹配此接口。
 * main.ts 将 PiHarnessFactory 实例作为 AgentInvokePort 注入。
 */
export interface AgentInvokePort {
  invoke(otterId: string, message: string, options?: InvokeOptions): Promise<AgentRunResult>;
  abort(otterId: string): void;  // ← UA-2: 中断指定 Otter 的 Agent 生成
}
```

### PiHarnessFactory 修改（frameworks 层）← UA-2

**问题根因**：frameworks 层实现时未考虑 abort 需求。`PiHarnessFactory.invoke()` 创建 harness 为局部变量，`createHarness()` 返回类型不包含 `abort()`，外部无法中断正在运行的 Agent。

**修改内容**（D59）：

1. **存储活跃 harness 引用**：`PiHarnessFactory` 新增 `private activeHarnesses: Map<string, { abort: () => void }>` 实例属性。`invoke()` 开始时注册，完成/失败时注销。
2. **暴露 abort(otterId)**：新增 `abort(otterId: string): void` 方法。从 `activeHarnesses` 取出引用，调用 Pi harness 的 `abort()`。
3. **createHarness() 返回类型扩展**：加入 `abort?(): void` 方法。

**修改范围控制**：仅修改 abort 相关逻辑，不重构 invoke() 核心流程（session 管理、event 订阅、compaction 等保持不变）。

**实现调查点**（development 阶段需确认）：
- Pi `harness.abort()` 调用后，`harness.prompt()` 的 Promise 是 reject 还是 resolve？预期：reject（AbortError 或类似）
- abort 后 session 状态是否一致？Pi 的 JSONL session 是否记录了中断点？
- abort 能力边界：研究文档指出 abort 在 turn 之间生效，不能中断正在流式输出的消息或正在执行的工具。这是 Pi 的固有限制，不影响设计完整性。

### AgentInvoker 编排器

AgentInvoker 是 interface-adapters 层的编排器，依赖 `AgentInvokePort`（而非 PiHarnessFactory）。它负责：

1. 构建 DynamicContext（记忆检索 + 会话摘要）
2. 创建 streaming 消息
3. 调用 Agent 生成
4. 事件映射（Pi -> SSE + MessageEvent）
5. 完成或失败处理
6. 中断处理：调用 `agentInvoke.abort()` 真正停止 Agent ← UA-2

### DynamicContext 构建流程

AgentInvoker 在调用 `agentInvoke.invoke()` 前构建 DynamicContext：

```
1. 记忆检索（memoryRetrieval）：
   - 使用用户消息作为查询，调用 SearchMemory.search({ query, limit: 10, layer: "working" })
   - 将检索结果格式化为文本（entry.content + score）
   - 如果检索失败，memoryRetrieval 为 undefined（降级为无记忆上下文）

2. 会话摘要（sessionSummary）：
   - 调用 ManageSession.getActiveSession(otterId) 获取当前 session
   - 如果 session 有 summary 字段（前序 session 归档时写入），使用该值
   - 首次 session 或 summary 为空时，sessionSummary 为 undefined

3. 传入 invoke：
   - agentInvoke.invoke(otterId, userMessage, { dynamicContext, onEvent })
```

### SSE 流式通信设计

**端点**：`POST /api/conversations/:id/messages`

**完整流程**：
1. Controller 接收 HTTP 请求，调用 `SendMessage.send()` 创建用户消息（completed 状态）
2. Controller 调用 `AgentInvoker.invokeConversation()`，传入 `onSSEEvent` 回调
3. AgentInvoker 调用 `SendMessage.start()` 创建 otter 的 streaming 消息
4. AgentInvoker 发出 `message.start` SSE 事件（非 Pi 事件，AgentInvoker 手动发出）
5. AgentInvoker 构建 DynamicContext（记忆检索 + 会话摘要，见 DynamicContext 构建流程）
6. AgentInvoker 调用 `agentInvoke.invoke(otterId, userMessage, { dynamicContext, onEvent })`
7. Pi 事件通过 `onEvent` 回调到达 AgentInvoker：
   - AgentInvoker 将 Pi 事件映射为 SSE 事件，通过 `onSSEEvent` 回调推送给 Controller -> SSE stream
   - AgentInvoker 将 Pi 事件映射为 MessageEventInput，调用 `SendMessage.appendEvent()` 持久化
8. invoke 返回 `AgentRunResult`（包含 `text`），AgentInvoker 调用 `SendMessage.complete(messageId, { body: result.text, ... })`
9. 如果 invoke 抛出异常，AgentInvoker 在 catch 中调用 `SendMessage.fail(messageId)`，然后区分来源（A1）：
   - abort 导致（`abortedOtters` 命中）-> 发出 `message.aborted` SSE 事件
   - 系统错误导致（未命中）-> 发出 `error` SSE 事件

**SSE 响应格式**：
```
event: message.start          # AgentInvoker 发出（非 Pi 事件）
data: {"messageId":"msg-xxx","otterId":"otter-xxx"}

event: message.delta          # Pi message_update -> SSE
data: {"text":" incremental text"}

event: tool.start             # Pi tool_execution_start -> SSE
data: {"toolName":"search_memory"}

event: tool.result            # Pi tool_execution_end -> SSE
data: {"toolName":"search_memory","result":{...}}

event: message.complete       # Pi message_end -> SSE
data: {"messageId":"msg-xxx","duration":"2.3s","ctx":12000,"ctxMax":128000}

event: turn.complete          # Pi turn_end -> SSE
data: {}

event: message.aborted        # AgentInvoker 在 abort catch 中发出（非 Pi 事件）
data: {"messageId":"msg-xxx"}
```

**Abort 机制**：`POST /api/messages/:id/abort` — Controller 调用 `AgentInvoker.abort(otterId, messageId)`，AgentInvoker 调用 `agentInvoke.abort(otterId)`（即 `PiHarnessFactory.abort()`），Pi Agent 真正停止生成。`invoke()` 的 Promise reject 后，AgentInvoker 在 catch 中：调用 `SendMessage.fail(messageId)` + 发出 `message.aborted` SSE 事件。← UA-2: 完整实现，非受限实现。

### SSE 流生命周期（A2）

`sse-streamer.ts` 封装 Hono `streamSSE`，负责 SSE 流的创建、写入和清理：

**创建**：MessageController 在 `POST /api/conversations/:id/messages` 中调用 `sse-streamer` 创建 SSE 流，同时启动 `AgentInvoker.invokeConversation()`（异步，不 await）。

**写入**：`onSSEEvent` 回调将 SSE 事件写入流。事件类型：`message.start`、`message.delta`、`tool.start`、`tool.result`、`message.complete`、`message.aborted`、`error`、`turn.complete`。

**正常关闭**：`message.complete` 或 `message.aborted` 或 `error` 事件发出后，关闭 SSE 流。

**客户端断连**：Hono `streamSSE` 提供 `abort` 信号（`onAbort` 回调）。断连时：
1. SSE 流标记为已关闭，停止写入
2. 调用 `AgentInvoker.abort(otterId, messageId)` 中止 Agent 生成（避免无人消费的 Agent 继续消耗 token）
3. AgentInvoker 的 catch 块仍执行 `SendMessage.fail(messageId)`（消息状态持久化，不依赖 SSE 流）

**跨请求关系**：
- Request A（SSE 流）：`invokeConversation()` 异步运行，通过 `onSSEEvent` 推送事件
- Request B（abort）：`POST /api/messages/:id/abort` 调用 `AgentInvoker.abort()`，返回 202 Accepted
- Request A 的 catch 块发出 `message.aborted` 事件（如果 SSE 流仍连接），然后关闭流

## 设计取舍

| 取舍点 | 正方 | 反方 | 最终选择 |
|--------|------|------|---------|
| SSE vs WebSocket | SSE 语义匹配单向推送，Hono 内置支持，实现简单 | WebSocket 支持双向通信，前端已有 wsDisconnected 状态 | SSE（D50）。Agent 响应是单向推送，abort 用 POST 端点实现。前端 `wsDisconnected` 状态可复用于 SSE 连接断开检测 |
| DTO + 转换函数是否拆分为 DTO + Presenter | 分离更符合 Clean Architecture（Presenter 是 Interface Adapter 的经典组件） | 合并更简单，转换逻辑通常 < 10 行 | 合并（D53）。当前转换逻辑简单，分离增加文件数无额外价值 |
| AgentInvokePort 是否放入 usecases | usecases 层定义接口更符合"消费者定义端口"原则 | invoke 涉及 Pi Agent 运行时（frameworks 概念），不属于应用业务规则 | interface-adapters 层定义（D51）。invoke 是接口适配层的关注点，不是应用业务规则 |
| Tool 工厂 vs 每个 tool 独立导出 | 工厂统一管理依赖注入，确保 tool 获取 use cases 实例 | 独立导出更灵活 | 工厂模式（D52）。统一注入确保依赖一致性，tool-factory.ts 是唯一的 tool 创建入口 |

## 关键决策记录

### KDR-7：AgentInvokePort 签名与 PiHarnessFactory 结构匹配（架构师-2 审视修正）

- **决策点**：AgentInvokePort 的签名应该面向 Controller（友好参数）还是面向 PiHarnessFactory（结构匹配）？
- **草稿方案（架构师-1）**：AgentInvokerPort 面向 Controller，参数包含 `{ otterId, conversationId, userMessageId, onEvent }`，PiHarnessFactory "隐式实现"
- **审视意见（架构师-2）**：PiHarnessFactory.invoke() 签名完全不同，不构成隐式实现。AgentInvokerPort 是独立接口，需要适配器
- **最终决策**：AgentInvokePort 签名与 PiHarnessFactory.invoke() 结构匹配（`invoke(otterId, message, options?)`），TypeScript 结构类型系统允许直接注入。AgentInvoker（编排器）依赖 AgentInvokePort 接口，负责 Controller 友好参数到 invoke 参数的转换
- **决策依据**：避免额外的适配器层。结构匹配使 main.ts 可以直接将 PiHarnessFactory 作为 AgentInvokePort 注入，AgentInvoker 负责编排逻辑（DynamicContext 构建、消息生命周期管理、事件映射）
- **参与者**：架构师-1、架构师-2

### KDR-8：Pi 事件三路映射链（架构师-2 审视修正）

- **决策点**：AgentEvent 类型如何定义？
- **草稿方案（架构师-1）**：自定义 5 种事件类型（text_delta/tool_start/tool_result/turn_end/error），与 Pi 实际事件和实体 MessageEventType均不一致
- **审视意见（架构师-2）**：三处类型不一致会导致映射混乱
- **最终决策**：AgentInvokePort 使用 Pi 的实际事件类型（`type: string; delta?: string`）。AgentInvoker 负责三路映射：Pi 事件 -> SSE 事件（给前端）+ MessageEventInput（持久化到 DB，使用实体的 MessageEventType）
- **决策依据**：单一事实来源。Pi 事件是原始来源，SSE 和 MessageEvent 是两种输出格式，映射逻辑集中在 AgentInvoker
- **参与者**：架构师-1、架构师-2

### KDR-9：DynamicContext 构建流程（架构师-2 审视补充）

- **决策点**：AgentInvoker 如何构建 DynamicContext？
- **草稿方案（架构师-1）**：未定义
- **审视意见（架构师-2）**：核心流程缺口，Agent 对话不是简单的 invoke(otterId, message)
- **最终决策**：AgentInvoker 在调用 invoke 前构建 DynamicContext：(1) 使用用户消息调用 SearchMemory.search() 检索工作记忆，格式化为文本；(2) 从 ManageSession.getActiveSession() 获取前序 session 的 summary
- **决策依据**：记忆检索和会话摘要是 Agent 上下文构建的必要步骤，必须在设计文档中明确定义
- **参与者**：架构师-1、架构师-2

### KDR-10：Abort 机制完整实现（用户指令修正 ← UA-2）

- **决策点**：Abort 机制如何实现？
- **草稿方案（架构师-1）**：Controller 设置 AbortController，传递给 PiHarnessFactory.invoke()
- **审视意见（架构师-2）**：PiHarnessFactory.invoke() 不接受 AbortSignal，Pi 的 harness.prompt() 是否支持中断未知
- **一审最终决策**：受限实现。AgentInvoker 维护 abortSet，在 onEvent 回调中检查。Pi 内部 LLM 请求可能后台继续，结果被忽略
- **用户修正（UA-2）**："发现问题就应该从根源解决，而不是打补丁"。受限实现是 hack 方案，会导致代码仓变成"屎山代码"。用户明确授权移除"不修"硬约束
- **最终决策**：完整实现。修改 PiHarnessFactory（frameworks 层）暴露 abort 能力：(1) 存储活跃 harness 引用 (2) 暴露 abort(otterId) 方法 (3) AgentInvokePort 加入 abort 签名。AgentInvoker.abort() 调用 PiHarnessFactory.abort()，Pi Agent 真正停止
- **决策依据**：用户指令优先（UA-2）。从根源解决问题优于打补丁。Pi 的 abort() 能力边界（turn 间生效，不中断流式输出）是 Pi 的固有限制，但已是最佳可用方案
- **参与者**：架构师-1、架构师-2、用户
- **修改历史**：一审"受限实现" -> 用户修正 -> "完整实现"
