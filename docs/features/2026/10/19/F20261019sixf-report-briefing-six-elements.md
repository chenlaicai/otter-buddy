# 汇报六要素——PR 汇报必须让搭档 30 秒看清「什么事/要你干什么/后续尾巴」

## 1. 背景 / 问题

### 1.1 搭档反馈（原话引用，10/16，本对话）

> 「我最近遇到一个情况，那就是，你们海獭做完 pr 向我汇报时，没有说 还残留什么后续、把什么东西排在了后续。然后每次都是我合入之后，你收尾时才跟我说 还有啥啥后续。我觉得这一点必须优化下，汇报时就要说清楚 背景/方案/关键决策/当前情况/后续等等这些，快速让我知道这是个什么事情，然后要我干什么，关键信息都要让我快速看懂」

### 1.2 现行案例

PR #864 合入后收尾时才提「衍生的 #867 是 OPEN 待办，保留」——这个尾巴在呈终审时搭档根本不知道（本对话 10/16 消息）。问题不在「有后续」——有后续是正常工程状态——问题在**信息释放时机**：合入前的汇报不说，合入后的收尾才说。搭档拍「合入」这个板时，决策依据是不完整的。

### 1.3 旧规范的缺口

F20260916rptl 建立的三层简报（3 秒执行摘要 / 30 秒关键信息 / 完整版）解决了「拍板时不知道方案全貌」（F20260909debr 治盲签拍板），但对照搭档 10/16 的要求，仍有四个缺口：

| 缺口 | 旧规范状态 | 后果 |
|---|---|---|
| 「这是什么事」无必填位 | 3 秒层只有结论+风险+置信度 | 搭档扫一眼不知道在说哪个 PR/议题 |
| 「要你干什么」无必填位 | 隐含在结论里 | 「知晓即可」与「要拍板」分不清 |
| 「当前情况」无数字来源约束 | 30 秒层无此区块 | 「基本完成」是自报口径，凭印象说完成 |
| 「后续事项」无显式呈报要求 | decision-briefing.md 此前无「后续/残留/排期」字段（全文检索零命中，10/16 核实） | 「没说」与「没有」不可区分——信息黑洞 |

第 4 条是搭档反馈的直接痛点。10/16 核实记录：decision-briefing.md 全文搜「后续/残留/排期」零命中，旧规范确实没有这个字段——不是执行走样，是规范本身缺位。

## 2. 方案设计

### 2.1 六要素映射三层结构

不新起模板体系，在现行三层简报上增量落六要素：

| 要素 | 落点 | 要求 |
|---|---|---|
| 这是什么事 | 3 秒层 | 一句话背景（哪个任务/PR/议题） |
| 要你干什么 | 3 秒层 | **必填**：拍板/合入/知晓/无——不许省 |
| 背景 | 30 秒层 | ≤3 行：为什么走到这一步，触发点是什么 |
| 方案与关键决策 | 30 秒层 | 含被否方案和否决理由；执行期关键取舍也在此交代 |
| 当前情况 | 30 秒层 | 状态一览：做到哪了/验证到什么程度/刻意没做的是什么；**数字必须带来源**；**完成状态三级分级** |
| 后续事项 | 30 秒层 | 逐条列残留/排期/衍生/留观，每条带去向；**分流**「需要你介入的」vs「不需要你介入的」；没有就**显式写「无」** |

两条纪律贯穿：

- **「没说」≠「没有」**——六要素之内一个不许省，没有也要显式写「无」。
- **长汇报（≥500 字）末尾复述 3 秒层要点**（尤其「要你干什么」）——扫开头和结尾就能拼出全貌。

### 2.2 新增：离场回顾格式（while you were away）

长任务/定时任务/小獭回报等「搭档不在场时发生的事」，汇报按三段式：

1. **你离开期间发生了什么**：干了什么、产出了什么（关键数字带来源）
2. **现在停在哪**：当前状态 + 卡点（有卡点说卡点，没卡点说「畅通」）
3. **接下来干嘛 + 要你干什么**：下一步计划 + 需要搭档的动作

设计依据：Muse Code 的 recap/request 协议（「while you were away recap」，协议级一等公民方法）——异步 agent 的用户回场时需要 30 秒接上上下文。小獭向大獭回报、大獭向搭档转报同理：**汇报对象不在场是常态不是例外**，别用「在场对话」的口吻写「不在场期间」的事。

### 2.3 完成状态三级分级

「当前情况」里的完成状态分三级，不许混用：

| 级别 | 定义 | 汇报要求 |
|---|---|---|
| 已验证完成 | 有工具返回证据支撑（CI 绿/测试全过/锚点可达） | 附验证锚点 |
| 自检完成 | 自查通过但未经独立验证 | 标注「自检」，不许写成「完成」 |
| 未验证 | 尚未验证 | 如实标注，不许含糊 |

设计依据：Codex Completion Audit 原则——**不确定的证据 = 未达成**。汇报里的「完成」必须能回答「凭什么说完成」。

### 2.4 五条修订点的业界依据

详见 R20261019agnt（四家调研全文）：

| # | 修订点 | 业界依据（置信度） |
|---|---|---|
| 1 | 数字必须带来源 | Muse PatchSummary 服务端统计（高）；与本项目 A1 证据锚点纪律同构 |
| 2 | 后续事项分流 | Dots approval / Claude notification（中/高）——行动召唤必须显著 |
| 3 | 离场回顾三段式 | Muse recap/request（高） |
| 4 | 完成状态分级 | Codex Completion Audit（中高，记忆条目 F20260807eval） |
| 5 | 长汇报末尾复述结论 | Claude TL;DR 协议（高） |

## 4. 设计取舍

### 4.1 不推倒重来，在三层结构上增量（被否方案：另起独立汇报模板体系）

被否理由：F20260916rptl 的三层结构刚建立（9/16），且直接源于搭档当时明确要的「三秒/三十秒/完整版」——六要素与三层结构不是竞争关系，是内容要素与组织形式的正交组合：六要素答「说什么」，三层结构答「怎么说」。另起体系会产生两套并存的简报格式，徒增选择成本与规范分裂。六要素逐项映射进现有三层落点（见 2.1 表），改动面最小、学习成本最低。

### 4.2 「要你干什么」放 3 秒层而非 30 秒层

候选位置有二：30 秒层信息更全、判断更稳；3 秒层可见性最高。选 3 秒层，理由：行动召唤错过成本最高（Claude notification / Dots approval 的共同设计——行动召唤要有最高显著度），且「拍板/合入/知晓/无」四选一的判断粒度不依赖 30 秒层的背景信息，放 3 秒层不牺牲准确性。

### 4.3 完成状态用三级而非两级（已验证/未验证）

考虑过两级制（更简）。保留「自检完成」中间级，理由：两级制下「自检通过但未独立验证」只能归入「未验证」，会系统性低估獭的工作状态——汇报失真方向从「虚报完成」变成「虚报未完成」，同样误导拍板。三级制与 Codex 证据质量五档（证明完成/矛盾/未完成/证据不足/缺失）对齐精神：中间态如实呈现，不做二元压缩。

### 4.4 纯 prompt 层落地，不动运行时（被否方案：工具链自动检测数字来源）

被否理由：Muse PatchSummary 的「服务端算数字」需要运行时支持（diff 统计、CI 状态查询接口），当前项目无此基建；prompt 层「数字必须带来源」+ 模板自检清单已能覆盖主要场景（写的人被要求标注来源，看的人有清单可查）。工具链自动检测列为后续观察项——若 prompt 层落地后仍出现数字虚报，再上工具链。
