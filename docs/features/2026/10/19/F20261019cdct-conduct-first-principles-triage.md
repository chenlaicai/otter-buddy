# 海獭行为准则第一性原理重整（#1557）

## 目标

獭的价值 = **让问题离解决更近**，不是让问题的清单更整齐。四文件收口，把 issue/待办从「记录在案」导向「离解决更近」。

## 非目标

- 不新增机制工具（不加新列、不加新表、不加新定时任务）——**警惕用更多规则治理规则泛滥**
- 不改 matters 状态机与宣告权守卫（F20261006mtlp 域）
- 不自动关闭任何 issue（剪枝一律呈卡裁决，裁决权恒在搭档）
- 不处理 PR 侧纪律（R1/审视流程已覆盖）

## 数据实证（2026-10-19 摘牌时点）

| 指标 | 数值 |
|---|---|
| open issue | 101 |
| 10 月新建 / 关闭 | 124 / 79（净增 +45） |
| assignee 数 | 0（全量无主） |
| 最老条目 | #486，53 天 |
| 超 14 天静默条目 | 63 |
| 三桶占比 | P0P1 bug ×14 / daily-review ×20 / question ×4 / tech-debt P2 ×41 / enh P2 ×8 / other ×14 |

上游三个定时任务（8:30 健康检查 / 9:00 healing 分析 / 7:30 未闭环扫描）每日产出候选，下游「每日-issue-处理」消化上限 3 条/日且需搭档勾选——上游无准入门槛、下游有消化瓶颈，存量必然积累。

## 方案设计

### 1. SYSTEM.md R2 —— 准入两问 + 净增熔断

在既有 Issue 纪律（案发现场/锚点/标签/聚合）基础上，追加分段：

- **Issue = 承诺不是收纳箱**（2026-10-19 搭档定调，#1557）：立案前两问——①能写出可验证的完成条件吗？②有人修有排期位吗？P0 现场与搭档亲报直接立案，其余观察/评估类发现默认进日报候选池（7 天未勾选自动出池），不许「先记着」。
- **净增熔断**：open > 60 或单月净增 > 20 时只允许 P0/P1 与搭档点名项新立（9:30 清单头每日报熔断状态）。

### 2. 候选池（8:30 报导尾段 + 9:30 细则，单一真相源在 9:30）

观察类/评估类/单条信号不足以定性的发现（「值得看看」「待评估」「策略口径问题」）默认进日报末尾「候选池」段——一句话线索 + 证据锚点，不建 issue。8:30 侧只留指针（体积纪律，细则在 9:30 任务）：
1. 候选连续 7 天无人勾选（9:30 清单回复引用）自动出池，出池不补救
2. 同一线索二次出现时附首次出池记录，仍未勾选继续出池——重复出现不是立案理由，「勾选」才是
3. P0 现场与搭档亲报不走候选池，直接立案
4. 判定犹豫时问一句：这条现在有人修吗？没有 → 候选池
5. 状态载体：候选即日报文本（不建库不建表）——执行 7 天出池时按当日 8:30 日报逐条核对首次出现日（消息历史可检索），无则视为出池

### 3. 轮换切片（每日-issue-处理）

D 类排期 issue 全量刷屏（101 条）改轮换：按最后实质更新日倒序取最旧 25 条为当日切片，切片内发生处置的自动滚出，次日补入新最旧条目；全量盘点职责移交月度剪枝审视。另附当日新建 P1/P0 全量（不占 25 条额度）——高优不因轮换埋没。清单头第一行固定为熔断状态：`净增熔断：open N | 昨日新增 x / 关闭 y | 状态：正常/触发`。

stale 规则同步统一（审视发现 2 处置）：旧条款「tech-debt 放宽到 30 天」删除，新语义统一为——非 daily-review issue 实质静默超 14 天 stale 关闭；tech-debt 不走 stale 关闭，实质静默超 14 天进月度剪枝候选（特赦权在搭档，剪枝呈卡裁决）。「更新」指实质推进（认领/关联 PR/评论推进），例行 ping/标签补齐/重开不算。

### 4. issue 层候选源（monthly-prune-review）

三层候选源变四层——新增第 3 层：全量 open issue，实质静默超 14 天入候选（统一阈值，不再按 tech-debt 放宽）。判定材料用 `gh issue list --state open --json number,updatedAt,comments --jq` 取最后实质评论时间；P0/P1 bug 类不入剪枝候选。候选项附：静默天数 / 有无验证断言与关闭标准 / 最后实质动作。批量处置方式：可合并（同域同根因）/ 可关闭（关闭标准已满足或已被取代）/ 待搭档特赦（写明为何留）——批量操作一律呈卡裁决后执行，不自行关。

## 存量分桶处置（本 PR 只立规矩，存量动作另走）

本 PR 四文件只立规矩；存量处置动作按分桶另走，不与规矩 PR 混在同一 PR：

- **question ×4**（#1051 #1204 #1298 #1472）：当场消化——已在对话内回答的引用答案关闭；等搭档原话的直接呈上
- **daily-review ×20**：三日内快判——P1 级真问题转正入排期，P2 观察类转候选池，已修的关
- **P2 系 ×63**（tech-debt 41 + enh 8 + other 14）：不下逐条结论——留给月度剪枝首跑批量处置（首次运行 10 月内跑一轮）
- **P1 ×14**：正常排期，不裁剪（本来就要修的）
- **熔断状态**：当前 101 open > 60 → 已处于触发态。存量处置节奏需快于原计划，question×4 当场消化是第一步

## 影响

- 次日 8:30 日报出现「候选池」段（原本会直接立案的观察类发现改走候选池）
- 次日 9:30 清单头出现熔断状态行
- 次月月度剪枝首跑将处理 P2 系 63 条的静默候选
- 净增趋势与 open 水位由每日大盘统计跟踪，跌破 60 后熔断解除

## 取舍

- **不加新机制工具**：搭档关切「用更多规则治理规则泛滥」——本方案只改四个 prompt 文件的文字规则，零代码新增（不加列/不加表/不加任务），所有判定（候选池/静默/熔断）都是 prompt 层行为约定，由定时任务执行时落地，成本低、可逆性好
- **阈值选择（open>60 / 净增>20 / 静默>14 天）**：基线数据为 101 open / 净增 +45 / 63 条超 14 天静默——阈值取存量状态的目标区间，非拍脑袋；太松则堰塞湖不退，太紧则真问题被误伤。月度剪枝首跑后可校准
- **为何是 prompt 层而非代码层**：立案/消化/剪枝都是獭的行为，prompt 层约束直接作用于行为源头；若 prompt 层约束失效（熔断被绕过、候选池变新坟场），再升级代码层硬闸（如 gh issue create 守卫）——先软后硬，观察一个迭代周期
- **不变更「每日-issue-处理」勾选后开工纪律**：搭档 2026-09-17 定调「issue 处理必须经同意」不变——本方案收紧的是立案上游，与下游勾选开工完全兼容
