# 《山河收刀人》长篇武侠连载与跨轮次创作账本

## 背景与目标

搭档要求创作一部 200—300 万字、以 PR 交付的武侠小说，并用这项真实长任务检验海獭的长期记忆与任务规划编排能力。题材取向不是追逐玄幻标签而抛弃武侠，而是以传统江湖关系为根，用有代价的东方玄幻规则扩大世界冲突。

全书采用 8 卷、960 章、约 240 万字的工作目标。规模是规划约束，不允许以重复、灌水或提纲凑数；完稿区间服从搭档提出的 200—300 万字。

## 非目标

- 不修改产品运行时、prompt、skill 或数据库。
- 不建立自动续写服务或定时任务，不在无人工/agent 触发时后台生产内容。
- 不用设定集、章节标题或重复文本虚增正文字数。
- 不在一次 PR 中宣称完成尚未写出的章节。

## 方案设计

### 故事层

- 核心题目：《山河收刀人》；主角陆停舟，出身归义镖局的收刀人。
- 类型：武侠为骨、玄幻为势；以送刀、认刀与归还名字贯穿八卷。
- 先确定终局因果，再分解分卷目标、章节卡和每批正文，避免边写边换终极反派。

### 长任务层

- `story/` 保存稳定设定与规划；`continuity/` 保存随正文变化的事实。
- 每批写作遵循“读账本与近期正文 → 写正文 → 更新逐章事实 → 异体连续性/文学审视 → 修订与 delta 复核”。
- `progress.json` 区分目标与已完成；`chapter-log.jsonl` 逐章记录摘要、视角、时间、地点、新增事实和伏笔变动。
- 人物伤病、持有物、知识边界、时间线与未还伏笔均须可从账本追溯，不依赖某次会话记忆。

### 交付层

- 首个 PR 建立连载主干并交付正式开篇，后续按批次追加。
- 文学质量不能由字数脚本替代；机械检查负责章号、文件、JSON 可读性与进度一致性，异体审视负责节奏、人物、逻辑和武侠质感。
- Modification-Class：`docs-config`——本变更只新增 Markdown/JSON 创作内容，不触及代码机制或既有产品行为。

## 设计取舍

- **不写 960 章一次成型的僵硬细纲**：锁定八卷因果与第一卷全卷节拍，详细章节卡滚动维护；给人物反应留下生长空间，但不能改变终局因果。
- **不以全知账本替代正文**：账本记录可检索事实，具体语感以最近正文为准。
- **不追求首 PR 体量虚胖**：首批以能验证开篇声音、人物关系和连续性流程为准；总目标与实际进度分账。
- **不拆分多个互相依赖的未合入长篇 PR**：同一连载主干持续增量，减少跨 PR 继承冲突。

## 验收标准

### 全书终态（尚未完成）

| 场景 | 操作 | 预期结果 |
|---|---|---|
| 体量 | 统计 960 个正式正文文件的去标题字符数 | 200—300 万字，且非提纲/设定/重复文本 |
| 连续性 | 逐章对照人物、时间线、持有物与伏笔账本 | 无未经正文解释的状态跳变；终局伏笔全部有处置 |
| 文学质量 | 分卷异体审读 | 每卷有完整矛盾与收束，终局由既有因果和人物选择完成 |

### 首个 PR（本次交付）

| 场景 | 操作 | 预期结果 |
|---|---|---|
| 档案完整 | 阅读 README、创作圣经、总纲和账本 | 能独立回答写什么、写到哪、下一章如何接 |
| 真实正文 | 打开 `chapters/` | 存在完整正式章节，非仅规划文档 |
| 进度诚实 | 对照正文与 `progress.json` | 已完成章数/字数不高于实际，未把目标写成成果 |
| 结构 | 解析全部 JSON/JSONL 并检查连续章号 | 无语法错误、无重号/漏号（从第 1 章起） |
| 文学与连续性 | 异体对抗审读 + 修订后 delta 复核 | 无严重逻辑/连续性发现，审视意见逐条处置 |
