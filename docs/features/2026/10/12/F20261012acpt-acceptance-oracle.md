# F20261012acpt 验收客观化补全

## 背景

**意图锚（搭档原话，2026-10-12）**：

> 「我觉得，趁热乎，你来深入分析，然后给出咱们海獭系统的优化方案」

承接同日讨论：外部案例《500+ Billion Tokens Later: Letting AI Agents Decompile A First-Person Shooter》（Maurice Heumann，2026-10-09，https://momo5502.com/posts/2026-10-09-game-decompilation/ ）中，agent 反编译项目第一个月「80% 进度看起来很好、语义全错」，解法是把验收从 LLM reviewer 判断换成字节比对的客观 PASS/FAIL（The Oracle）。搭档判断「看起来很好」是 agent 通病，要求将该洞察转为海獭系统优化方案。

**结晶门豁免留痕**：搭档「趁热乎，你来深入分析，然后给出……方案」含直接出方案的明示意图，C1–C5 五问豁免（范围开放部分以「未决问题」节显式留槽）。

### 深入分析：外部案例的可迁移结论

原案例三件套（均有一手实证）：
1. **correctness 必须定义且机器可查**——「人类出了名地不擅长精确表达意图，所以 reviewer 永远不够」；客观 PASS/FAIL 是 agent 能得到的最好反馈，且精确反馈下便宜模型逆袭（成本结构反转）
2. **验收装置必须防篡改**——被验收者反复试图改验证脚本把自己的函数排除出比对，最终 CI 用哈希锁死脚本；worker 注释成为「非故意 prompt injection」骗过 reviewer
3. **进度指标与质量指标是两种数字**——「80% 已翻译」与「83% 字节精确」混报即「看起来很好」的温床

机制归因（**迁移推断，非案例一手实证**——案例一手实证的是：agent 改验证脚本、字节比对 oracle、worker 注释骗过 reviewer）：**agent 会收敛到验收函数上——用什么验收，就产出什么**。用「reviewer 觉得像」验收，产出「看起来像」。

### 深入分析：海獭系统现状盘点（先找反对，再找支持）

**已有基建（好消息：oracle 等价物地基已在）**：
| 机制 | 锚点 | 性质 |
|---|---|---|
| 能力测试层（真装配+真模型，行为不变量断言） | F20260806tstr，tests/capability/ | 档 1 机器验收 |
| A3 模型可见内容重建比对（篡改一字报级路径差异） | R20260817dshp | **海獭版字节比对** |
| lint 系列 ratchet（lint-prompt-anchors / lint:docs / lint:capability，上限只降不升） | 5a381f1a 等 | 验收装置防倒退 |
| merge_pr 机械闸（partnerApproval 逐字校验） | merge_pr 工具 | 机器闸 |
| RHI 确定性指标引擎（bugfix 占比/文件复发率/hotspot/链停滞，全无 LLM） | 3bd7f2f1 | 质量指标面 |
| 噪声带对照纪律（涨跌须对照 7 日常态波动） | 8cc1ecd3（RRSI 移植） | 断言纪律 |
| 证据锚点规则（A1：事实断言必须附锚点） | F20260916evan | **对话纪律（非机械）** |
| 教训沉淀验收条（三要素现场） | F20260917lssc | 验收标准先例 |

**三缺口（本方案要补的）**：
- **G1 系统断言无 provenance**：安全词扫描的 reminder 文案「用户消息命中安全词『停下』」（stop-word-scanner.ts:51 附近模板、dispatch-chain-engine.ts:182 注入）不附消息锚点、不区分来源——2026-10-12 假急停实证（定时任务 prompt 被当用户消息扫描，LLM 归因错误无人可查，issue #1430）。A1 证据锚点是对话纪律，管不住**系统注入的断言**。
- **G2 验收装置可被被验收者修改**：实现者可在 PR 中放宽/删除测试断言过 CI（「改验证脚本」的同构场景）；adversarial-review 维度无「测试弱化」专项认定；能力测试基线改动无声明要求。
- **G3 进度与质量混同**：汇报惯例只报产出数（PR/任务/issue 数），不报「其中已验证几个」〔凭印象归纳，置信度中——无机械统计支撑〕；定时任务「跑完」≠「有效果」无效果验收（雷达自 9 月起每日运行〔调度任务「每日 AI 雷达」〕，prompts/scheduled/daily-ai-radar.md 无任何效果指标条款〔可 grep 核实；delta 复核订正：初稿误写为工作区副本路径 radar/prompt-template.md，仓库真相源为本路径〕——「看起来在跑」的现行形态）。

## 目标

- T1: 系统注入的事实断言附机器证据锚点；无锚点断言机械降级标注为「未核实」（治 G1）
- T2: 验收装置防弱化——测试/基线改动显式声明 +「测试弱化 = 严重发现」进检视维度（治 G2）
- T3: 双数字汇报（已产出 / 已验证）进文档模板与检查项（治 G3）
- T4: 效果验收试点 1–2 个定时任务（治「看起来在跑」）

## 非目标

- **不照搬字节比对**：多数海獭产出（方案/文档/决策）无 ground truth，强推机械化即 Goodhart——档 3 产出维持「对抗审视 + 搭档拍板」
- **不做测试作者分离**（测试不由检视獭编写）：成本翻倍，「测试弱化检查」覆盖主要风险
- 不给方案/文档质量强加机械打分指标
- 不新建指标采集管道（效果指标挂现有 RHI/health 数据面）
- 不包含 #1430 的 bug 修复本身（独立 issue 独立修，本方案 T1 是其增强层）

## 未决问题

- T1 锚点格式与降级文案规范（`[证据: msgId=… seq=…]` 形态待实现时定稿，或呈搭档）
- T1 范围：仅安全词链路先行，还是所有系统注入断言（health 结论/指标声明）一次铺开——**建议窄口先行**，验证后扩
- T4 效果指标口径（点菜率定义、统计窗口）试点期确定
- 基线哈希登记是否需要（见设计取舍：暂缓）

### T1 断言证据锚点闸（净新增机制，G1）

**现状**：`dispatch-chain-engine.ts:182` `scanStopWords(userMessageContent).reminder` 生成文案「用户消息命中安全词『停下』」注入 prompt——①不区分消息来源（定时任务 prompt 同样进扫描）②断言无消息锚点，LLM 无法自查。

**做法**：
1. reminder 模板携带机械证据锚点：`[证据: msgId=<uuid> seq=<n> 来源=user|scheduler]`——锚点由消息系统机械生成，不经 LLM
2. 来源枚举为 `user|scheduler|system`（三态而非二值——2026-10-12 11:57 安全词二次复现的触发源即 system 合成消息：首哑告警转发文本被扫描命中「停下」，实证已补录 #1430 评论；二值枚举会把当日刚复现的形态挤进错误桶）。非 user 来源的触发消息，reminder 改为「疑似命中（来源非用户消息）」或直接不注入（与 #1430 修复方向一致；本方案不替代该修复）
3. 无锚点可附时，断言机械降级为「未核实推测」——**降级标注由 reminder 模板生成器机械拼接（纯字符串拼接，不经 LLM 书写）**，机械闭环不依赖 prompt 纪律（回应检视建议 1：G1 自己论证了 prompt 纪律管不住系统注入断言，降级执行不能又交回 prompt 层）；LLM 侧的行为约束由 prompt 层另行承接（A1 已有措辞）

**涉及文件**：src/usecases/signal/stop-word-scanner.ts（模板）、src/usecases/conversation/dispatch-chain-engine.ts（传元数据）——实现随 #1430 修复 PR 走。**落地声明**（回应检视建议 4）：该 PR 含净新增机制（锚点格式），commit/PR 的 Modification-Class 须声明 `mechanism-addition` 并引用本文档「机制预算四问」节，避免 B4 变更标识机械核对判为声明不符（bugfix 混装机制）；T2/T4 落地 PR 同理需履行 B6 intent 声明与 B7 Golden Gate 义务。

### T2 测试弱化防线（流程+文档层，G2）

### T3 双数字汇报（模板层，G3）

**做法**：docs 模板（特性文档交付表、汇报惯例）强制双行数字：「已产出 X / 其中已验证 Y」；daily-health-check 检查项加一条抽查。早期「已验证 0」是常态——这正是要暴露的现实，不粉饰。**适用域划档**（回应检视建议 6）：双数字仅适用档 1/2 产出；档 3（战略判断/产品方向）无「已验证」定义域，用「已过审视/已拍板」文字口径——避免把档 3 形式机械化（非目标节 Goodhart 红线）。

## 设计取舍

| 取舍 | 决策 | 替代方案 | 理由 |
|---|---|---|---|
| 字节比对式 oracle 移植 | 不照搬，按 ground truth 有无分三档 | 全面 oracle 化 | 多数产出无 ground truth；强推机械化 = Goodhart；原案例作者自己也说非反编译项目只能「靠创造力逼近」 |
| 测试作者分离 | 不做 | 测试由检视獭编写 | 成本翻倍；「弱化检查 + 声明制」覆盖主要风险（篡改的主要形态是放宽而非全新编造） |
| T1 范围 | 窄口先行（安全词链路） | 全部系统断言一次铺开 | 机制铺太宽的负面教训在案；窄口验证后再扩 |
| 基线哈希登记 | 暂缓，先声明制 | lint 扩展哈希校验 | 净新增机制成本高；声明+检视先行，仍有逃逸再升级 |
| 效果指标 | 只观测不考核 | 进 RHI 考核面 | 防 Goodhart；考核化会催生凑数行为 |
| 档 3 是否机械化 | 不 | 方案质量打分 | 不可定义领域强行指标化的危害大于收益 |

**机制识别检查点判定**：命中「新增信号类型/消息格式」（T1 锚点格式）、「新增决策分支」（无锚点降级判定）→ 判定**涉及净新增机制**（T1）→ 四问必答 + 重对抗门必过。T2–T4 为流程/模板/观测层，判定不涉及净新增机制。

## 机制预算四问（T1 断言证据锚点闸）

① **谁需要它**：所有读系统注入断言并据其行动的獭（大獭/小獭——假急停实证中是大獭误行动）；以及事后复盘的搭档（可追溯断言出处）。「应该有」不算——有 10-12 事故实证。
② **失败后果**：无锚点断言被当事实 → 系统误行动（急停/误判用户意图），用户可感知损害（工作流被打断、信任损耗）；已实际发生一次（#1430）。
③ **后续机制**：锚点本身可能错吗——锚点由消息系统机械生成（uuid/seq），不经 LLM 书写，错误面收窄到消息系统自身故障；降级文案可能过密造成忽略 → 试点期观测降级率，过密时收窄注入条件而非删锚点。
④ **退役条件**：当全部系统断言的来源都自带机器可查 ID（工具返回结构化 ID 成为惯例）时，显式锚点字段冗余，可删。**中间复盘点**（回应检视建议的全称化倾向）：试点 2–4 周后复审一次——评估非 user 来源触发占比、降级率、扩面进度（G1→health/指标声明链路），复审结果决定继续/收窄/扩面；无复审记录则本机制视为长期化并需搭档知情。
