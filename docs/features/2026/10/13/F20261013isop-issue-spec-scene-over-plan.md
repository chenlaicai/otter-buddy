# issue 产出规范修正：案发现场强制 + 方案段分级 + 开工独立核实

## 背景

搭档 chen（2026-10-13 16:57）提出：提 issue 时海獭会把可能的解决方案写上去，误导后续处理獭。期望：案发现场必须百分百真实，方案必须经过深入排查后才能给出，不能想当然。

## 根因

不是个别海獭的坏习惯，是制度性诱因——SYSTEM.md R2 硬性要求「必须带具体修复方案」，daily-health-check.md 跟着写死。提 issue 的海獭被要求必须给出方案，没排查也得憋一个。处理端（每日-issue-处理.md）没有「重新核实」防护，勾选后方案默认继承。

实证抽查：
- #1453：案发现场扎实，但「建议修复方向」段含未经排查的机理猜测
- #1460：整段「疑似机理（待验证）」+「备选假设」，虽标了「待验证」但锚定效应仍在

## 修改内容

### 1. SYSTEM.md R2 Issue 纪律（.pi/SYSTEM.md）

**改前**：「必须带具体修复方案（代码/配置/prompt/流程），不能只写「留评论跟踪」」

**改后**：「必须含案发现场（证据真实、含锚点）与影响；修复方案仅在排查后给出，未经排查的方向须显式标「假设」」

### 2. daily-health-check.md issue 产出规范（prompts/scheduled/daily-health-check.md）

**改前**：「每个 daily-review issue 必须有具体修复方案（SYSTEM.md R2）」

**改后**：案发现场强制（证据真实、含锚点）+ 方案段两态可选——「已排查结论」（附排查过程证据链）或「排查方向（假设，未验证）」（显式标置信度）；禁止无排查过程的裸方案。修复方案不是必填——写不出时标「暂不修复：<原因>」。

### 3. 每日-issue-处理.md 开工纪律（prompts/scheduled/每日-issue-处理.md）

新增一条硬规则：
「开工前独立核实案发现场：动手修前必须独立核实 issue body 中的案发现场描述是否属实（查日志/跑命令/读代码，不靠 issue 内的方案当结论）；issue body 内的方案一律视为假设，不继承不采纳，核实后自行给出修复方案」

## 设计取舍

- 不是一刀切删掉方案段：daily-review 里有些 issue 是排查结论型（排查做完了才提 issue 留跟踪），这类带方案合理。给方案段分级标注（已排查结论 vs 排查方向假设），而不是禁止。
- 处理端加独立核实条：即使 issue 里的方案是「已排查结论」，处理獭也应独立核实——排查可能有盲区，独立核实是第二道防线。
