# F20260804safe repo-safety 写前检查门

## 术语定义

| 术语 | 定义 |
|------|------|
| **写前检查门（Hard Gate）** | 在执行任何文件写入操作前，必须先验证目标文件是否在 git 版本控制中。验证通过才能进入 worktree 流程 |
| **流程跟随任务** | 当子任务涉及修改追踪文件时，无论主线任务类型，都必须将该子任务视为代码变更 |
| **任务框定偏差** | 排查类任务被框定为"只读"，修改动作被视为"顺手修正"而非代码变更 |

## 背景

### 起因：模型连接池配置对话

大獭在"模型连接池配置"对话中排查 `config.yaml.example` 时，直接修改了两个字段：
- `database.path`：修正路径格式
- `circuitBreaker.maxChainDepth`：修正配置值

这两个修改绕过了 repo-safety 的 worktree + PR 流程，直接在 main 目录执行了 edit 操作。

### 三层根因分析

| 层级 | 问题 | 具体表现 |
|------|------|----------|
| **L1 任务框定** | 排查任务被框定为"只读" | 大獭将排查中的修改视为"顺手小修正"，不认为是代码变更 |
| **L2 指示模糊** | SKILL.md 红线 #5 只覆盖"自检修正" | 红线 #5 说的是"排查过程中发现自己的推理或工具调用有误"，没有覆盖"排查中发现的非自检问题" |
| **L3 触发缺失** | repo-safety 没有写前检查门 | 没有机制在 edit/write 前判断文件是否 git 追踪 |

### 关键观察

原 repo-safety 设计假设：修改仓库文件的意图是在进入对话时就明确的（如"改个 bug"、"提个 PR"）。

实际情况：修改意图可能在排查过程中动态产生。排查者最初没有修改意图，但发现问题后"顺手"修改——此时 repo-safety 的触发条件（看到"提交"等关键词）不匹配。

## 目标

### T1 — repo-safety 新增写前检查门

在 SKILL.md 红线区域新增第 6 条红线「写前检查门（Hard Gate）」：
- 对任何 git 追踪文件执行 edit/write 前，先验证文件是否在版本控制中
- 验证方式：`git ls-files --error-unmatch <file>`
- 如果是 git 追踪文件，必须先进入 worktree 流程
- 没有 worktree 就不动笔

### T2 — SYSTEM.md 新增流程跟随任务原则

在核心原则区域新增「流程跟随任务」：
- 当子任务涉及修改追踪文件时，无论主线任务类型，都必须走 repo-safety 流程
- 不确定时先问搭档

### T3 — 补充排查类 skill 子任务切换说明

在 repo-safety「与其他 skill 的关系」区域补充：
- 排查类 skill 在执行过程中，如果发现需要修改 git 追踪文件，应将子任务从"只读排查"切换为"代码变更"

## 设计方案

### D1 — 写前检查门（红线 #6）

**触发点**：在对任何文件执行 edit/write 操作前

**检查逻辑**：
```
对目标文件执行 git ls-files --error-unmatch <file>
├── 成功（文件在版本控制中）→ 必须进入 worktree 流程
└── 失败（文件不在版本控制中）→ 可以直接操作
```

**关键原则**：
- 没有 worktree 就不动笔
- 验证必须是主动行为，不能依赖记忆或假设

### D2 — 流程跟随任务原则

**核心思想**：流程跟随任务，而不是任务迁就流程

**决策树**：
```
子任务涉及文件修改？
├── 否 → 继续当前流程
└── 是 → 文件是 git 追踪的？
    ├── 否 → 直接修改
    └── 是 → 切换为代码变更任务，走 repo-safety 流程
```

### D3 — 排查类 skill 子任务切换

**场景**：排查类 skill（core-workflow / troubleshooting）执行中发现需要修改文件

**切换流程**：
1. 识别需要修改的文件
2. 判断文件是否 git 追踪（写前检查门）
3. 如果是，暂停排查任务
4. 切换为代码变更任务
5. 走 repo-safety 的 worktree + PR 流程
6. 完成后可继续排查任务

## 硬约束

1. 写前检查门必须在每次 edit/write 前执行，不能依赖缓存或记忆
2. 验证方式必须使用 `git ls-files --error-unmatch`，不能用其他方式
3. 流程切换必须是显式的，不能静默忽略
4. 不确定时必须问搭档，不能自行判断
