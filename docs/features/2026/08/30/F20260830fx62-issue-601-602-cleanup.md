# #601/#602 尾巴收口

## 背景

PR #598（F20260829cstd 成本/产出看板）合入后转出两个尾巴 issue：

- **#601**：rhi-scan-worker `total_commits` 用例 flaky（当时初判 14 次 1-2 失败）
- **#602**：`cache_hit_rate` 指标行成为无消费者死数据（消费端已全部改为 token 推导）

搭档 2026-08-30 12:59 指示「这两个小尾巴现在不能直接处理掉吗」→ 本 PR 收口。

## #601 定性：已被 #597 顺带修复，无需代码改动

**双向复跑实证**（2026-08-30）：

| 代码基线 | 复跑次数 | 结果 |
|---|---|---|
| main HEAD（f7e785d0，含 #597） | 55 连跑 | **全过** |
| 旧基线（56a99a20，#598 合入时） | 50 连跑 | **13 次失败（~26%）**，断言 `total_commits` 5≠6 或 chain_states regressed≠active 交替出现 |

旧基线失败断言出现**两种形态**（total_commits 少 1 / chain_states active→regressed），证实 #601 与 #594（chain-builder 秒级 author date 排序平局）**同根因**：beforeAll 5 个 commit 同秒创建，author date 平局导致排序不稳定，连带窗口内计数与链状态判定漂移。

#597（F20260829hscx）的顺手修复——夹具 `nextCommitDate()` 每个 commit 递增 1 小时唯一日期——同时治好了 #601 和 #594 的复现路径。

**处置**：#601/#594 均 close（注明被 #597 顺带修复，附双基线复跑数据）。
