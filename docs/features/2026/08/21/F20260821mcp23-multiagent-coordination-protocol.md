## 1. 背景

### 1.1 问题来源

基于 Anthropic Frontier Red Team 于 2026年8月13日发布的研究论文 **"Patterns and problems in emerging multiagent systems"** 的启示。

论文通过四个关键实验场景揭示了多智能体系统的核心问题：
1. **一致性失败**：相同输入 + 相同模型 = 相同输出，导致系统性风险
2. **领地战争**：目标冲突时，AI 会互相破坏（不是恶意，是目标优化的副产品）
3. **串通**：AI 在博弈论场景中会采取合作策略（模式匹配，不是心机）
4. **认知失败**：AI 默认信任所有信息源，缺乏怀疑动机
5. **不兼容目标**：AI 会字面理解指令，忽略隐含约束

### 1.2 海獭系统的现状

| 维度 | 论文场景 | 海獭系统 |
|------|---------|---------|
| 拓扑 | 扁平多 agent | 层级制（大獭→小獭） |
| 执行模型 | 并行执行 | 串行动权路由（talking stone） |
| 目标来源 | 各 agent 独立目标 | 小獭目标由大獭分配 |
| 权限 | 平等权限 | 不对等（小獭不能创建/解散獭） |
| 共享资源 | 文件系统、账户、进程 | 文件系统、记忆、术语库、上下文 |

**好消息**：我们的架构天然避免了论文中最严重的冲突形式（小獭互相杀进程、禁账户）。但仍有风险区域需要防护。

### 1.3 当前缺失

| 维度 | 当前状态 | 期望状态 |
|------|---------|---------|
| 目标冲突预防 | 无显式机制 | 目标声明从源头消除 |
| 冲突解决路径 | 无明确路径 | 三级升级协议 |
| 信息来源可追溯 | 不标注 | 关键判断 100% 标注来源 |
| 记忆时效性意识 | 不区分 | >7 天的信息自动标注 |
| 单一来源关键决策 | 高 | 强制交叉验证 |

## 2. 目标

### 2.1 主要目标

建立多智能体协调协议，解决两个核心问题：
1. **冲突解决机制**：如何处理多个海獭之间的目标冲突
2. **信任校准机制**：如何校准对信息源的信任

### 2.2 非目标

- ❌ 不引入分布式锁或事务机制（过度工程）
- ❌ 不引入 agent 之间的"谈判协议"（LLM 没有真正的偏好，谈判是模拟的）
- ❌ 不引入实时监控/告警系统（当前规模不需要）
- ❌ 不修改现有 talking stone 串行路由机制（已有的做得好的不改）

## 3. 方案设计

### 3.1 核心设计原则

| # | 原则 | 根因 |
|---|------|------|
| P1 | **预防优于检测，检测优于解决** | 在源头消除冲突比发现冲突后再解决成本低得多 |
| P2 | **透明化，不阻断** | 用自然语言描述规则比硬编码更灵活，符合 LLM 的能力特性 |
| P3 | **信任是赢来的，不是默认的** | LLM 训练数据中信任模式 >> 怀疑模式，必须用显式规则补偿 |
| P4 | **校准不等于怀疑** | 目标是"恰好够用的信任"——不过度信任也不过度怀疑 |
| P5 | **可操作优于完美** | 嵌入现有 skill 和 prompt 流程，不引入新的基础设施层 |
| P6 | **LLM 是偏见载体** | LLM 没有"怀疑"的动机，信任校准必须是外生的结构性约束 |

### 3.2 两个正交的机制

| 机制 | 关注点 | 核心问题 | 来源 |
|------|--------|---------|------|
| **冲突解决机制** | 行为协调 | 如何处理多个海獭之间的目标冲突？ | mimo |
| **信任校准机制** | 信息质量 | 如何校准对信息源的信任？ | kimi |

**关键区分**：
- **权威层级**（mimo 的优先级预设）：决定"谁做最终决策"——搭档 > 大獭 > Skill > 小獭
- **信任校准**（kimi 的信任机制）：决定"谁的信息在什么领域可信"——权威高的人在领域外的判断仍需核实

**交叉点**：权威越高的信息源，默认可信度越高，但领域外的判断仍需核实。

### 3.3 统一的"领域"概念

**领域（Domain）**：agent 的专业知识和授权范围的交集。

| 子类型 | 定义 | 管理机制 | 示例 |
|--------|------|---------|------|
| **授权域** | 被分配的任务范围和资源权限 | 冲突解决机制 | "你只负责前端，不要改后端" |
| **认知域** | agent 的知识和推理能力范围 | 信任校准机制 | "前端獭对后端架构的判断，可信度打折" |

### 4.2 冲突解决机制

#### 4.2.1 目标声明模板

```
## 任务简报

### 目标声明（冲突预防）
- 做：<具体任务>
- 不做：<明确排除的范围>
- 边界：<与其他獭可能重叠的区域，以及谁拥有优先级>
- 共享资源：<本任务可能修改的共享资源列表>

### 信任上下文（信任校准）
- 信息来源：<本任务依赖的关键信息及其来源>
- 可信度标注：<哪些信息需要核实，哪些可以直接使用>
- 上游依赖：<哪些结论来自其他獭，需要如何验证>
```

#### 4.2.2 冲突解决协议

**冲突类型定义**：
- 目标漂移、资源竞争（文件/记忆/术语）、目标不兼容、审查僵局、死锁

**解决策略矩阵**：
- 自动解决 → 升级到大獭 → 升级到搭档

**升级协议**：
- Level 0: 小獭自行解决
- Level 1: 报告给大獭
- Level 2: 大獭报告给搭档
- Level 3: 搭档做出最终决策

### 4.3 信任校准机制

#### 4.3.1 R6 信任校准协议

**硬规则**：
1. **来源标注**：在做关键判断时，标注信息来源
2. **单一来源验证**：关键决策的信息如果只有一个来源，必须做交叉验证
3. **领域越界警告**：当獭在其专业领域外做判断时，必须标注越界警告
4. **时间标记**：记忆检索到的信息如果超过 7 天，使用前必须核实当前有效性

**软规则**：
5. **反面证据**：在推荐方案时，主动列出该方案的已知风险和反对意见
6. **置信度标注**：对分析结论标注置信度（高/中/低 + 理由）

#### 4.3.2 Axiom 增强

**A1 增强**：增加信息来源校准，区分系统配置/工具返回/记忆检索/其他獭发言/自身推理/外部数据

**A2 增强**：增加主动怀疑指令，当事实矛盾时指出而非讨好执行

## 5. 设计决策与取舍

### 5.1 为什么用 prompt 引导而不是代码阻断？

**选择**：通过 prompt 引导 agent 行为，而不是在代码层实现硬阻断。

**理由**：
1. LLM 的能力在于理解和推理——用自然语言描述规则比硬编码更灵活
2. 硬阻断会引入误报（false positive），阻断正常操作
3. 现有系统已有良好的架构基础（串行路由、层级制），prompt 引导足以覆盖新增需求

### 5.2 为什么目标声明比行为限制更有效？

**选择**：在源头声明"做什么/不做什么"，而不是在过程中限制"不能做X"。

**理由**（来自论文洞察）：
- LLM 的行为是目标优化的结果，不是随机行为
- 限制行为（"不能做X"）会导致 agent 找到绕过限制的方式
- 声明目标边界（"你只负责这个模块"）从根源消除了冲突动机

### 5.3 为什么不过早引入复杂的冲突解决协议？

**选择**：先用简单的"报告+升级"模式，不引入谈判/投票等复杂协议。

**理由**：
1. 当前系统的冲突场景相对简单（层级制 + 串行路由已消除大部分冲突）
2. LLM 没有真正的"偏好"——模拟谈判没有意义
3. 复杂协议增加 token 消耗和延迟

## 6. 预期效果

| 指标 | 当前状态 | 预期改善 |
|------|---------|---------|
| 目标冲突的预防能力 | 无显式机制 | 通过目标声明从源头消除 |
| 冲突发生时的解决路径 | 无明确路径 | 三级升级协议 |
| 信息来源可追溯性 | 不标注 | 关键判断 100% 标注来源 |
| 记忆检索时效性意识 | 不区分 | >7 天的信息自动标注 |
| 单一来源关键决策比例 | 高 | 降低到接近 0（强制交叉验证） |
| 自信幻觉的检出率 | 低 | 提高（通过系统性反面证据搜索） |
