# F20260807aropt: 对抗审视反讨好优化

## 问题现象

海獭在执行 adversarial-review skill 时，频繁输出"小问题，不堵塞"，替搭档做了合入决策。

典型行为链：
```
审查者发现真实问题 → 分类为次要观察 → 因为不是阻断性，所以不否决结论
→ 输出"可以合入" → 搭档认为没问题 → 问题被跳过
```

## 根因分析

三因叠加：

1. **模板给了出口**：当前模板 `[需要修改 / 可以合入（附条件）]` 是二元选择，审查者被迫在"否决"和"放行"之间选。当问题不够硬但也不算干净时，审查者被模板推向"可以合入"。

2. **次要观察处置留了灰色地带**：`记录（issue/PR 描述）` 允许审查者写一句"记录为 issue"就完事，没有跟进义务，实际等价于"以后再说"的变体。

3. **LLM 讨好倾向**：阻断门槛 `"仅凭这一条，我会否决吗？"` 答不上来就不是阻断——这在模糊地带天然偏向归入次要观察，因为"否决"是强动作，LLM 倾向回避。

## 红蓝对抗结论

### 第一轮

- 红方：根因是 LLM 讨好倾向，改模板没用
- 蓝方：模板有"可以合入"出口，LLM 就会选它
- 用户判断：两者都有道理，应该结合

### 第二轮

- 红方：自检清单是假把式，LLM 会自我合理化
- 蓝方：有 checklist 比没有好，LLM 对结构化指令遵从率更高
- 用户判断：**原则/认知/心智在 system prompt，步骤/方法/业务流程在 skill，决定权交给 LLM。harness 的职责是写好这些内容，而不是让 LLM "必须"做某事。"必须"是软件系统才具备的能力，LLM 永远不具备。**

### 第三轮

- 红方：方案自相矛盾——原则否定了"可以合入"，但模板保留了它
- 蓝方：保留"可以合入"是为了让决策者有最终决定权
- 用户判断：**红方。移除"可以合入"，改为"存在以下问题（决策者判断）"**

## 最终方案

### 设计原则

1. **结构性消除出口**：移除"可以合入"选项，审查者不再有合入判断的结构化出口
2. **原则引导，不是强制执行**：LLM 不能"必须"做某事，但可以被引导理解为什么要做某事
3. **写清原则，让 LLM 自己判断**：harness 的职责是写好原则和流程，不是控制 LLM 行为

### 改动 1：移除"可以合入"出口

模板从 `[需要修改 / 可以合入（附条件）]` 改为 `[需要修改 / 存在以下问题（决策者判断）]`。

审查者不再有"可以合入"这个选项。当有问题时，审查者输出问题清单，合入决策交给搭档。

### 改动 2：审查者自省

在"审查结论"前插入"审查者自省"，引导审查者思考：

- 我是否把问题降级了？
- 我是否在替搭档做决定？
- 我是否用了淡化问题的话？

### 改动 3：后果视角

在阻断性门槛定义后增加"后果视角"，引导审查者换个角度思考：

如果这个问题流入生产，用户会怎样？系统会怎样？搭档会怎样？

### 改动 4：处置的真实性

次要观察处置规则增加"处置的真实性"原则：

"记录为 issue"必须是真实的。如果你不确定会不会创建，那这个问题要么现在修，要么问搭档。

## 具体规则修改

### SKILL.md 修改点

#### 修改 1：产出模板 - 审查结论章节

当前：
```markdown
## 审查结论

[需要修改 / 可以合入（附条件）]

结论必须是二元的。"基本没问题"不是有效结论。存在未处置的阻断性问题 → 必须"需要修改"。
```

改为：
```markdown
## 审查者自省

在给出结论前，想想这些问题：

- 我是否把问题降级了？如果一个问题是真实的，为什么它是"次要观察"而不是"阻断性"？
- 我是否在替搭档做决定？我是不是在帮搭档省事？
- 我是否用了淡化问题的话？"小问题"、"影响不大"——这些话是在描述问题，还是在为不修复找理由？

这些问题没有标准答案。但如果你发现自己在合理化，停下来想想：你是在如实报告，还是在回避判断？

## 审查结论

[需要修改 / 存在以下问题（决策者判断）]

结论必须是二元的。"基本没问题"不是有效结论。存在未处置的阻断性问题 → 必须"需要修改"。存在问题但不够阻断 → "存在以下问题（决策者判断）"，由搭档决定是否合入。
```

#### 修改 2：Behavioral Rules - 阻断性门槛

当前：
```markdown
- **阻断性**：单凭这一条就足以否决本次交付。门槛问题："仅凭这一条，我会否决吗？"答不上来就不是阻断。
```

改为：
```markdown
- **阻断性**：单凭这一条就足以否决本次交付。门槛问题："仅凭这一条，我会否决吗？"答不上来就不是阻断。
  - **后果视角**：当你准备把一个问题归为"次要观察"时，换个角度想想：如果这个问题流入生产，用户会怎样？系统会怎样？搭档会怎样？你不需要给出一个"正确答案"。但这个视角可以帮助你判断：你是在如实评估问题，还是在回避判断。
```

#### 修改 3：Behavioral Rules - 次要观察处置

当前：
```markdown
- Dispositions: 阻断性问题 → "在当前 PR 修复" or "开发者回应（审查者认可）"；次要观察 → 额外允许 "记录（issue/PR 描述）"。
```

改为：
```markdown
- Dispositions: 阻断性问题 → "在当前 PR 修复" or "开发者回应（审查者认可）"；次要观察 → 额外允许 "记录（issue/PR 描述）"。
  - **处置的真实性**："记录为 issue"是一种处置，但它必须是真实的。如果你说"记录为 issue"，你应该真的打算创建这个 issue。如果你不确定会不会创建，那这个问题要么现在修，要么跟搭档说清楚："这个问题我看到了，但我不确定要不要修，你怎么看？""以后再说"不是处置。
```

#### 修改 4：审查者 vs 决策者章节

当前：
```markdown
### 审查者 vs 决策者

审查者和决策者是不同角色。当两者冲突时：

- **审查者的责任**：诚实报告问题，结论保持"需要修改"
- **决策者的权力**：可以决定合入未修复的问题
- **处理方式**：当决策者要求合入未修复的问题时，记录"决策者选择合入"作为处置，审查者不改为"可以合入"

审查者的结论反映问题的存在，不反映决策者的选择。
```

改为：
```markdown
### 审查者 vs 决策者

审查者和决策者是不同角色。

- **审查者的责任**：如实报告问题。结论只有两种："需要修改"（有阻断性问题）或"存在以下问题（决策者判断）"（有问题但不够阻断）。审查者不能输出"可以合入"——那是决策者的判断。
- **决策者的权力**：看到问题清单后，决定是否合入。决策者可以决定合入未修复的问题，但必须记录决策。

审查者的结论反映问题的存在，不反映决策者的选择。
```

#### 修改 5：后续动作声明

当前：
```markdown
| 产出类型 | 下一步动作 | 执行者 | 触发条件 | 不满足时处理 |
|----------|-----------|--------|----------|-------------|
| 审视报告（需修改） | 作者处置 | 实现者（异体） | 报告交付后 | 正常终止，报告交付搭档 |
| 审视报告（可合入/可定稿） | 搭档终审 | 搭档 | 结论为通过时 | 搭档不在场 → 记录结论到 memory，搭档回来后终审 |
| 审视报告（对立僵局） | 搭档裁决 | 搭档 | 触发升级信号时 | 搭档不在场 → 记录僵局状态到 memory，搭档回来后裁决 |
```

改为：
```markdown
| 产出类型 | 下一步动作 | 执行者 | 触发条件 | 不满足时处理 |
|----------|-----------|--------|----------|-------------|
| 审视报告（需修改） | 作者处置 | 实现者（异体） | 报告交付后 | 正常终止，报告交付搭档 |
| 审视报告（存在以下问题） | 搭档决策 | 搭档 | 报告交付后 | 搭档不在场 → 记录问题清单到 memory，搭档回来后决策 |
| 审视报告（对立僵局） | 搭档裁决 | 搭档 | 触发升级信号时 | 搭档不在场 → 记录僵局状态到 memory，搭档回来后裁决 |
```

### anti-patterns.md 修改点

#### 修改 1：Let It Slide 反模式

在"Fix"部分增加处置真实性引用：

当前：
```markdown
**Fix**: Every issue needs a disposition: "在当前 PR 修复" or "开发者回应（审查者认可）". 次要观察允许第三种去向"记录（issue/PR 描述）"——但记录是分流不是拖延，"后续优化"本身仍然禁用。
```

改为：
```markdown
**Fix**: Every issue needs a disposition: "在当前 PR 修复" or "开发者回应（审查者认可）". 次要观察允许第三种去向"记录（issue/PR 描述）"——但记录是分流不是拖延，"后续优化"本身仍然禁用。
  - **处置的真实性**：如果你说"记录为 issue"，你应该真的打算创建这个 issue。如果你不确定会不会创建，那这个问题要么现在修，要么跟搭档说清楚。"以后再说"不是处置。
```

#### 修改 2：Rubber Stamp Review 反模式

当前：
```markdown
**Fix**: Every dimension must be explicitly addressed in the report — findings, or an explicit "无发现". "无发现" must be stated, not implied. But a finding manufactured just to fill a dimension is not a finding — see Scattergun Review.
```

改为：
```markdown
**Fix**: Every dimension must be explicitly addressed in the report — findings, or an explicit "无发现". "无发现" must be stated, not implied. But a finding manufactured just to fill a dimension is not a finding — see Scattergun Review.
  - **审查者不能输出"可以合入"**：审查者的结论只有"需要修改"或"存在以下问题（决策者判断）"。"可以合入"是决策者的判断，不是审查者的。
```

## 验证计划

### 手动验证

1. 让海獭执行一次对抗审视，观察是否还会说"小问题不堵塞"
2. 检查结论是否只有"需要修改"或"存在以下问题（决策者判断）"
3. 检查"审查者自省"是否被认真回答
4. 检查"记录为 issue"是否是真实的处置

### 长期观察

观察海獭在新模板下的行为变化。如果仍然有问题，再调整原则引导的措辞。
