# 背景

## #516：15 分钟链超时误杀长编排任务 + error 静默死亡

《每日 issue 处理》定时任务 8-24/25/26 连续三天 `Agent invocation timeout`：
scheduler 的 `CHAIN_TIMEOUT_MS = 15 分钟` 看门狗到点即 reject，但底层链还在跑——
8-26 那次链实际跑到当天 18:47 正常收尾（PR 交付 + 审视 + issue 关闭全部完成），
账面却记 failed。3 次 failed → `status=error` → 停跑，全程零通知零告警，用户看板偶遇才发现。

链引擎承载两种负载：派小獭开发（数小时）与单獭例行检查（数分钟）。15 分钟只对后者合理。

## #517：invoke 失败但 execution 记 completed

手动触发《每日 issue 处理》（execution fc368fcf）现场：预重启 lock 超时 +
invoke `Lock acquire timeout`（消息 seq 263 status=failed），但 execution 记 **completed**（60 秒）。

吞错路径：orchestrator `failTerminal`/`abortTerminal` 把消息置 failed 后**正常返回 TurnResult**
（不抛错）→ 链引擎 `Promise.allSettled` 消化 rejection 只 log → `executeChain` 正常 resolve →
scheduler 看到正常 resolve → 记 completed。agent 侧的 failed 状态没有传递回 execution status。

后果：execution 表不可信 + 熔断保护（3 次失败置 error）被绕过——如果发生在 cron 循环里，
一个真挂的任务会永远记 completed 且无人知晓。

# 设计

## #516-a：任务级超时配置（timeoutMinutes）

- **数据模型**：`scheduled_tasks` 加 `timeout_minutes INTEGER` 列（nullable，迁移幂等）。
  `ScheduledTask` 实体加 `timeoutMinutes: number | null`，null = 用调度器默认。
- **校验**：实体层 `isValidTimeoutMinutes`（整数 1-1440，即 1 分钟到 24 小时）；
  create/update 走同一校验函数，update 传 null 清除配置回默认。
- **全链路透传**：HTTP DTO / controller / agent tool（`create_scheduled_task` 加
  `timeoutMinutes` 参数，工具描述引导长编排任务设 240）/ web 前端类型 + 任务卡标签
  「链超时 N 分钟」。

## #516-b：超时语义从「一刀切墙钟」改为「静默容忍窗 + 硬上限」

`watchChainWithActivity`（链路径专属，非链降级路径保留旧 5 分钟一刀切）：

1. 与链 promise 竞速：链 settle（成功/失败）→ 透传返回/抛错。短任务不被拖到静默窗满。
2. 静默窗（默认 15 分钟，`timeoutMinutes` 可覆盖）到 → 探测锚点消息（触发时的系统消息）
   之后是否有新消息（streaming/speaking/completed/failed/aborted **任一状态**都算活跃）：
   - 有 → 链活跃，续期等待下一个静默窗口（8-26 现场跑了 16 小时的链不再被误杀）
   - 无（含探测失败）→ 再查链是否恰好 settle（探测是 async 的，探测空隙内链可能已结束——
     含消息写入失败的 DB 异常路径）：已 settle 且成功 → 透传成功；已 settle 且失败 → 原样上抛；
     未 settle → 判死，抛 `Agent invocation timeout`
3. 总时长恒受 24h 硬上限约束（防真死循环占住调度器），超限抛显式错误信息。

探测失败判死的理由：链消息流不可读（DB 故障等）时链产出无从验证，继续等待只会永远占位。

## #516-c：error 状态落通知（消灭静默死亡）

`notifyTaskErrored`（best-effort，通知失败不阻塞状态变更）：

1. 任务所属对话注入系统消息 `[定时任务错误] 「任务名」连续 N 次执行失败，已自动停跑…`
2. 写 healing event（errorType=`performance`、severity=`high`、context 含 taskId 与最近错误），
   进入 self-healing 定期分析视野。

触发点：`handleExecutionFailure` 连续失败 ≥3 置 error 时；`triggerOnceWithRetry` 重试耗尽置
error 时（once 任务同样不静默）。

## #517：execution 落库前记账校验

`assertNoFailedMessages`（链/非链两路径统一）：`completeExecution` 前查锚点消息之后的消息，
存在 `senderType='otter' && status='failed'` 的消息 → 抛错走 `handleExecutionFailure`，
execution 记 failed（含失败消息预览），不再盲目记 completed。
消息拉取按 100 条/页分页推进（游标=末条消息 id），不受单页上限漏检深层失败（对抗审视发现 2）。

判定信号源说明（任务简报关注点）：失败信号以**最终消息状态**为准——`agent 调用抛错`
路径（invoke reject）本来就记 failed，本修复补的是「链跑了但消息终态 failed」的吞错路径。
「链跑了但熔断」（circuit break 自动重启后成功收尾）消息终态为 completed，不受影响。

Why 锚点之后：同一会话旧轮次的 failed 消息（已熔断/已人工处理）不应牵连本次执行。
Why 只看 otter 消息：failed 的发出者必为执行链上的獭；用户消息不存在 failed 生命周期。
Why best-effort：查询抛错/返回异常值不阻塞记账（校验失败视为通过，交给既有 failure 路径兜底）。

# 影响范围

- 兼容性：`timeout_minutes` nullable，旧任务行为不变（15 分钟静默窗默认）。旧库自动迁移。
- 行为变化：链超时不再 15 分钟一刀切——静默 15 分钟才判死（长链活跃时不再误杀）；
  非链降级路径保留 5 分钟一刀切。
- 不做（任务边界）：不动 RHI 面板、不动 lock 机制（#423 lock timeout 家族另行处理）、
  不改 heal 面板。
