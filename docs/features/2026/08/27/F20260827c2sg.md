# 獭间信号 C2：signal-parser + resolve_signal

**父方案**：[F20260826mwrd](../26/F20260826mwrd.md) Part 2（signal-parser 与 `<signal>` 通道 + 裁决写路径）。C1 已交付 halt 投递管道（[F20260826sgpa](../26/F20260826sgpa.md)），本期补齐 objection/blocked 的完整闭环：小獭发信号 → 台账落 pending → 大獭 resolve_signal 裁决 → resolved/dismissed 留痕。

## 交付内容

| 层 | 文件 | 内容 |
|---|---|---|
| parser | `src/usecases/signal/signal-report-parser.ts`（新） | `<signal type severity>` 块抽取：tokenizer + 栈式配对（顶层块为落账候选，嵌套块是外层 payload 的一部分不冒名落账）、normalize（转义/反引号/全角引号）、属性逐项校验（顺序无关）、白名单（type 仅 objection/blocked——halt 只能经 halt_otter 工具，伪造不可入台账）、payload ≤1000 截断、每消息 ≤5 块、畸形块静默剥离、parse/strip 共享同一配对结果（结构上不同步不可能） |
| 拦截 | `signal-tools.ts` `interceptSignalReport` | speak 入口（tool-factory createSpeakTool 内，healing 拦截之后）：剥离 + fire-and-forget 落账 pending，落库失败不阻断发言 |
| 裁决 | `signal-tools.ts` `createResolveSignalTool` | big 专用：signalId（支持短 ID 前缀，只搜 pending）+ status（resolved/dismissed）+ resolution（必填——空裁决等于没裁决）；存在性/跨对话/幂等三重校验（checkResolvable）；状态迁移以本工具为唯一数据源 |
| 接线 | `tool-factory.ts` / `session-helpers.ts` / `config/tool-manifest.json` | resolve_signal/halt_otter 归入 orchestration block（仅 big 引用）；small 型不含（裁决权在大獭）；fallback 列表同步；白名单测试覆盖 manifest 生产路径与 fallback 双面 |

## 与方案的偏差

| 偏差 | 理由 |
|---|---|
| 锚点样式校验未做（方案说「parser 校验 payload 非空且含锚点样式」） | payload 含锚点与否属语义判断（F 文档 ID/file:line 的形态千变万化），正则白名单会误杀合法异议。降级为 prompt 层义务（C4 SMALL_OTTER.md 写明「异议必须含文档锚点或 file:line，空泛异议程序无效」）+ 每日对账统计异常异议率（C4）。**改了让系统变好还是变更差**：把语义判断放 parser 是伪精确，放 prompt+对账是可运营的 |
| UI 徽章渲染不在本期 | 方案 Part 5 归 C4（prompt+UI 同期），本期只把数据面备齐（signal_events 已有 status/resolution 字段，徽章数据源就绪） |

## 审视决策史（检视獭-513 对抗审视，kimi 异模型）

| 发现 | 处置 | 决策理由 |
|---|---|---|
| 🔴 严重：manifest system block 引入 halt_otter/resolve_signal → small 生产白名单泄漏（loader groups 并集语义；测试未传 projectRoot 走 fallback，断言面与生产面不同构） | 新建 orchestration block 隔离两工具（small 的 groups 不含它）；测试补 manifest 生产路径断言 | 接受。探针实证成立；「裁决权在大獭」是本期核心安全边界，隔离失效 = 权限提升回归 |
| 🟡 建议：未闭合块跨块吞噬后续合法块（非贪婪匹配吃到内层闭合标签），合法信号以错误类型落账 | 首轮正则加嵌套守卫后被发现 4 打回（粒度过粗，payload 含 `<signal` 字样的合法块被误丢/反引号示例冒名落账），最终重写为 tokenizer + 栈式配对 | 接受且升级。正则三件套表达不了「标签平衡配对」语义，换数据结构解决而非继续打正则补丁 |
| 🟡 建议：属性顺序颠倒（severity 在 type 前）整块静默剥离，信号无声丢失 | 属性逐项匹配（TYPE_ATTR_RE/SEVERITY_ATTR_RE 独立于块匹配，顺序无关） | 接受。LLM 高频合法变体；两种顺序语义等价，不容忍等于随机丢信号断问责链 |
| 🔴 严重（第二轮新增，发现 4）：嵌套守卫粒度过粗——payload 含未闭合 `<signal` 字样的合法块整块丢失（初版可正常落账，回归）；反引号包裹的完整示例经 normalize 剥反引号后，内层以真实信号身份冒名落账且 strip 残留 `</signal>`（parse/strip 不同步） | 重写：tokenizeSignals + pairSignalBlocks（栈式配对）+ topLevelBlocks（嵌套归外层 payload）；开标签属性段排除 `<`（防 payload 裸字样吞闭合标签）；parse/strip 共享同一配对结果；探针场景 A/B 固化为单测 | 接受。两个探针实证成立；首轮处置的正则补丁被检视打回，验证了 tokenizer 方案的正调性 |

焦点 3（resolve 幂等误读面，C1 检视预告）检视结论为已闭环：幂等返回三段式（已是 X + 无需重复裁决 + 原处置回显），与真裁决成功的 `[裁决完成]` 形态可区分，误读面未换位置。
