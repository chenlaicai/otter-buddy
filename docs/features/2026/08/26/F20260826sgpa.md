## 关键设计决策（实现期）

1. **注入点实现在 model-runtime-registry 而非新文件**：`otter-hooks` 内联扩展（DefaultResourceLoader 的 extensionFactories）已有 context/before_agent_start/tool_result 三个 handler，tool_call handler 加在同一工厂——方案文档说「pi-session-factory 零命中，接线是 C1 主要工作量」，实际接线点已存在（检视獭-492 当时的源码验证也已确认 SDK 能力面），本 PR 是在既有管道上扩展，工程量远小于预期。
2. **block 消费语义（SDK 事实）**：`agent-loop.js` 对 `ToolCallEventResult.block=true` 生成 `createErrorToolResult(reason)` 作为 error tool result 返回 LLM——halt 指令以「工具执行失败+理由」的形态进入目标獭上下文。这决定 block reason 文本必须自带全部行为指令（已写入 halt-block-reason.ts）。
3. **同 invoke 持续 block**：takeForBlock 首次消费后指令进 active，同 invoke 余下生命周期所有工具调用继续被 block——防 LLM 无视第一次 block 换个工具继续干。endInvoke 在 session dispose（finally 块）清理，改派后的新 invoke 干净起步。
4. **fail-open**：ALS store 读不到（理论上不发生，防御性）→ 放行。理由：halt 是协作增强不是安全机制，误伤正常工具流的代价 > 漏一次 halt（大獭可重发）。
5. **落账状态机**：halt_otter 打标时落 pending；首次注入时（onHaltFirstBlock）迁移 resolved（resolvedBy=system）。halt 无待裁决事项，resolved 即「指令已到达」的审计事实。幂等防重：repo.resolve 只允许 pending→resolved/dismissed 单向迁移。
6. **halt_otter 仅 big 型**：whitelist 控制（manifest big=`*` 自动含；small 显式排除）。small 型有 query_signals（复盘自己被停的记录）。
7. **参数传递**：signalRepo 挂 ToolContext（`ctx.signalRepo`）而非 createTools 第 6 参——max-params 约束 + repo 本就是 invoke 级注入物。

## 与方案的偏差

| 偏差 | 理由 |
|---|---|
| ExtensionRunner 接线未新建（方案预期「主要工作量」） | 接线点已存在于 model-runtime-registry 的 otter-hooks——方案基于检视獭-492 对 pi-session-factory 的检索（字面准确但漏了 model-runtime-registry），实现时补正事实 |
| signal_events 增 `target_otter_id` 列 | halt 的「谁停了谁」是一等查询维度（UI 徽章 + 大獭复盘）；objection/blocked 留 null |
| halt 状态用 resolved 而非 completed | 复用三态枚举避免 C2 状态机分叉；语义注释在实体文件 |
| 注入义务 3 从「用 yield 交回」改为「报告后停止即交回」+ speak 豁免 | 对抗审视发现 1：持续 block 场景下 yield 字面不可执行；且义务 2 的「一次 speak 输出」同样被全工具 block 封死。处置 = guard 加 speak 豁免（toolName 来自 SDK tool_call 事件）+ 文本改写为与机制事实一致 |

## 审视决策史

### 检视獭-498 对抗审视（3 建议发现）

| 发现 | 处置 | 说明 |
|---|---|---|
| 1. 注入文本「用 yield 交回」在 yield/speak 被 block 场景不可执行 | 接受并深化 | 复核时发现更深一层：义务 2「一次 speak 输出」同样不可执行（guard 全工具 block）。处置：guard 增加 speak 豁免（不消费 pending，下一个非 speak 边界注入，落账时序不变）+ 注入文本改写（停止即交回、speak 是唯一豁免工具） |
| 2. haltToolCallGuard 在 frameworks 层、usecases 测试反向 import（依赖倒挂） | 反驳 | frameworks→usecases import 是仓库既有允许方向（model-runtime-registry 先例，greeting-gateway 等 frameworks 文件均 import usecases 模块）；guard 依赖 OtterInvokeContext（frameworks 类型）与 otterInvokeStorage（frameworks 装配层），下沉反而引入 usecases→frameworks 反向依赖。usecases 测试 import frameworks 遵循同向原则 |
| 3. 文档 1713 vs PR 1720、实体注释 resolvedBy 口径 | 接受并修订 | 文档改 1720（含 28 新增）；实体注释改 resolvedBy=system |
