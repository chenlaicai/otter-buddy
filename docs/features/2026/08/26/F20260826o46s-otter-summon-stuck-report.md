# issue #466 诊断与 Prompt 兜底

## 背景

issue #466（daily-review，2026-08-26 生成）：用户 25 分钟内两次手动干预小獭异常——07:19:59 UTC 强制中断（「经过 14 次工具调用后，chen强制中断了当前发言」），07:46:33 UTC 指挥「@大獭 这个mimo好像有问题，你要不解散下然后重新拉一个进来？」。issue 标注两次干预是否同一只 mimo、同一异常「未确认」。修复三层：诊断先行 → Prompt 兜底（本 PR 主体）→ 防护评估。

## 诊断方法与数据源

复用 issue #424 已验证的方法：pi session jsonl 是唯一保存完整输出与工具调用序列的事实源（`data/sessions/*.jsonl`）。时区：memory/DB 均为 UTC。定位路径：

1. `message_segments` 表反查两条消息 body → 关联 `messages` 表取 sender_id / sender_name / created_at
2. `agent_sessions` 表 otter_id → session_file 映射
3. 逐行解析 session jsonl，按时间窗（07:10–07:50 UTC）提取 `toolCall`/`tool_use` 事件序列

## 诊断结论：两次干预分属两只獭、两种异常形态

### 干预 1（07:19:59 UTC，强制中断，14 次工具调用）

- **肇事者**：`kimi-coder`（otter_id `d997e72a-...`，**不是 mimo**）
- **证据**：`messages` 表 07:16:09 一条 `kimi-coder` status=aborted；`message_segments` body 恰为「[chen中断] 经过 14 次工具调用后，chen强制中断了当前发言。」
- **异常形态**：**超长任务无中间汇报**。session `2026-08-25T06-18-24`（kimi-coding）07:09–07:18 时段还原：10 次 bash（sed/grep 侦察真实 DOM 与色值）→ 1 次 `get_html_card_contract` → 07:17:29 `write` 卡 1（5115B 超 4KB 上限）→ 07:18:00 `write` 卡 2 → 07:18:09 / 07:18:32 / 07:18:48 连续三次 bash 压缩重写（仍超限）→ 07:19:59 被用户中断。14 次工具调用零次 `speak`——用户盯着「正在工作」10 分钟，看不到任何中间产出。
- **性质判定**：非死循环（每次工具调用参数不同、目标合理），是「任务复杂（单卡 ≤4KB 约束 + 两张卡）+ 无中间汇报」的可预见卡住。A2「卡住时停下来报告困境」原则在小獭 systemPrompt 中缺位是促因之一。

### 干预 2（07:46:33 UTC，「这个 mimo 好像有问题」）

- **肇事者**：`mimo`（otter_id `ee033b4b-...`），07:44 大獭刚派工做 PR-1 海獭身份证实现（消息 `ab86254c`）
- **证据**：`messages` 表 07:41:30 `mimo` status=aborted，`message_segments` body 为「[系统保护] 生成过程超时，已自动中断。」；接替者 `mimo2` 07:47:04 亦 aborted（同样系统保护超时），其 segment 1 自述「前一只 mimo 超时是因为生成太长被系统杀了」。
- **异常形态**：**单次生成超长被系统超时保护中断**，与工具调用循环无关。
- **性质判定**：生成篇幅失控（一次性产出过长实现方案），系统已有超时保护兜底；与干预 1 是不同根因。

### 时间线旁证修正

issue 推测「07:55 mimo 交付 PR #450」有误：实际 PR-1（PR #450）由 `mimo-面板工程师`（`d7d3b69d-...`，session `2026-08-25T07-05-40`）于 07:44:05 交付——这是更早派工的另一只 mimo，07:10 已交付面板方案报告，07:16 交付 Delta 复核，工具调用克制（07:10–07:20 仅 11 次）且每次都有 speak。它**不是**被干预的獭。

## 防护评估（仅评估，不在本 PR 实现）

两次干预暴露的防护缺口不同：

- **干预 1 型（工具调用无汇报）**：现有退化检测盯「输出重复」，OutputGuard/熔断盯「流式输出形态」，均不盯「工具调用次数 vs speak 汇报」这一维度。建议评估**工具调用预算告警**：连续 N 次工具调用无 speak 时，系统向编排獭（大獭）发提醒（不是中断——中断权留给獭/用户），让编排者主动介入。触发阈值可参考本次实测：kimi-coder 中断前 14 次，正常干活獭（mimo-面板工程师）同窗口 11 次但带 3 次 speak——「无 speak」是关键限定词，单纯计数会误伤正常长任务。落地位置候选：agent-invoker 层（能看到工具调用与 speak 流）或 dispatch-chain-engine。建议立独立 issue，与 #464（dissolve 误报）同属「小獭行为可观测性」主题可并期做。
- **干预 2 型（生成超时）**：系统已有超时保护中断，但中断后用户看到的只是「好像有问题」，无诊断信息。可评估在超时保护中断时向编排獭附带一句原因（超时/熔断/手动），成本低于预算告警，可与预算告警同一 issue 评估。

## 方案设计（本 PR 主体：Prompt 兜底）

**目标**：把 SYSTEM.md A2「卡住时停下来报告困境，不要继续无意义的工具调用空转」从全局原则下沉为 otter-summon 小獭任务模板的显式字段，让每只新召唤的小獭在 systemPrompt 层面就收到「无结论要主动汇报」的指令。

**改动**（`.pi/skills/otter-summon/SKILL.md` 步骤 2 写 systemPrompt 模板，单点一句话）：

```
你的任务：[一句话]
背景信息：[相关上下文、已有结论、约束条件]
特性文档：[路径，如存在]
预期产出：[格式]
完成标准：[什么算做完]
卡住汇报：连续多次工具调用仍无结论时，主动 speak 汇报当前困境与卡点，不要继续空转（#466：用户曾因等不到结论被迫强制中断）
```

**取舍**：
- 放在基础模板而非「任务简报模板」——基础模板是每次召唤必填，简报模板是复杂任务附加；卡住汇报应默认生效。
- 不写死 N 的数值——「连续多次」留给小獭按任务体量自判；写死数值会和大獭编排的任务复杂度脱节，且本 PR 定位是低成本兜底，精确阈值属于防护告警（代码层）的职责。
- 不重构整个 skill——issue 明确要求「改动保持克制，一两句话」。
