# 补丁抵抗双层机制：修改场景存在性对抗 + 每日全局回看

## 背景

搭档原话（意图锚）：

> 我发现一个问题，llm发现问题，然后会解决问题，但这个解决方式，不是去找到根因，然后去修复好，而是倾向于加一层额外的加固旁路，当出现xxx问题然后就能xxx兜底。然后反反复复，导致架构变得臃肿、复杂，问题也更多，然后再补，变成恶性循环了。

> 局部的正确组成了全局的错误。

> 协作流程中，应该加入一个海獭，不做别的，只对抗，站在全局视角去对抗本次特性是否是有问题的、设计是否合理，作为减法在场者，对抗现场的产物（应该包括pr和提的issue以及别的东西）

> 新增一个定时任务，每日检视前一天的特性（包括已合入的pr、提的issue，当然这里要区分清晰，可能涉及多个仓库）

> 这个对抗应该是所有需要修改的场景都应该有这么一个獭，你不要只局限在新特性开发 这个场景

> 不要每周，要每日，并且就应该是独立一个对话。因为每日issue处理只处理issue啊，但我上面说了的，这个还有对昨天一天的所有对话、产物的对抗检视

## 案例与分析脉络

本特性是 F20260907cmpx（机制预算）的直接延伸。9/7 已收敛五条通用根因并落三层解法（方案层四问/排查层修法排序/审视层软维度），覆盖**事前**与**事中**。9/8 搭档进一步反思，大獭补三层分析：

**行为层五个不对称**（为什么打补丁是 LLM 的引力中心）：
1. 目标函数局部性——LLM 奖励信号里没有"全局"这个变量
2. 加/删验证成本不对称——证否（无依赖）比证存贵一个数量级，LLM 回避验证不了的事
3. 对既有机制的本能顺从——缺"质疑存在合法性"的授权感，默认保留+包裹
4. 问题框架锁死解空间——找到的是症状的根因，不是系统易感性的根因
5. 根因常在上下文视野外

**系统层**：这是系统思考 Shifting the Burden 原型——症状解侵蚀治本能力（每次补丁成功训练系统"不用深挖" + 每个补丁使下次治本更贵），治本能力单调递减是结构不干预时的必然收敛态。

**认识层**：一切抵抗手段本质是"把全局信息压缩进局部决策点的装置"。prompt 层手段（四问/排序/维度）是低保真压缩器；度量、测试基础设施、减法在场者是高保真手段。

**掘根对抗评估的理论修正（本特性沉淀）**：
- **根因⑥升格**：抵抗手段本身服从生成回路（根因①在 meta 层的复现）——四问退化为模板填空、审视维度退化为橡皮图章、对抗角色退化为仪式。F20260907cmpx 把"仪式化退化"当风险，应升格为根因
- **认识层补判定标准**：压缩器保真度取决于**不可预测性**——固定清单可被迎合，随机追问深度才有真阻力

**掘根对提案的两轮评估要点**：
- 一轮否决提案 1（专职对抗獭）——理由：上下文装不下演化史、每单必反存在危机、牙齿与阻塞矛盾；二轮撤回否决——搭档扩展触发到"所有修改场景"解决覆盖问题，轮换制消解存在危机，分级制缓解阻塞
- 提案 2 处置通道：搭档坚持"每日 + 独立对话 + 全量产物 + 搭档晨间视野"，优于"标签进 issue 流"
- **校验关系洞察（本轮最有价值）**：两提案互为效果度量——提案 1 的 commit 声明是提案 2 的验证输入；提案 2 发现的补丁模式反哺提案 1 的分级阈值。不需要额外度量机制
- **自检悖论修正**：轻对抗从"自检"改"声明"——让正在打补丁的 LLM 自检等于没检；声明进 git 记录可审计

## 目标

- T1: 一切修改场景（不限新特性）按分级插入存在性对抗——重对抗召轮换检视獭，轻对抗 commit 声明
- T2: 每日独立对话全量回看昨日产物，产出严重度排序的补丁清单进搭档晨间视野
- T3: 两机制互为效果度量，退役条件内建（防自身仪式化，对治根因⑥）
- T4: 理论修正沉淀（根因⑥升格 + 不可预测性标准），供后续机制设计引用

## 非目标

- ❌ 不建专职对抗獭角色（轮换制替代，消解存在危机）
- ❌ 不建回归测试套件（掘根指出的"终极减法在场者"，是平行工程线，单独立项论证，不挡本特性）
- ❌ 不扫全量对话原文（信号级提取替代，上下文窗口约束）
- ❌ 不动 SYSTEM.md 全局纪律（本机制属流程层）
- ❌ 不追溯改造存量 commit/PR（声明格式只约束新提交）
- ❌ 多仓库扩展首期不做——先限定 otter-buddy 主仓（含 web/ 子目录），跑熟后评估扩展

## 方案设计

### 1. 提案 1：修改场景的存在性对抗（实时防线）

**触发条件**：任何将要修改 git 追踪文件的决策点——新特性（requirement-analysis）、bug 修复（troubleshooting）、issue 处理（daily-review 定时任务）、配置/文档改动（worktree-isolation）全覆盖。

**分级触发**（修法排序→Modification-Class 显式映射）：

| 修法排序（troubleshooting 步骤 2） | 对抗级别 | Modification-Class 声明值 |
|---|---|---|
| ④ 新增机制 | **重对抗** | `mechanism-addition`（重对抗通过后 commit 声明） |
| ① 既有语义内修 | 轻对抗 | `narrow-fix` |
| ② 收窄管辖 | 轻对抗 | `scope-reduction` |
| ③ 删除机制 | 轻对抗 | `deletion` |
| 纯文档/配置微调（不经修法排序） | 轻对抗 | `docs-config` |

| 级别 | 动作 |
|------|------|
| **重对抗** | 召检视獭（轮换、无固定身份、异模型），问"这个修改在系统演化史中是治本还是治标"；方案落盘/动手前必须过（门控判定见下） |
| **轻对抗** | 不召獭，但 commit message 必须含 Modification-Class 声明行（见下） |

**重对抗的审查问题**（扩展自审视维度 #7，时机从 PR 后前移到决策前）：
- 这个修改在系统演化史中是治本还是治标？（要求检视獭 search_memory 查相关机制演化脉络）
- 若新增机制：四问答案是否在位？③后续机制预测了什么？
- 若修复：为什么修法排序①②③不够，必须选④？

**重对抗门控判定**：检视獭审查后出具三种结论之一——`确认治本` / `疑似治标（附理由）` / `信息不足（附缺口说明）`。实现獭仅持 `确认治本` 方可继续；`疑似治标` → 暂停呈搭档裁决；`信息不足` → 检视獭须将"我审不了"本身作为结论呈搭档，禁止硬给质量可疑的答案（承认审不了比假装审了更有价值，本身即对根因⑥的抵抗），搭档裁决：补充信息后重审 / 基于已有信息自行决定继续或中止。

**轻对抗声明格式**（commit message body 追加一行，进 git 记录可审计）：

```
Modification-Class: narrow-fix | scope-reduction | deletion | docs-config | mechanism-addition
```

声明是提案 2 的验证输入——每日回看发现"声明非 mechanism-addition 但实际 diff 加了机制"= 最硬的补丁证据（🔴 高严重度）。

**分级标准复用**：troubleshooting 修法排序（步骤 2）已要求獭做①②③④分类判断，轻/重对抗只是在该判断上映射动作，零新增分类负担。

**插入点（按 skill，映射跨 skill 内联）**：
- `troubleshooting/SKILL.md` 步骤 2 修法排序后：选④ → 重对抗门（含门控判定）；选①②③ → 提示后续 commit 声明对应值（①→narrow-fix / ②→scope-reduction / ③→deletion），声明细则见 worktree-isolation
- `requirement-analysis/SKILL.md` 步骤 6 四问后：净新增机制 → 重对抗门（四问答案是审查材料；通过后在设计取舍留痕门控结论）
- `worktree-isolation/SKILL.md` 步骤 4 提交前：commit 必含 Modification-Class 声明行，取值与修法排序的对应表内联（同上表）
- `code-implementation/references/commit-convention.md`：声明行入提交模板，附取值说明

**轮换制**：重对抗执行者 = 当次任务的检视獭（code-implementation 步骤 10 已有），无固定身份——消解掘根指出的"每单必反"存在危机。模型分配沿用 otter-summon 异模型规则。

### 2. 提案 2：每日全局回看（事后防线）

**形式**：每日定时任务（早 8:00 Asia/Shanghai），独立对话执行（create_scheduled_task 触发，不污染任何工作对话上下文）。

**输入（信号级提取，非全量原文）**：
- 昨日所有 PR diff + commit message（`gh pr list --search "merged:YYYY-MM-DD"` + `git log`）——验证 Modification-Class 声明是否属实
- 昨日创建/修改的 issue（`gh issue list --search "created:YYYY-MM-DD"`）
- 昨日对话负空间信号：search_memory 检索含"砍"/"不做"/"太复杂"/"回到"/"兜底"/"加固"的消息 + 修法排序选②③的 case——"差点加了什么"最暴露补丁冲动

**产出：昨日补丁清单**（speak 到独立对话 + create_linked_resource 存档），每条附证据（PR 链接/对话引用/issue 号），按严重度排序：

| 严重度 | 判定标准 | 搭档动作 |
|--------|---------|---------|
| 🔴 高 | 新增机制但四问缺失（尤其退役条件）；或 commit 声明与实际 diff 不符 | 当天决定砍/补答 |
| 🟡 中 | 四问在位但③后续机制预测了新补丁（生成回路显形） | 本周内决定 |
| 🟢 低 | 窄修但有顺手新增痕迹 | 观察，下次触碰时决定 |

**处置通道**：搭档晨间视野——搭档是唯一全局裁决者，清单是"砍/留/观察"决策输入。不进 issue 流（避免处置通道转嫁），不产生自动动作。

**退役条件**（防自身仪式化，对治根因⑥；判据均带操作定义）：
- "实质发现" = 清单条目经搭档处置为「砍」或「补答」（搭档在条目上留非"已阅/忽略"的处置意见；搭档未审阅的条目不计入任一侧）
- "全部误报" = 搭档对当日全部条目处置为「忽略/不是补丁」
- 连续 14 天清单为空或全部误报 → 降频为每周
- 连续 30 天无实质发现 → 暂停，下次大版本重构前再启用
- 作弊检测（可观察代理指标）：搭档在清单生成前 24 小时内对机制作「砍/修改」的次数 > 当日清单实质发现数 → 差值即"提前砍"量度；该差值连续 7 天为正 → 检视獭主动在清单中报告降频建议

### 3. 两提案的校验关系（互为度量，零额外度量机制）

```
提案1 轻对抗声明 (commit) ──输入──> 提案2 每日验证
                                      │
提案1 重对抗阈值 <──反哺── 提案2 补丁模式统计
（如"选①的 case 30% 实为补丁"→ 收紧轻对抗标准）
```

### 4. 本特性自审（机制预算四问）

① **谁需要**：搭档（唯一全局裁决者，需要结构化的减法输入替代人肉察觉）；写代码的獭（需要低成本声明通道替代含糊自检）。
② **失败后果**：不落地 → 补丁叠加延续（恢复机制 10 天演化实证）；落地但仪式化 → 每日一份无人看的清单（成本 ≈ 每日几分钟扫描 + 搭档晨间扫一眼，可接受，且有退役条件兜底）。
③ **后续机制**：重对抗创造"被否决的修改"新状态 → 处置走既有决策树（修订/反驳/呈搭档），不新建流程；每日清单创造"待裁决条目"新状态 → 处置者就是搭档本人，无转嫁。两机制互为度量的设计消除了独立度量机制的需求。
④ **退役条件**：提案 2 有明确量化退役（上文）；提案 1 的重对抗——连续 20 次门控结论全部为「确认治本」且零「疑似治标」/零「信息不足」 → 降级为抽检（每 5 次抽 1 次），并在每日清单中报告该信号。

## 影响范围

- 所有走 troubleshooting 的排查：修法排序后多一步对抗分级判断
- 所有走 requirement-analysis 的方案：四问后净新增机制强制过重对抗
- 所有 commit：message 多一行 Modification-Class 声明
- 每日 8:00 新增一个独立对话的定时任务（搭档晨间多一份清单）
- 审视维度 #7（机制预算）从重对抗角度获得时机前移的执行点，维度本身不变

## 风险与约束

- **轻对抗声明流于形式**（根因⑥复现）：獭机械写 "no mechanism added"——对冲：提案 2 每日验证声明与 diff 的一致性，不一致即 🔴，声明有了被审计的压力
- **重对抗拖慢紧急修复**：事故响应时多一道门——对冲：紧急修复（P0）可先修后补审，在 commit 声明中标注 `P0-emergency (post-review pending)`，每日清单追踪补审落实
- **每日清单信号提取误报**：关键词检索粗糙（"砍"可能是闲聊）——对冲：清单条目必须附证据链接，搭档扫一眼即可判误报；误报率本身是退役条件的输入
- **检视獭上下文装不下演化史**（掘根一轮理由，仍然成立）：单次重对抗看不到完整脉络——对冲：审查问题要求 search_memory 查演化脉络；提案 2 的批量回看补全局视野（两提案互补）

## 不兼容更新

无（纯新增流程文本与定时任务，不改既有步骤语义与编号；commit 模板新增一行对旧提交无追溯）。

## 设计取舍

| 取舍 | 决策 | 替代方案 | 理由 |
|---|---|---|---|
| 对抗触发锚定 | 一切修改场景（行为本质） | 仅 requirement-analysis（skill 边界） | 搭档指正：bug 修复是补丁重灾区（五连修复全走 troubleshooting），skill 边界会漏主入口 |
| 对抗执行者 | 轮换检视獭 | 专职对抗獭 | 掘根：固定身份→"每单必反"存在危机→目标替代；轮换制无身份需捍卫 |
| 轻对抗形式 | commit 声明（可审计） | 提交前自检（不可观测） | 掘根自检悖论：能让 LLM 可靠自检打补丁，问题根本不会存在；声明进 git 可被提案 2 验证 |
| 每日回看产出通道 | 搭档晨间视野 | 标签进 issue 流 | 处置者必须是有全局视野的人；issue 流无根治能力，只是延后 |
| 回看频率 | 每日 | 每周 | 搭档决策：补丁显形最快时间窗，且要看昨日全量产物（不只是 issue） |
