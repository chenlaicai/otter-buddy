## 两遗留问题修复

### 修复1：scripts/otter-buddy.sh 端口口径对齐 loadConfig（修法① narrow-fix）

- **根因**：脚本第 7 行 `PORT="${PORT:-3000}"` 写死，健康检查（:96）与端口预检（:43）查错端口；服务监听端口唯一裁决者是 `config/config.yaml` 的 `server.port`（config-service.ts:609 applyDefaults `server: { port: d(raw.server?.port, 3000) }`）。
- **修法**：新增 `resolve_config_port()` 解析 config.yaml 的 `server.port`（grep 首个 `port:` 数字行），端口优先级：`-p/--port` 显式参数 > `PORT` env > config.yaml > 3000。usage 文本同步更新。
- **决策树**：① narrow-fix ✔（只改端口推导，不动健康检查逻辑）；② 无需加开关——config 不存在时回落 3000 与原行为一致；③ 不改默认值——3000 仍是缺省。

### 修复2：app.ts patrolWorker.start 移到 initAgentAndScheduler 之后（修法① narrow-fix）

- **根因**：`patrolWorker.start()` 原在 L265（schedulerService 声明于 L327 的 TDZ 期内），PatrolWorker.start 立即同步跑首轮 tick，'scheduler-reconcile' duty 闭包执行 `schedulerService.reconcileMissedWindowsNow()` → `ReferenceError: Cannot access 'schedulerService' before initialization`（dist/src/app.js:141:68，9/30 09:33 启动日志实证）。
- **修法**：构造保持原位（duty 闭包延迟绑定），`start()` 移到 `agentInvokerRef.current = agentInvoker` 之后（schedulerService 已初始化）；dispose 路径加 `patrolWorkerStarted` 标志防御 startRhiWorker=false 时未 start 的 worker 被 stop。
- **决策树**：① narrow-fix ✔（只移动 start 调用位置，不动构造/duty 定义）；② 无需开关；③ 不改变 tick 语义（首轮仍在启动后立即跑，只是时序合法化）。
- **备选方案否决**：「首轮 tick 延迟」会改变运行时对账时效语义（#823 要求启动即对账），且延迟时长拍脑袋，不如顺序调整干净。

## Discovered Issues（不在本 PR 修复，是否立项由搭档决定）

1. **config 写保护/审计**：主仓 config.yaml 可被任何 cwd=主仓的会话随手改写（本次是搭档自己，下次可能是小獭）。建议方向：写保护开关或写入审计日志（谁、何时、改了什么）。

3. **alpha.sh 与手工验证实例互检**：本次 77757 手工拉起 3102 与 alpha.sh 的 hash 端口段（3178）脱节，建议 alpha.sh start 前扫描 3100-3198 占用情况并告警，或在 `.otter-alpha.json` 登记手工实例。
