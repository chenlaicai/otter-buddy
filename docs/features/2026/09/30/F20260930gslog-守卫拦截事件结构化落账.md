# bash 守卫拦截事件结构化落账

## 背景

**触发**：搭档 2026-09-30 拍板（对话「外部洞察」，决策简报卡回执 choice=go_all）三步走第①步：「拦截事件结构化」。

**问题链**（kimi 深挖分析 + 大獭补充在途事实，工作区 kimi-safety-analysis.md）：
1. 守卫拦截事件落 healing_events 时 description 自由文本拼接、context 仅 `{layer:"framework"}`——无规则 ID、无落点信息（pi-session-factory.ts:787 现状）
2. 直接后果：#1207（cd worktree 后写命令被误判主仓写，9/25 单日 14 条）的关闭验证只能人工翻台账数数；「哪条规则误报最多」问不出来——误报治理只能靠獭吐槽一次修一次
3. 结构性根因：Anthropic 安全公告（2026-09-30 四篇）的治理范式——护栏好不好必须看数据；跨会话模式检测需要结构化数据基础

## 方案设计

### 设计原则：外挂分类器，不碰守卫本体

守卫 v2（F20260928grv2）判定核心正处快速演化期（#1207 修复在途 worktree guard-cwd-1207、#1240 豁免粒度待修），且守卫 reason 文案本身就是面向被拦獭的教学文本（含正道引导），不宜为分类把文案改薄。**方案：在落账侧新建外挂分类器，从 reason 首句指纹分类，守卫零改动**。

### ruleId 指纹表（reason 首句锚定）

守卫每条拦截文案首句唯一（grep 实测 2026-09-30 HEAD），以首句为分类锚：

| ruleId | 首句指纹 | 层级（宪法分层预备） | 语义 |
|---|---|---|---|
| `self_kill_literal` | 「bash 命令包含针对主进程 PID 的终止命令」 | 防自杀 | kill 字面主 PID |
| `self_kill_pidfile` | 「终止进程的命令引用了主进程 PID 文件」/「主进程 PID 文件引用」（V1/V2 双形态双指纹） | 防自杀 | 终止 PID 文件 |
| `self_kill_byname` | 「bash 命令包含按名匹配的批量终止命令（pkill/killall）」 | 防自杀 | pkill/killall |
| `self_kill_nonliteral` | 「bash 命令中终止进程的目标为变量或命令替换」 | 防自杀 | kill $VAR/$() |
| `self_kill_pipe_shell` | 「bash 命令通过管道传入 shell 执行且包含终止进程操作」 | 防自杀 | echo kill \| sh |
| `self_kill_script` | 「bash 呣令通过脚本语言执行了终止进程操作」 | 防自杀 | python -c kill |
| `self_kill_eval` | 「bash 命令使用 eval 包装了含数字参数的操作」 | 防自杀 | eval 拼接变体 |
| `self_kill_process_group` | 「信号将发送到当前进程组」 | 防自杀 | 终止进程组（V2 U1/#1169） |
| `script_file_exec` | 「从文件读取脚本执行」 | 防绕过 | bash <file> / bash file（V2 U5） |
| `self_kill_script_stop` | 「bash 命令调用的 otter-buddy.sh 解析到主仓，其 stop/restart 会终止主进程」 | 防自杀 | 脚本 stop/restart |
| `self_kill_indirect` | 「bash 命令包含 otter-buddy.sh 引用与间接调用特征」 | 防自杀 | 脚本间接调用 |
| `main_write` | 「当前 bash 工作目录在主仓（未 cd 到 worktree）」 | R1 闸门 | 主仓写 |
| `data_destructive` | 「主仓 data/」（文案带括注「运行时数据：metrics/logs/workspaces」，锚「主仓 data/」耐受括注） | R1 闸门 | data 破坏 |
| `pr_merge` | 「bash 命令包含 gh pr merge——PR 合入是搭档专属动作」 | 权限边界 | gh pr merge |
| `sleep_block` | 「裸 sleep 会让搭档看到长时间静默黑盒」（发射点已剥前缀的干净文案特征） | 习惯 | 裸 sleep |
| `unknown` | （以上皆不中） | — | 未映射（兜底） |
| `pid_missing_fallback` | checkWhenMainPidMissing 路径（V1 兜底链文案） | — | PID 缺失兜底 |

### 落账链路改造（pi-session-factory.ts buildGuardInterceptHook）

改造前 context：`{ layer: "framework" }`
改造后 context：
```ts
{
  layer: "framework",
  ruleId,                    // 上表指纹分类结果
  commandHead,               // 命令前 60 字符（脱敏对齐 #858 口径，复用 sanitizeQuotedText）
  hasWorktreePath,           // 命令文本是否含 worktree 路径特征（/worktrees/）
  ...(repeated ? { repeatedIntercept: priorCount + 1 } : {}),
}
```

**为何 commandHead 砍到 60 字符**：description 里的「命令前缀 120 字符」实测含完整路径泄露（如 worktree 全路径），context.commandHead 截短并只留判定必需特征——遵循 #858 脱敏哲学，但 description 里的命令前缀保留（供人工排查）。

**为何不做 resolve 侧 outcome 标注**：当前 batch_resolve / resolve 的 resolution.notes 是自由文本，标注「误报/真报」靠 resolutionAction 枚举不覆盖。强塞进 notes 会复刻「自由文本不可聚合」老问题。outcome 标注留给第③步（裁决摩擦）一并设计——该步会动 healing-tools.ts 参数面，与本步解耦。

### 设计取舍

- **外挂分类器 vs 守卫内嵌 ruleId**：选外挂。守卫本体正在 v2 演化（#1207 在途），内嵌会产生同文件冲突+文案教学生命周期与分类锚耦合；外挂指纹表独立演进，守卫文案改了只需指纹表跟着改一行。
- **首句指纹 vs 结构化 ruleId 从守卫返回**：守卫返回值是 string（reason），改返回结构是跨层改动（circuit-breaker-helpers/ orchestrator 全要动）。首句指纹在落账侧解决，链路零侵入。
- **存量数据**：不迁移。存量 guard_intercept 事件保持自由文本（可用 description LIKE 'bash 守卫拦截%' 查到），新事件带 ruleId——新旧共存期聚合脚本用 COALESCE 兼容。
- **机制判定（issue 驱动未经 RA 的特性必答）**：机制识别检查点逐项核对——本次未新增机制（落账字段扩展属观测性增强，拦截行为零变化）；判定结论：**未新增机制**，四问不适用（narrow-fix 级观测增强）。
- **最简实现检查**：已过——仓库已有 sanitizeQuotedText 可复用（脱敏）；指纹表 14 条为全量枚举（grep 实测首句唯一定理），无更简实现。
