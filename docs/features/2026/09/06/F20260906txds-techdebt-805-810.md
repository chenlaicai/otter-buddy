## 背景

PR #809 收尾（F20260904ldgr）时盘点出两笔「发现了、评估过、有意不修」的 tech-debt（#805、#810）；PR #812（F202609048840）收尾后又添一笔同类。搭档拍板「你处理吧」，两笔打包一个 worktree 清偿。

## 两项修复

### #805：迁移 rebuild FK 防护统一

migration.ts 里 4 个表重建函数的防御风格不一致：

| 函数 | 来源 | FK 切换 | try/finally |
|---|---|---|---|
| rebuildDispatchAttemptsSourceCheck | #792 P2 | ✓ | ✓（完整模式） |
| rebuildRestartPendingResumesStatusCheck | #812 F4 | ✓ | ✓ |
| rebuildAttachmentsKindCheck | #608 | ✓ | ✗ |
| rebuildExecutionsStatusCheck | #654 | ✗ | ✗ |

- `rebuildExecutionsStatusCheck`（scheduled_task_executions，含 3 个 FK：scheduled_tasks/messages/turns）补齐 OFF + try/finally + ON
- `rebuildAttachmentsKindCheck` 补 try/finally（原本 OFF 后若事务抛异常 foreign_keys 恢复不回来）

影响评估：极低——幂等守卫使代码路径只在很老的库升级时走到；纯防御统一，防极小概率场景（DROP 被引用父表触发 FOREIGN KEY constraint failed + 异常路径 pragma 泄漏）。

### #810：note 滑动窗口截断

#795 追加语义 + recordStart 的 prev= 全量嵌套前情，使 note 在极端 retry 场景无界膨胀（100 次 retry × 300 字符 ≈ 30KB）。保留策略（检视獭-ldgr 与作者一致推荐的滑动窗口方向）：

- `NOTE_HARD_CAP = 4096`（单行总量上限，字符）+ `NOTE_KEEP_SEGMENTS = 20`（段数窗口）双约束
- `capNote()` 纯函数：超窗/超限从最旧 `"; "` 段开始丢，近期链（含 prev= 压缩链、最近 reason）完整保留
- 截断必留标记：丢段加「…（更早 N 段已截断）」；单段无分隔符超限（脏数据）尾部硬切加「…（前段超长已截断）」——取证语义不静默
- 标记挤占上限时标记优先保留（「丢了多少」比「最早内容」重要）

**五条写路径统一收口**（读-拼-截断-写，better-sqlite3 同步单连接 + 事务包裹）：

1. `recordStart`：prev= 嵌套后截断（无界膨胀源头）
2. `recordFinish`：拼接后总量截断（不是只截新片段——旧 note 已近上限时拼新片段仍会越限，首版实现此处有缺口，自检发现后改为读-拼-截断-写）
3. `appendNote`：同上
4. `markStaleInProgressFailed`（死亡证明）：SQL 直拼改逐行事务
5. `failAllInProgressForOtter`（dissolve 销账）：同上

grep `prev=` 排查习惯不受影响：只丢最旧段，近期段完整；短链场景（回归锁用例）无标记、无行为变化。

## 取舍

- 为什么不在写入时逐条硬上限（如单段 300 字符）：会破坏 #795「完整保留前情链」的意图表达；滑动窗口把「保多久」的决策集中在 capNote 一处，语义单一
- 为什么截断在 repo 层不在展示层：台账是取证通道，落库即有界才能保证 DB 不被撑大；展示层不重复做
- 为什么 4KB/20 段：#810 讨论中的建议值；100 次短 retry 链在 20 段窗口内会丢段但有计数标记，可接受
