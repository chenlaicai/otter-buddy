# 注释 F 编号密度收敛（#1482）

## 问题

2026-10-14 搭档发现代码注释中 F 编号密度失控（单文件 102 处），大量是「S1 处置：…」形态——把对话层审视过程流水账刻进代码。排查结论：Why 注释规范只管「为什么」，从未约束编号密度；lint-prompt-anchors 只拦注入面；代码注释不在任何约束范围，惯例自由生长。

**开工核验（2026-11-02，事实更新）**：原案发现场 `src/frameworks/agent/bash-safety-guard.ts` 密度已 102→5（守卫终态重写顺带治愈，PR #1702/#1711）；全仓现存量 2875 处/436 文件，top 文件 agent-invoker.ts 188 处（抽样绝大多数为正经决策锚点）。签名初筛（处置/轮次/审视语汇）命中 97 处，逐条甄别后真流水账 64 处（含处置轮同族补剥）；初筛正则有召回缺口（同族形态漏报约 20 处，见后续观察节）——**问题仍成立但严重度显著低于 issue 立项假设**。

## 方案

### ① 收敛条款（coding-principles.md）

新增「特性编号锚点纪律」小节，核心判据：**这条注释删掉后，读者会不会丢失一个必须溯源才能理解的决策**——会，则带编号；不会，则剥。三类不带：显而易见决策、对话层过程记录（处置轮次/检视发现编号——归特性文档处置记录段，代码只留终态结论不留到达过程）、同文件同特性第 2+ 处非独立决策点引用（锚点价值在稀缺性）。

存量口径：新代码严格执行；碰旧文件顺手甄别（变更范围内必清，范围外不强制）。

**机械闸暂不建**：语义不可机械判定（「S1/S2 口径」是设计文档章节标签还是处置轮次需要人判），lint 密度告警会误伤正经锚点。先观察条款执行，写进「后续观察」。

### ② 存量甄别清理（42 变更文件 = 40 src 注释 + 条款 + 本文档；diff 64 替换行，多行注释块计 1 处）

97 处签名命中逐条人工甄别（工作区 1482-signature-hits.txt 为甄别底稿）：

- **A 类剥除（64 处，含处置轮同族补剥）**：过程标签剥离、F 编号与终态 Why 保留。例：`F20261016gwr1 修复轮（M-46f0e74d 严重 1，检视獭1519）：动态词位不弃权` → `F20261016gwr1：动态词位不弃权`（matter 编号/检视獭名/轮次是到达过程，非设计意图）；两处「attempts 归零」补终态动机（历史积压任务不该永久占用熔断计数）
- **C 类保留（33 处，误报率 34%）**：签名误报——「处置状态机」（RHI 领域词，F20260917trig 的特性本体就叫处置状态机）、「delta」（SSE 流事件/名册差分注入/遥测字段语义）、「留痕」（运行时行为描述）、「S1/S2 口径」（设计文档章节引用）、「§2/§4/§6」（特性文档章节号非轮次）。注：初版人工点数误报为「~50 处/>50%」，对抗审视 r1 机器比对（底稿×diff 内容匹配）纠正为 64/33/34%——数字以机器对账为准

### 设计取舍

- **不做全量 2875 处逐条清理**：issue 建议方向 2 原文只点名高密度文件，且抽样证明存量大部分是合规锚点；全量清理的审查成本远超边际收益，条款的「碰旧文件顺手甄别」口径让存量随正常开发逐步收敛
- **机械闸缓建而非直接建**：issue 方向 3 本就是「可选，先观察」；实测误报率 34%（97 命中里 33 处误报）意味着黑名单式强签名 lint 误伤面可控但非零，且语义判定（设计章节标签 vs 处置轮次）机械做不可靠——先观察条款执行，不急着上闸
- **A 类清理保留 F 编号本身**：编号是溯源锚点（跳特性文档看完整决策史），剥的是「到达过程」标签，不是锚点——与条款「过程归特性文档、代码留终态」一致

### 审视处置（对抗审视 r1 两轮，2026-11-02）

r1 首轮（16:58）发现同族漏检，检视獭在报告外自行补剥了 35 行（7 文件；越界动作，内容经作者逐行核验采纳——见下方边界记录）；r1 终轮（17:08）出 2 严重 + 2 建议，处置如下：

- **严重 1（甄别账目失实）已修**：初版人工点数「A~45/C~50/误报率>50%」，机器对账（底稿×diff 内容匹配）实测 64/33/34%——数字是估算非实测，且被声明为未来机械闸决策基线。已全量订正（本文档 + 条款机械闸段 + PR body），机械闸缓建结论不变但论据换真数：误报率 34% 意味着黑名单式 lint 误伤面可控但非零，缓建理由从「大面积误伤」修正为「误伤非零 + 语义判定需人判，先观察条款执行」
- **严重 2（同文件残留+口径歧义）已修**：stop-word-scanner.ts 两处「审视发现/建议 N」、platforms.ts:163/:638 同族剥除；「变更范围内必清」歧义（行级/文件级）在条款中写明：变更范围=本 PR 触碰的文件内全部同族语汇，不限 diff 行
- **建议 3（召回缺口）已修**：后续观察节写明初筛漏报面（约 20 处同族形态未入底稿），机械闸评估需同时看精度与召回
- **建议 4（「剥」字三义）已修**：口径节拆明三种操作（删整条注释/剥标签留终态/剥编号留结论），各自适用判据，防误删有价值注释
- **边界记录**：检视獭两次越界（评审过程中 commit+push 远程分支 c355126a；只读任务书下直接改 worktree 10 文件）——内容全部采纳但行为违反异体执行边界，处置：报告以终版为准、越界改动经作者逐行核验后入提交（作者承担内容责任）、越界事实记入本段留痕。经验：检视类任务书需明确「修复由作者执行」而非仅「不得改」——发现问题 temptation 顺手修的冲动需要更强的边界约束
- **首轮同族补剥内容说明**：35 行分布（payload-extract-aux 11、embedding-service 9、work-ledger-repository 5、scheduler-service 4、work-ledger-report 3、pi-session-factory 3）+ 作者补 platforms/stop-word-scanner 5 处，均为「检视獭NNNN 归属括注/对抗审视洞 N/审视建议N/round-N 轮次」形态，终态 Why 保留
