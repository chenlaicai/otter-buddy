# 部署文档纠正进程拓扑（F20261120ctopd）

## 背景

搭档拍板两条：

1. **CoLink 是独立系统，与海獭无关联**——不存在「CoLink 能力并入主中枢」这回事；
2. 当前 `colink-agent-app` 的**轻进程模式认可保留**。

而 `deploy/ecs/README.md` 里还躺着旧计划的两句话：

| 位置 | 原文 | 问题 |
| --- | --- | --- |
| 首次部署步骤 | 「过渡期保留（CoLink 对接不能断），待 CoLink 能力并入主中枢进程后退役」 | 把长期形态写成临时件，且承诺一件不会发生的事 |
| 终态进程拓扑 | 「这台机只有一个海獭系统——主中枢进程；colink-agent-app 过渡保留至能力并入」 | 同上，且与「轻进程保留」的拍板正相反 |

这类残留的价格不是排版：后来者会按它去规划「并入」，或把适配进程当成可以删掉的临时件。

## 改动清单

| # | 改动 | 锚点 |
| --- | --- | --- |
| 1 | 首次部署步骤：删掉「待并入后退役」，写清 CoLink 是独立外部系统、适配进程是长期形态 | `deploy/ecs/README.md` |
| 2 | 「终态进程拓扑」→「进程拓扑：两个 systemd unit 长期并存」，附判别口径 | 同上 |
| 3 | 新增「对外入口分工」：`app.<域名>` 是 CoLink 回调入口；中枢网页入口要另装站点与证书才存在 | 同上 |
| 4 | 验证节补「先判入口是否存在」的自检（`curl -sk -o /dev/null -w '%{http_code}'`；404/证书错时先排查站点未装或误配，不直接判成中枢进程故障） | 同上 |

## 关键取舍

1. **不写「终态」这个词**。写终态就隐含「还会变」；两个 unit 的分工是稳定事实，用「长期并存」+ 判别口径表达，谁要改就得先改口径。
2. **判别口径落在「谁对谁负责」而不是「部署在哪台机」**。同机不是临时件的理由——中枢对自己负责、CoLink 是外部平台，两边靠 HTTP 对接，所以「能力收拢」不会让适配进程消失。这句话可以直接搬去回答将来任何「这个进程能不能删」的提问。
3. **入口自检写成「先判存在」而不是「应该是 200」**。现网中枢网页入口压根没装，若文档只写「应当 200」，值班的人会去查中枢；先判站点在不在，才把「没装」和「坏了」分开。
4. **只改文档，不动部署脚本**。`deploy.sh` 的双 unit 段落本来就是对的（一次部署覆盖两段），错的是 README 里关于这两个 unit「命运」的叙述。

## 现场核实（只读）

| 项 | 实测 |
| --- | --- |
| 两个 unit | `otter-buddy` / `colink-agent-app` 均 active |
| App 监听 | `127.0.0.1:31130`（页面/事件）、`127.0.0.1:31131`（MCP 代理） |
| App → 中枢 | `OTTER_BASE_URL=http://127.0.0.1:3000`（回环） |
| 中枢监听 | `*:3000`（旧版本行为，尚未部署监听收口；公网 3000 被安全组拒连） |
| nginx 站点 | 仅 `colink-agent-app.conf`（`app.<域名>` → `127.0.0.1:31130`）；中枢域名落到默认 server |
| CoLink App 探活 | `https://app.60.205.214.148.sslip.io/manifest.json` → 200 |
