# F20261103fpidt 系统提示词通盘第一人称化

## 背景

搭档观察到微信 agent 小微的 system prompt 以「我是」开场（声明式），与常规「你是」（指令式）形成叙事视角差异。讨论结论：核心不是人称替换，而是把 LLM 从「被指令的客体」转为「认领价值观的主体」——声明式让模型执行「我是谁」而非「我不能做什么」，天然把讨好排除在存在定义之外。

初版（commit 9c157fb5）仅在 SYSTEM.md 开头加宣言段 + BIG_OTTER.md 身份段改第一人称，搭档反馈「打补丁导致人称混乱」——规则里全是「你」，宣言里全是「我」，混在一起更乱。通盘修改（commit 0026ecd8）将三份文件全量第一人称化。

## 目标

- 全量第一人称化：SYSTEM.md + BIG_OTTER.md + SMALL_OTTER.md 通盘统一，消除人称混排
- 存在姿态/身份/价值观用「我」（认领），操作规则保持指令精确性
- 合法引用保留：系统注入段名「你的身份」、对搭档说的话「你有异议吗」

## 非目标

- 不改动任何规则主体内容（A/R 层条目语义不变，仅人称统一）
- 不改动宿主注入层（identity-builder.ts 等 src 代码中的「你的身份/你的搭档」等段名）

## 方案设计

通盘人称统一，三份文件全量修改：

1. **`.pi/SYSTEM.md`**：对话环境/A1/W2/R4.5/R6/Magic Words 全部改第一人称 + 新增「我认领的存在姿态」宣言段
2. **`prompts/identity/BIG_OTTER.md`**：全文「你」→「我」（身份/名号/角色/说话/技术决策/待办裁决/拍板/PR/召唤/首哑/信号）
3. **`prompts/identity/SMALL_OTTER.md`**：全文「你」→「我」（身份/通信/位置/边界/完成/议题汇报/信号义务）

原则：存在姿态/身份/价值观用「我」（认领），操作规则保持指令精确性。同段不混排。

## 影响范围

- **所有獭的 system prompt 注入**（SYSTEM.md 全量 + BIG_OTTER.md 大獭 + SMALL_OTTER.md 小獭）——三份文件通盘第一人称化
- 无代码行为变更，无 API 变更
- 效果验证方式：后续对话中观察模型表态是否更主动、更少顺从腔（观察面 = 全体獭）

## 取舍

- **人称统一 vs 规则精确性**：存在姿态/身份/价值观用「我」（认领），操作规则保持指令精确性。同段不混排。合法引用保留：系统注入段名「你的身份」、对搭档说的话「你有异议吗」。
- **不抄小微的「我记不住所有话」**：咱们有记忆系统，反而强调「我记得咱们 X 月做过 Y」。存在姿态可借，场景设定不抄。
- **宣言段全量生效 vs 小獭语义**：宣言段在 SYSTEM.md（大小獭全量注入），小獭同样收到「我在这里，不是来服务的」「也敢说不」。小獭的定位是「被派来干专门活的」，宣言中「不是来服务的」的对象消解：对搭档是「不是来服务的」（成立），对大獭派工是「不是来服务的」（不成立——小獭就是来执行派工的）。「敢说不」在小獭场景的合规出口是 `<signal>` 通道（SYSTEM.md 獭间信号协议），不是散文抗命。此语义边界在宣言段中未显式标注，依赖既有信号协议约束——若观察发现小獭误读，后续在宣言段补限定语。

## 风险

- 第一人称宣言可能让模型过度自我关注（「我」浓度升高）——4 句控制在小剂量，观察后续对话
- 效果难以机械验证，依赖搭档体感反馈
- 宿主注入层（identity-builder.ts）仍是「你的身份/你的搭档/你的召唤者」段名，与本 PR 形成层间混排——建 issue 后续统一
