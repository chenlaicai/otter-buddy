# 检视建议「同主题可完善项」强关联判定补例：随单做完整、不留尾巴（#1890 复盘）

## 问题（现场）

2026-11-16 #1890（宿主注入层身份文案全量第一人称化，#1756 收口）。检视獭 PASS 附 3 条建议，其中 S2：`dispatch-chain-engine.ts:827` roster 提示行「非你的搭档…你的搭档是 X」仍第二人称——与 PR 主题「全局第一人称」完全同源，但检视方建议「单独 issue 定夺」，作者（大獭）随后回复也推荐「B：另开 issue，不在 #1890 里改」。

搭档两轮纠正：
- 「为啥还残留给其他 issue。你这一次就给我把这件事做完整了结了！」（驳回另开 issue）
- 追问「你觉得这个 S2 应该用哪个更好？或者哪个才对」

最终判定：S2 与本 PR 语义强关联（同一收口性主题的残留），按既有「建 issue 前置闸」应**默认当场修**；「另开 issue」非合法出口。随单修完 S2（roster 行列 + 3 处测试断言 + 特性文档同步），#1890 合入（merge `a9390dc6`），#1756 自动 CLOSED。

## 根因

「建 issue 前置闸」（author-response-protocol.md）的强关联清单只列三类：守护本 PR 行为不回退 / 澄清本 PR 刚改口径 / 修复本 PR 变更直接引入或暴露的问题。**「收口本 PR 所涉主题的一致性可完善项」这一类不在清单里**——S2 属此类，却因「另一个注入层（F20260928wxid）/ 文件不在 PR 变更清单内」的表象被两方误判为弱关联。清单不全 → 判断失效 → 规则在场但没人用它。

## 方案

`author-response-protocol.md` 两处补全（零新机制，只把既有判断边界写全）：

1. **强关联清单补第 4 例**：收口本 PR 所涉主题的一致性可完善项（如本 PR 做「全局第一人称」，发现同一收口性主题的第二人称残留——同根因同口径，属强关联，默认当场修；「另开 issue」须过下方合法清单论证，未论证/未裁决即提非合法出口）——并带 #1890 S2 现场作反例。
2. **伪理由反面清单经检视去重不动**：「同主题但不在本 PR 变更文件内」是既有「涉及本 PR 未变更的文件」的严格子集（零判定增量），不新增；#1890 根因的修复本体在强关联判定层（第 4 例），伪理由层无补条必要。

## R8.5 准入三问

1. **决策者变了么**：没有。本单只是把既有规则的强关联判定写全，没有新增裁决权或转移决策层；方向决策仍归作者/搭档。
2. **靠自觉还是靠守卫**：**明示靠自觉+异体**——关联度分类是语义判断，不是数据能识别的；强关联清单显式补例是给自觉提供清晰判据，不假称机械托底。
3. **深潜成本降了吗**：降——同主题小尾巴在作者处置第一条决策树处即被判定为强关联、默认当场修，免去「另开 issue → 搭档纠正 → 随单返工」两轮往返（#1890 现场实付成本）。
