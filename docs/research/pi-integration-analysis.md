# Pi 集成方式对比分析

## 概述

本报告分析 Pi 的两种集成方式：**SDK 集成**（当前方案）与 **CLI 集成**，对比其架构差异、技术权衡和适用场景。

**核心结论**：**维持当前 SDK 方案**。理由：Otter 是单机 Node.js 应用，SDK 方式提供更低延迟、更简单运维、更好的类型安全，且团队已熟悉 SDK 方式。

---

## 1. 两种集成方式定义

| 方式 | 定义 | 通信方式 |
|------|------|---------|
| **Pi SDK** | 通过 npm 包直接嵌入应用进程 | 函数调用（进程内） |
| **Pi CLI** | 通过命令行工具作为独立进程运行 | MCP 协议（跨进程） |

---

## 2. 架构对比

### 2.1 Pi SDK 集成（当前方案）

```
┌─ Otter 进程（只有一个）──────────────────────┐
│                                              │
│  ┌─ frameworks/agent/ ─────────────────────┐ │
│  │  PiHarnessFactory                      │ │
│  │    AgentHarness (npm 库)                │ │
│  │      LLM -> AgentTool.execute()        │ │
│  │              └── 调用 usecase          │ │
│  │                    └── 调用 repository │ │
│  │                          └── SQLite    │ │
│  └────────────────────────────────────────┘ │
│                                              │
│  ┌─ HTTP Server ──────────────────────────┐ │
│  │  Express/Fastify                       │ │
│  │    SSE 流式推送                         │ │
│  └────────────────────────────────────────┘ │
└──────────────────────────────────────────────┘

特点：
- 单进程架构
- 函数调用，无协议开销
- 直接内存访问，无序列化
- 部署简单，无额外依赖
```

### 2.2 Pi CLI 集成（替代方案）

```
┌─ Otter 进程 ──────────────┐     ┌─ Pi CLI 进程 ──────────────┐
│                            │     │                            │
│  HTTP Server               │     │  Pi CLI                    │
│    │                       │     │    │                       │
│    ▼                       │     │    ▼                       │
│  MCP Client                │────>│  MCP Server               │
│    │                       │     │    │                       │
│    ▼                       │     │    ▼                       │
│  Tool 执行函数              │     │  AgentHarness              │
│    │                       │     │    LLM -> tool_call        │
│    ▼                       │     │           │                │
│  返回结果                   │<────│           ▼                │
│                            │     │    MCP tool_call 通知      │
└────────────────────────────┘     └────────────────────────────┘

特点：
- 双进程架构
- MCP 协议通信（JSON-RPC over stdio/SSE）
- 需要序列化/反序列化
- Tool 由 Otter 执行，Pi CLI 等待结果（待验证：Pi CLI 是否支持 MCP Server 模式）

**关键机制说明**：
1. Otter（MCP Client）发送请求给 Pi CLI（MCP Server）
2. Pi CLI 内部调用 LLM
3. LLM 返回 tool_call
4. **Pi CLI 通过 MCP 协议通知 Otter 执行 Tool**（Tool 是应用代码，不是 Pi CLI 的一部分）
5. Otter 执行 Tool 逻辑并返回结果
6. Pi CLI 继续处理

**待验证**：Pi CLI 是否支持 MCP Server 模式和 Tool 回调机制。从 Pi 是"嵌入式 Agent 库"来看，CLI 可能只是 SDK 的薄封装，不一定支持跨进程 Tool 调用。
```

## 3. 技术维度对比

### 3.1 进程模型

| 维度 | Pi SDK | Pi CLI | 分析 |
|------|--------|--------|------|
| **进程数量** | 1 个 | 2 个 | SDK 更简单，无进程管理开销 |
| **通信方式** | 函数调用 | MCP 协议 | SDK 零开销，CLI 有序列化/网络开销 |
| **数据共享** | 内存共享 | 需要序列化 | SDK 可直接传递对象，CLI 需要 JSON 序列化 |
| **错误处理** | 异常抛出 | 协议错误码 | SDK 更直观，CLI 需要解析错误协议 |
| **部署复杂度** | 低 | 高 | SDK 只需 npm install，CLI 需要额外安装 Pi CLI |

### 3.2 性能特征

| 维度 | Pi SDK | Pi CLI | 量化估算 | 数据来源 |
|------|--------|--------|---------|---------|
| **启动延迟** | 低（模块加载） | 高（进程启动） | SDK: ~100ms, CLI: ~1-2s | **估算值**，需实际测量 |
| **Tool 调用延迟** | 极低（函数调用） | 中等（网络往返） | SDK: <1ms, CLI: 10-50ms | **估算值**，需实际测量 |
| **内存占用** | 共享进程内存 | 独立进程内存 | SDK: 共享, CLI: 额外 100-200MB | **估算值**，假设 CLI 加载完整 Node.js 运行时 |
| **CPU 利用率** | 单进程 | 多进程 | SDK: 更高效（无上下文切换） | 基于操作系统进程调度原理 |

**数据来源说明**：
- 以上性能数据均为估算值，未经实际测量
- 实际性能取决于：Pi CLI 的实现方式、MCP 协议栈效率、网络延迟（如果跨机器）
- 建议在正式选型前进行基准测试

**MCP 协议开销分析**：
- 序列化/反序列化：JSON 编解码，数据量小时开销可忽略（<1ms）
- 协议握手：建立连接 + 版本协商，一次性开销（~10-50ms）
- 消息分帧：JSON-RPC over stdio/SSE，帧解析开销（~1-5ms/消息）
- 错误处理：协议级错误码解析 + 重试逻辑
- 连接管理：心跳检测 + 断线重连（如果需要）
- **总开销估算**：单次 Tool 调用 10-50ms（含协议往返），具体取决于实现

### 3.3 开发复杂度

| 维度 | Pi SDK | Pi CLI | 评估 |
|------|--------|--------|------|
| **初始集成** | 中等（npm 依赖 + TypeScript 类型） | 低（CLI 命令） | CLI 更快上手 |
| **Tool 实现** | 简单（函数实现） | 复杂（需要 MCP Server） | SDK 更直观 |
| **调试难度** | 低（同进程断点） | 高（跨进程调试） | SDK 更易调试 |
| **类型安全** | 高（TypeScript 原生） | 低（MCP 协议弱类型） | SDK 编译时检查 |
| **测试复杂度** | 低（直接 mock） | 高（需要 mock MCP） | SDK 更易测试 |

### 3.4 运维特征

| 维度 | Pi SDK | Pi CLI | 评估 |
|------|--------|--------|------|
| **进程管理** | 无需 | 需要守护进程 | SDK 更简单 |
| **日志聚合** | 统一日志流 | 分散日志 | SDK 更易排查 |
| **监控指标** | 应用内收集 | 需要额外采集 | SDK 更易集成 |
| **资源限制** | 应用级控制 | 进程级控制 | CLI 更灵活 |

### 3.5 扩展性

| 维度 | Pi SDK | Pi CLI | 评估 |
|------|--------|--------|------|
| **多 Agent 并发** | 自然并发（async/await） | 进程池管理 | SDK 更简单 |
| **跨语言支持** | 仅 Node.js | 任意语言 | CLI 更灵活 |
| **热更新** | 需要重启应用 | 可独立更新 CLI | CLI 更灵活 |
| **资源隔离** | 共享资源 | 进程级隔离 | CLI 更安全 |

### 3.6 可靠性

| 维度 | SDK 方式 | CLI 方式 | 评估 |
|------|---------|---------|------|
| **崩溃隔离** | 弱 | 强 | SDK：Agent 崩溃影响主应用；CLI：进程隔离，崩溃不影响主应用 |
| **故障恢复** | 需重启应用 | 可重启进程 | CLI 方式故障恢复更快 |
| **优雅降级** | 应用级控制 | 进程级控制 | CLI 方式可独立降级 Agent 功能 |
| **资源泄漏** | 影响主应用 | 仅影响 Agent 进程 | CLI 方式资源泄漏影响范围更小 |

**可靠性权衡**：
- **SDK 方式**：Agent 稳定性直接影响主应用，需要更严格的错误处理
- **CLI 方式**：进程隔离提供更好的容错性，但增加运维复杂度

### 3.7 安全性

| 维度 | SDK 方式 | CLI 方式 | 评估 |
|------|---------|---------|------|
| **进程隔离** | 无 | 有 | CLI 方式提供更强的安全边界 |
| **权限控制** | 应用级 | 进程级 | CLI 方式可独立控制 Agent 进程权限 |
| **数据隔离** | 共享内存 | 独立内存 | CLI 方式数据隔离更彻底 |
| **攻击面** | 共享进程 | 独立进程 | CLI 方式攻击面更小 |

**安全性权衡**：
- **SDK 方式**：Agent 代码与主应用同进程，安全边界较弱
- **CLI 方式**：进程隔离提供更强的安全性，但增加通信开销

### 3.8 测试策略

| 维度 | SDK 方式 | CLI 方式 | 评估 |
|------|---------|---------|------|
| **单元测试** | 简单（直接 mock） | 复杂（需要 mock MCP） | SDK 更易测试 |
| **集成测试** | 简单（同进程） | 复杂（跨进程） | SDK 更易测试 |
| **端到端测试** | 简单（单进程） | 复杂（多进程） | SDK 更易测试 |
| **调试难度** | 低（同进程断点） | 高（跨进程调试） | SDK 更易调试 |

**测试策略差异**：

**SDK 方式**：
```typescript
// 单元测试：直接 mock Tool
const mockTool = { execute: vi.fn() };
const harness = createHarness({ tools: [mockTool] });
await harness.prompt("test");
expect(mockTool.execute).toHaveBeenCalled();

// 集成测试：同进程，直接调用
const result = await harness.invoke("test");
expect(result.text).toContain("expected");
```

**CLI 方式**：
```typescript
// 单元测试：需要 mock MCP 协议
const mockMcpClient = { sendRequest: vi.fn() };
const otter = createOtter({ mcpClient: mockMcpClient });
await otter.sendToAgent("test");
expect(mockMcpClient.sendRequest).toHaveBeenCalled();

// 集成测试：需要启动 Pi CLI 进程
const cliProcess = spawn("pi-cli", ["serve"]);
// ... 等待连接、发送请求、验证响应
cliProcess.kill();
```

## 4. 架构决策树

```
选择集成方式时，按以下决策树判断：

1. 应用是否为 Node.js？
   ├─ 否 -> 选择 Pi CLI（SDK 仅支持 Node.js）
   └─ 是 -> 继续

2. 是否需要跨语言 Tool 调用？
   ├─ 是 -> 选择 Pi CLI（通过 MCP 协议）
   └─ 否 -> 继续

3. 是否对延迟敏感（<10ms Tool 调用）？
   ├─ 是 -> 选择 Pi SDK（函数调用无开销）
   └─ 否 -> 继续

4. 是否需要进程级资源隔离？
   ├─ 是 -> 选择 Pi CLI（独立进程）
   └─ 否 -> 继续

5. 是否需要独立更新 Agent 逻辑？
   ├─ 是 -> 选择 Pi CLI（可独立升级）
   └─ 否 -> 选择 Pi SDK（更简单）
```

**决策树局限性**：
- **过于简化**：只考虑了 5 个二元决策，没有考虑混合方式、渐进式迁移、成本因素
- **假设条件**：假设 Pi CLI 支持 MCP Server 模式（待验证）、性能数据准确（估算值）
- **未考虑因素**：团队规模和技能结构、项目时间线和预算、未来技术演进方向

**混合方式分析**：
混合方式（部分 Tool 用 SDK，部分用 CLI）在技术上可行，但增加复杂度：
- **优点**：可以针对不同 Tool 选择最优方式
- **缺点**：需要维护两套集成代码，增加调试复杂度
- **适用场景**：只有少数 Tool 需要跨语言支持时
- **建议**：除非有明确的跨语言 Tool 需求，否则不建议采用混合方式

## 5. Otter 项目验证

### 5.1 Otter 项目特征

| 特征 | 值 | 匹配 SDK | 匹配 CLI |
|------|-----|---------|---------|
| 语言 | Node.js/TypeScript | ✅ | ✅ |
| Tool 调用 | 调用 usecase（同进程） | ✅ | ⚠️ 需要跨进程回调 |
| 延迟要求 | 低（实时对话） | ✅ | ⚠️ 额外开销 |
| 部署环境 | 单机部署 | ✅ | ⚠️ 多进程管理 |
| Agent 数量 | 多个（大獭、设计獭、检视獭） | ✅ 自然并发 | ⚠️ 进程池管理 |

### 5.2 SDK 方式优势（匹配度高）

1. **单进程架构**：Otter 是单机应用，不需要分布式部署
2. **低延迟**：实时对话场景，Tool 调用需要极低延迟
3. **类型安全**：TypeScript 原生支持，编译时检查
4. **简单运维**：无额外进程管理，日志统一
5. **自然并发**：多个 Agent 通过 async/await 自然并发

### 5.3 CLI 方式潜在价值（当前不适用）

1. **跨语言 Tool**：如果未来 Tool 需要用 Python 实现（如 ML 模型），CLI 方式更灵活
2. **独立更新**：Agent 逻辑可以独立于主应用更新
3. **资源隔离**：Agent 崩溃不影响主应用

### 5.4 如果从零开始选择

如果项目从零开始，没有已实现的 SDK 方案，决策因素会有所不同：

- **技术因素**：SDK 方式仍有优势（低延迟、类型安全、简单运维）
- **团队因素**：如果团队熟悉 MCP 协议，CLI 方式的学习成本会降低
- **生态系统因素**：如果需要集成非 Node.js 工具，CLI 方式更有优势

**结论**：即使从零开始，SDK 方式仍是合理选择，但决策权重会有所不同。如果团队熟悉 MCP 协议且有明确的跨语言 Tool 需求，CLI 方式可能是更好的起点。

## 8. 何时考虑迁移到 CLI

如果出现以下信号，应重新评估 CLI 方式：

### 8.1 建议迁移的时机（满足以下任一条件）

1. **跨语言 Tool 需求确认**：
   - 需要集成 Python ML 模型、Go 高性能计算、Rust 系统调用
   - 该 Tool 无法用 Node.js 实现或性能不可接受

2. **独立更新需求确认**：
   - Agent 逻辑更新频率远高于主应用（> 5x）
   - 重启成本高（影响用户体验或业务连续性）

3. **资源隔离需求确认**：
   - Agent 内存/CPU 使用影响主应用稳定性
   - 隔离是必要需求，而非优化

4. **生态系统需求确认**：
   - 需要集成其他 MCP 兼容工具
   - CLI 方式的扩展价值明确

### 8.2 不建议迁移的情况

1. **团队技能不足**：团队对 MCP 协议不熟悉，学习成本高
2. **项目时间紧张**：没有足够时间进行 PoC 和基准测试
3. **需求不明确**：跨语言 Tool、独立更新等需求不确定
4. **Pi CLI 能力不足**：Pi CLI 不支持 MCP Server 模式

## 9. 迁移评估

### 9.1 迁移成本估算

| 阶段 | 工作内容 | 估算时间 | 风险等级 |
|------|---------|---------|---------|
| **阶段 1** | MCP Server 封装 | 1-2 周 | 中等（需要理解 MCP 协议） |
| **阶段 2** | MCP Client 集成 | 1-2 周 | 中等（跨进程通信调试） |
| **阶段 3** | 部署调整 | 3-5 天 | 低（运维脚本） |
| **总计** | - | 3-5 周 | - |

### 9.2 风险评估

| 风险 | 影响 | 概率 | 缓解措施 |
|------|------|------|---------|
| **Pi CLI 不支持 MCP Server** | 高（方案不可行） | 中等（需验证） | PoC 验证 Pi CLI 能力边界 |
| **性能不达标** | 中等（需要优化） | 低（估算保守） | 基准测试验证性能数据 |
| **团队技能不足** | 中等（需要培训） | 低（有学习曲线） | 提前培训 + 文档支持 |
| **集成复杂度超预期** | 中等（延期风险） | 低（架构清晰） | 分阶段实施 + 持续集成 |

### 9.3 回滚策略

**如果迁移失败，回滚方案**：

1. **代码回滚**：保留 SDK 方式代码，CLI 代码在独立分支
2. **数据回滚**：Session 数据兼容（都使用 Pi 的 JsonlSessionRepo）
3. **部署回滚**：CLI 进程停止，回退到 SDK 单进程模式
4. **回滚成本**：约 1-2 天（主要工作是文档更新和团队沟通）

## 10. 研究文档对齐

> 本文档基于 `docs/research/pi-capability-analysis.md` 的研究成果。

| 研究结论 | 本文档应用 |
|---------|-----------|
| Pi 是嵌入式 Agent 库（非外挂式 CLI） | SDK 方式是 Pi 的原生集成方式，CLI 是扩展用法 |
| MCP 解决跨进程通信问题 | CLI 方式需要 MCP 协议，SDK 方式不需要 |
| AgentTool 是应用代码 | SDK 方式下 Tool 是函数调用，CLI 方式下需要跨进程回调 |
| 冷启动模型（R17） | SDK 方式下更简单（函数调用），CLI 方式下需要管理进程生命周期 |
