# R20260821xmrv: Shadow Mind 与跨模型对抗审视

## 1. 背景

### 1.1 起因

来自 linux.do 社区的一篇帖子介绍了"Shadow Mind"方案：用两个并行的 AI agent（"代码与项目结构审计者"和"成功目标一致性审计者"）在代码生成过程中实时审查，大幅减少人工介入成本。

这引发了更深层的问题：**AI 审查 AI 的结构性局限是什么？如何突破？**

### 1.2 现状

otter-buddy 的当前审查流程：
- **adversarial-review skill**：代码实现完成后进行对抗审视
- **异体执行原则**：审视者不得是实现者（单 agent 场景下降级为搭档确认）
- **B1-B4 基础维度**：结构化审查方向（但更接近引导而非硬性 checklist）

问题：审视獭与实现獭默认使用相同模型，且审视者看到实现者的完整上下文。

## 2. 核心发现

### 2.1 上下文锚定效应（Context Anchoring）

LLM 的注意力机制硬性约束了输出是输入的条件分布。当检视者看到"我选择了方案 X，因为 Y"，这些信息成为推理的锚点。

**具体表现：**
- 检视者的推理起点从"X 到底好不好"偏移到"X 已被选，Y 是理由，让我验证 Y 是否合理"
- 被锚定的检视者倾向于验证（validate）而非质疑（challenge）
- 这比人类的 anchoring bias 更强——人类有独立记忆和经验可以对抗锚点，LLM 的推理被 attention 机制硬约束

**启示：** 异体执行（不同 agent 做审查）能解决"自己审自己"的问题，但不能解决"看到对方思路后被锚定"的问题。

### 2.2 同模型同盲区（Shared Model Blind Spots）

两个使用相同模型的 agent 共享同一份训练数据的隐性偏差。

**具体表现：**
- 两者共享同一套"什么是好代码"的隐性标准
- 一个在开发者看来"很自然"的架构选择，检视者也觉得"很自然"
- 真正的 bug 藏在两人都觉得没问题的地方
- LLM 生成的代码天然是"看起来对"的（训练目标就是 plausible），"看起来对但实际有微妙问题"的代码恰好是同模型都会漏过的

**启示：** "异体"如果只是同模型不同 prompt，实际上是不够的。真正的异体应该是不同模型。

### 2.3 Checklist 的来源悖论

Checklist 通过强制逐条检查来减少上下文锚定的影响。但如果 checklist 本身是 LLM 基于当前上下文临时生成的，则 checklist 也被同一上下文锚定——只是把问题往后推了一步。

**checklist 的来源光谱：**

| 来源 | 受当前上下文锚定？ | 有效性 |
|------|---------------------|--------|
| LLM 针对当前代码临时生成 | ✅ 被锚定 | 低——检查维度与开发者关注点重叠 |
| 预置的稳定规则（项目编码规范、架构红线） | ❌ 脱钩 | 中高——但覆盖面取决于规则制定者 |
| 历史教训沉淀（之前踩的坑） | ❌ 脱钩 | 高——针对已知问题模式 |
| 领域标准（OWASP、语言官方 best practice） | ❌ 脱钩 | 高——行业共识 |
| 人类专家定义（搭档拍板的硬性红线） | ❌ 脱钩 | 高——跟模型判断无关 |

**结论：** 有效的 checklist 必须是预置的、脱钩于当前上下文的、来自历史和领域知识的。LLM 临时生成的 checklist 不解决根本问题。

## 3. 三个改进维度

### 3.1 维度一：模型多样性（最强杠杆）

不同模型的训练数据不同、架构不同、隐性偏好不同，盲区的重叠面最小。

**类比：** 不同学科的专家会诊——各自的知识背景和判断模式不同，能互补发现对方看不到的问题。

**在 otter-buddy 中的实现：**
- 系统已支持 mimo、kimi、glm 三种模型
- 审视獭可以选择与实现獭不同的模型
- 实现方式：`otter-summon` skill 的 `modelAlias` 参数

### 3.2 维度二：同模型多次并发推理（有帮助但较弱）

即使同模型，多次独立推理可以覆盖概率分布的"尾部"——某些被低概率压制的判断路径偶尔会被采样到。

**局限：** 同模型同上下文，概率分布主干一样。核心偏差（被高概率锁定的"看起来对"的路径）不管跑多少次都会被重复选中。

**类比：** 让同一个专家反复看同一个病例——每次注意到的细节可能略有不同，但知识盲区是固定的。

**聚合策略：**
- 取合集（union）：覆盖面最大，审查场景更适合（漏报代价 > 误报代价）
- 取交集（intersection）：最可靠，但可能漏掉只有某次能发现的问题

### 3.3 维度三：结构化关注点分工（基础保底）

同一模型拆成不同角色，每个角色只关注一个维度（代码质量 vs 需求一致性 vs 安全性 vs 性能）。

**价值：** "强制注意力聚焦"本身有意义——不会因为关注了实现细节就忘了回头检查需求。

**局限：** 受同模型同盲区限制，是三个维度中最弱的。但作为 checklist 的补充仍然有效。

## 4. 三层防线模型

基于以上分析，提出三层防线叠加的审查架构：

```
┌─────────────────────────────────────────────┐
│  第三层：模型多样性                            │
│  不同训练分布的模型交叉审查，盲区不重叠         │
├─────────────────────────────────────────────┤
│  第二层：客观验证                              │
│  可执行的测试、运行结果，不依赖任何模型判断     │
├─────────────────────────────────────────────┤
│  第一层：结构化 checklist                      │
│  预置的、脱钩于当前上下文的已知问题模式检查     │
└─────────────────────────────────────────────┘
```

**各层的能力边界：**

| 层 | 能兜住什么 | 兜不住什么 |
|----|-----------|-----------|
| Checklist | 已知的问题模式（known unknowns） | 未知的新型问题（unknown unknowns） |
| 客观验证 | 可执行验证的功能正确性 | 架构质量、代码可维护性等软性指标 |
| 模型多样性 | 大部分语义层面的深层问题 | 训练数据未覆盖的全新问题类型 |

## 5. 对 otter-buddy 系统的建议

### 5.1 审查模型多样化（P0）

**建议：** adversarial-review skill 默认使用与实现者不同的模型。

**实现方式：**
- 实现獭用默认模型 → 检视獭用 mimo（强推理）
- 实现獭用 mimo → 检视獭用 kimi（长上下文分析）
- 仅在搭档显式指定时使用相同模型

### 5.2 预置项目级 checklist（P1）

**建议：** 在 skill 和 memory 中维护项目级审查 checklist，从历史 review 发现的问题中沉淀。

**实现方式：**
- adversarial-review skill 内置通用检查项（当前 B1-B4 的硬化版本）
- 项目级高频雷区通过 memory 积累，每次审查前加载
- 搭档可定义硬性红线，加入 checklist

### 5.3 审查前置：过程中的分阶段审查（P2）

**建议：** 借鉴 Shadow Mind 理念，不必等代码写完才审查。在实现过程中分阶段触发审查（如每完成一个模块/函数）。

**注意：** 需要平衡审查频率与打断成本。过频的审查会打断生成流，导致上下文碎片化。

### 5.4 关注点拆分审查（P2）

**建议：** 将审查拆为独立的关注点维度，每个维度由独立的审查 agent 负责：

- **代码结构审查者**：代码坏味道、架构违反、复杂度
- **需求一致性审查者**：是否满足原始需求、是否偏离设计
- **安全性审查者**：注入、权限、数据泄露风险

## 6. 开放问题

1. **审查频率的最优平衡点？** 过频打断生成流，过稀积累问题。需要实验数据。
2. **跨模型审查的 prompt 差异化策略？** 不同模型是否需要不同的审查 prompt 设计？
3. **checklist 的自动演化机制？** 如何从审查结果中自动提取新的 checklist 项？
4. **成本与收益的量化？** 多模型审查增加的 token 消耗 vs 减少的返工成本，平衡点在哪？
